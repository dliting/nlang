# The GIL and Multiple Carriers

## What this means for your program

Multiple carriers pay off in two situations: the program spends time inside **blocking native calls** (file and network input/output, where one task's wait overlaps another task's work), or in **pure-compute segments** — code that only reads and writes local variables (arithmetic, comparisons, branches, local assignments) executes concurrently across carriers. Object-dense code (heavy object construction, string concatenation, container operations) is still serialized segment by segment for now; finer-grained locking for those stores comes in a later release. The defaults therefore stay conservative: the embedding library runs a single carrier, and `nvm` uses at most four. Leave the carrier count alone unless measurement shows a benefit.

## How it works

The VM holds a **global interpreter lock** (GIL) that covers **store operations** — heap allocation and object fields, strings, containers, streams, and the internal tables of the synchronization primitives. Instruction segments that touch only frame-local state (constant loads, local assignment, arithmetic, comparison, branching) need no lock, so several carriers can each run a virtual thread at the same time; the moment an instruction writes shared storage, it takes the lock for that one operation and releases it when done. The store lock makes shared-memory updates mutually exclusive, so language code never has to guard shared memory against a second virtual thread. Context switches happen only at safepoints (function entry and loop back edges), bounded by a scheduler budget of about 1000 back edges per turn.

Garbage collection also stops the world at these safepoints: every executing thread reaches one, the last to arrive runs the collection, and execution then resumes. Programs cannot observe the pause.

A **carrier** is an operating system thread that runs virtual threads. The library defaults to a single carrier; embedding hosts opt in with `VmExecutor::SetCarrierThreadCount`, and `nvm` defaults to at most four (`--carriers=N`, 1..64). Multi-carrier parallelism comes from two kinds of window: a native call that declared a blocking section under version 5 of the native application binary interface (ABI) — the VM releases the GIL for its duration, so other carriers run other virtual threads — and the pure-compute segments themselves (the lock-free segments described above). A third-party native that does not declare its blocking section holds the GIL for the whole call and every carrier stalls.

Determinism in tiers: under a single carrier, the same program with the same input produces the same interleaving (FIFO queue plus a fixed back-edge budget). With multiple carriers, dequeuing applies **wake affinity** — a carrier scans a constant window at the head of the queue and prefers the context it last ran itself (a never-dispatched context counts as matching any carrier); if the window holds no match, the head dispatches. Affinity reorders which entry dispatches, for execution locality only, so the scheduling order is unspecified and changing the carrier count changes the interleaving; program correctness never rests on the interleaving — only on the `join`, channel, and mutex happens-before edges. Multi-carrier tests assert results after synchronization, never interleaving or durations. `sleep` is a scheduling hint with a lower bound: once every carrier is parked, a sleeper wakes within the operating system's timer granularity (about 15.6 ms on Windows). A paused debugger no longer holds the GIL: a freeze gate blocks new dispatches while the stop lasts, and each in-flight segment stops once it finishes (see [Known limitations](known-limitations.md)).
