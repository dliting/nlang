# Developing Libraries

NLang has exactly one library mechanism: a library is a directory on the import search path, and the standard library and third-party libraries go through the same discovery, compilation and execution path. This page is for library authors: how to organize a pure NLang library, how to write a mixed library with a native implementation, and how to distribute the result.

The design rationale behind the mechanism lives in [Library Mechanism](../vm-architecture/library-mechanism.md); the `import` syntax and visibility rules live in [Packages and Modules](../language-spec/packages.md). The examples here are identical to `examples/libdemo/` in the repository and compile as-is.

## 1. What a library is

A `.n` file directly inside a search directory is a package named after the file (minus the extension); subdirectories contribute dotted package names. Given a search directory `libs`:

```text
libs/
  mylib/
    math.n        -> package mylib.math
    text.n        -> package mylib.text
  quick.n         -> package quick
```

After `import mylib.math;` the consumer calls through the qualified name, e.g. `mylib.math.square(6)`. Imported members are not visible to bare names — making every dependency visible at the call site is deliberate.

The five search-path layers, `-I` and `NLANG_PATH` are covered under [ncc](../cli-tools/ncc.md) and [nvm](../cli-tools/nvm.md). Dotted-name libraries are not compiled into standalone units — they ship as project-file packages, see section 4.

## 2. A pure NLang library

The complete example is `examples/libdemo/` (flat: the library file sits next to the consumer):

```text
libdemo/
  main.n          the consumer program
  mylib.n         the library: two small math helpers
```

The entire `mylib.n`:

```text
// Library example: two math helpers forming their own compilation unit.
// A library has no entry point, so compile it with the build form first:
//   ncc build examples/libdemo/mylib.n -o mylib.ncu
int square(int x) {
    return x * x;
}

int sum(int[] values) {
    int total = 0;
    foreach (int v in values) {
        total += v;
    }
    return total;
}
```

The entire `main.n`:

```text
// Consumer example: imports mylib (same directory) and verifies it.
// After building mylib.ncu, compile and run in one step:
//   ncc examples/libdemo/main.n -I <dir holding mylib.ncu> -o main_run.ncu
// Exit 0 only when the assertions hold.
import io;
import mylib;

int main() {
    assert(mylib.square(6) == 36);
    int[] values = [1, 2, 3, 4];
    assert(mylib.sum(values) == 10);
    io.print("mylib ready: " + mylib.sum(values));
    return 0;
}
```

NLang emits one artifact per compilation unit: compiling `main.n` produces only the consumer's own unit, with no library code in it. The library unit is compiled once on its own, after which the consumer compiles and runs:

```text
> ncc build mylib.n -o mylib.ncu
> ncc build main.n -o main.ncu
> nvm main.ncu
mylib ready: 10
```

When `nvm` runs `main.ncu`, the loader sees it imports `mylib`, finds `mylib.ncu` along the search path, and links the two units at load time — a library never registers anywhere global; sitting on the search path is all it takes. (A library has no `main`, so the compile-and-run form `ncc mylib.n` reports "module has no entry point"; always compile libraries with the `build` form.)

A failed assertion throws and exits non-zero, so the example carries its own correctness check.

## 3. A mixed library: NLang plus a native implementation

When you need operating system application programming interface (API) access or existing C++ code, declare `native` functions in the library and ship a dynamic-link library (DLL) with it. The declaration side (`num.n`, package `num`):

```text
native int dbl(int x);

int quad(int x)
{
    return dbl(dbl(x));
}
```

The implementation side (`num_native.cpp`):

```cpp
#include <nlang/vm/NativeHost.h>

using namespace nlang::native;

static void Dbl(NativeHost* host, uint8_t* ret, const uint8_t* args, int argc)
{
    ReturnInt(ret, ArgInt(args, 0) * 2);
}

NLANG_DEFINE_NATIVE_INIT
{
    reg(registry, "num", "dbl", &Dbl);
    return NLANG_HOST_ABI_VERSION;
}
```

The contract between host and library — the application binary interface (ABI):

| Item | Convention |
|---|---|
| DLL name | `nlang_<namespace>.dll`, e.g. `nlang_num.dll` |
| Export | a single entry `nlang_native_init`, generated by `NLANG_DEFINE_NATIVE_INIT` |
| Registration | `reg(registry, "namespace", "function", &Impl)` dispatches by name |
| ABI version | the init returns `NLANG_HOST_ABI_VERSION`; a mismatch is rejected at load |
| Header | provided in the source repository (`include/nlang/vm/NativeHost.h`); no VM library to link against |
| Argument helpers | `ArgInt`/`ArgString`/`ReturnInt`/`ReturnString` and friends |

Compile the implementation into `nlang_num.dll` with any C++ compiler (add the repository `include/` to the header path) and place it next to `num.n`. When distributing, ship the library unit together with the DLL (next section). Typing rules for `native` declarations are in [Native Functions](../language-spec/native-functions.md).

## 4. Distribution

Two shapes:

- Source directory (flat): drop `mylib.n` into any search directory; consumers inline the signatures at compile time. The library unit is compiled once (`ncc build mylib.n -o mylib.ncu`, section 2) and shipped alongside the consumer. Simplest — and the shape the standard library uses.
- Precompiled package: `ncc build -p <project>.nproj -o <package>.npkg` packs the library units, for distributing without sources; dotted subdirectory libraries (e.g. `mylib/math.n`) ship in this shape as well. Unit images travel with the package and linking happens at load time — consumers point `-I` at the package directory and never need the library sources.

Consumers see no difference: both shapes are consumed as `import <package>;`; the five search-path layers are under [ncc](../cli-tools/ncc.md).

## 5. Compatibility notes

A host ABI version mismatch is rejected at load (the numbers are the versions each side reports and vary with the mismatch):

```text
Runtime error: native module '<DLL path>\nlang_mylib.dll' reports incompatible ABI version 999999; host expects 3
Backtrace:
  at use_mylib.main (use_mylib.n:13)
```

Rebuilding the native DLL against the newer NLang realigns the version. Beyond the host ABI there is no binary coupling: library and consumer compile independently.
