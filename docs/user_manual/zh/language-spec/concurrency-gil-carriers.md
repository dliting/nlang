# GIL与多载体

## 对你的程序意味着什么

多载体只有一种情形有收益：程序的时间花在阻塞式原生调用里——声明了阻塞段的原生，文件与网络输入/输出的等待能叠在别的任务的工作上。纯语言代码的程序加载体没有任何收益——字节码本来就一次只执行一个虚拟线程。所以缺省取向是保守的：嵌入库单载体，`nvm`至多4个。除非实测出收益，否则不用动载体数。

## 工作机制

虚拟机持有**全局解释器锁**（GIL，global interpreter lock）：任意时刻恰有一个虚拟线程在执行字节码，上下文切换只发生在安全点（函数入口与循环回边），并受每约1000个回边一次的调度预算约束。字节码层的互斥由GIL保证，语言代码无需担心两个虚拟线程同时改写共享内存。

**载体**（carrier）是承载虚拟线程执行的操作系统线程。库默认单载体；嵌入宿主经`VmExecutor::SetCarrierThreadCount`显式选入，`nvm`默认至多4个（`--carriers=N`，1..64）。多载体的并行只来自一类窗口：按ABI（应用二进制接口，application binary interface）第5版声明了阻塞段的原生调用——执行期间虚拟机交出GIL，其余载体可以运行其他虚拟线程（典型收益是把输入输出等待与其他工作重叠）；返回前重新取回GIL。未声明阻塞的第三方原生在整个调用期间持有GIL，其余载体全部停摆。

确定性分档：单载体下同一程序在相同输入下产生相同的交错顺序（FIFO队列＋固定回边配额）；多载体下出队带**唤醒亲和**——载体在队首常数窗内优先取自己上次执行过的上下文（从未分派过的上下文视作匹配任何载体），窗内未命中回退队首。亲和只为执行局部性重排取项，调度顺序因此未指定，改变载体数会改变交错顺序；程序的正确性不依赖交错——只依赖`join`、通道与互斥的happens-before（先行发生）。多载体测试断言同步后的结果，不断言交错顺序与时长。`sleep`只是带下界的调度提示：全部载体停泊后，睡眠者在操作系统定时器粒度内唤醒（Windows上约15.6ms）。调试器暂停时持GIL，全部虚拟线程冻结（见[已知限制](known-limitations.md)）。
