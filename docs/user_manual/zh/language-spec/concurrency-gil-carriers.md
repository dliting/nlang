# GIL与多载体

## 对你的程序意味着什么

多载体有两类情形有收益：程序的时间花在**阻塞式原生调用**里（文件与网络输入/输出的等待叠在别的任务的工作上），或者花在**纯计算段**里——只读写局部变量的代码（算术、比较、分支、局部赋值）能跨载体同时执行。对象密集的代码（大量创建对象、字符串拼接、容器操作）目前仍逐段串行，要到后续的细分锁版本才会放开。所以缺省取向仍是保守的：嵌入库单载体，`nvm`至多4个。除非实测出收益，否则不用动载体数。

## 工作机制

虚拟机持有**全局解释器锁**（GIL，global interpreter lock），它覆盖**存储操作**——堆分配与对象字段、字符串、容器、流和同步原语的内部表。只触及帧局部状态的指令段（常量装载、局部赋值、算术、比较、跳转）不需要锁，多个载体可以同时执行各自的虚拟线程；一旦指令要改写共享存储，取锁执行、完成即放。字节码层的互斥由存储锁保证，语言代码无需担心两个虚拟线程同时改写共享内存。上下文切换只发生在安全点（函数入口与循环回边），并受每约1000个回边一次的调度预算约束。

垃圾回收也在这些安全点停止世界：每个执行中的线程到达安全点，最后到达者执行回收，随后恢复执行。程序观察不到这次停顿。

**载体**（carrier）是承载虚拟线程执行的操作系统线程。库默认单载体；嵌入宿主经`VmExecutor::SetCarrierThreadCount`显式选入，`nvm`默认至多4个（`--carriers=N`，1..64）。多载体的并行来自两类窗口：按ABI（应用二进制接口，application binary interface）第5版声明了阻塞段的原生调用——执行期间虚拟机交出GIL，其余载体可以运行其他虚拟线程；以及纯计算段本身（上一段所述的无锁段）。未声明阻塞的第三方原生在整个调用期间持有GIL，其余载体全部停摆。

确定性分档：单载体下同一程序在相同输入下产生相同的交错顺序（FIFO队列＋固定回边配额）；多载体下出队带**唤醒亲和**——载体在队首常数窗内优先取自己上次执行过的上下文（从未分派过的上下文视作匹配任何载体），窗内未命中回退队首。亲和只为执行局部性重排取项，调度顺序因此未指定，改变载体数会改变交错顺序；程序的正确性不依赖交错——只依赖`join`、通道与互斥的happens-before（先行发生）。多载体测试断言同步后的结果，不断言交错顺序与时长。`sleep`只是带下界的调度提示：全部载体停泊后，睡眠者在操作系统定时器粒度内唤醒（Windows上约15.6ms）。调试器停机不再持有GIL：停机时冻结门阻止新分派，正在执行的段跑完后停住（见[已知限制](known-limitations.md)）。
