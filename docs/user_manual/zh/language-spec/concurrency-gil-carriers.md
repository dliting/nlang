# GIL与多载体

## 对你的程序意味着什么

多载体有多类情形有收益：程序的时间花在**阻塞式原生调用**里（文件与网络输入/输出的等待叠在别的任务的工作上）；花在**纯计算段**里——只读写局部变量的代码（算术、比较、分支、局部赋值）能跨载体同时执行；或花在**对象密集**的代码里——对象创建与字段读写无需加锁，容器、字符串、流、同步原语各持一把域锁，只有同类操作之间才互斥，不同域的操作彼此重叠。对象经`spawn`实参或通道跨载体共享后，其字段的并发读写属于数据竞争：可能读到过渡值，但不会损坏内存，协调共享可变状态须用`Mutex`。所以缺省取向仍是保守的：嵌入库单载体，`nvm`至多4个。除非实测出收益，否则不用动载体数。

## 工作机制

存储保护按**域**划分：堆与字符串的**分配**走每载体独立的空闲表，无需加锁；对象**字段读写**无需加锁；**容器**（List/Dict）、**同步原语**（mutex/通道侧表）、**流**与**字符串维护**（拼接摊平、常量缓存）各持一把域锁——同域操作串行，跨域操作并行。只触及帧局部状态的指令段（常量装载、局部赋值、算术、比较、跳转）同样无锁，多个载体可以同时执行各自的虚拟线程。域锁保证容器与字符串的内部结构永远不会被并发撕裂；共享对象的字段并发读写则属于数据竞争——可能读到过渡值，但不会损坏内存，协调共享可变状态须用`Mutex`。上下文切换只发生在安全点（函数入口与循环回边），并受每约1000个回边一次的调度预算约束。

垃圾回收也在这些安全点停止世界：每个执行中的线程到达安全点，最后到达者执行回收，随后恢复执行。程序观察不到这次停顿。

**载体**（carrier）是承载虚拟线程执行的操作系统线程。库默认单载体；嵌入宿主经`VmExecutor::SetCarrierThreadCount`显式选入，`nvm`默认至多4个（`--carriers=N`，1..64）。多载体的并行来自多类窗口：按ABI（应用二进制接口，application binary interface）第5版声明了阻塞段的原生调用——执行期间该载体停泊并放锁，其余载体可以运行其他虚拟线程；不触碰共享存储的原生直调（按ABI约定这类原生不得等待）；以及纯计算段与无锁存储访问本身（前文所述的无锁段）。宿主注册的回调一律走阻塞段协议，等待期间不占用任何载体。

确定性分档：单载体下同一程序在相同输入下产生相同的交错顺序（FIFO队列＋固定回边配额）；多载体下出队带**唤醒亲和**——载体在队首常数窗内优先取自己上次执行过的上下文（从未分派过的上下文视作匹配任何载体），窗内未命中回退队首。亲和只为执行局部性重排取项，调度顺序因此未指定，改变载体数会改变交错顺序；程序的正确性不依赖交错——只依赖`join`、通道与互斥的happens-before（先行发生）。多载体测试断言同步后的结果，不断言交错顺序与时长。`sleep`只是带下界的调度提示：全部载体停泊后，睡眠者在操作系统定时器粒度内唤醒（Windows上约15.6ms）。调试器停机不再持有GIL：停机时冻结门阻止新分派，正在执行的段跑完后停住（见[已知限制](known-limitations.md)）。
