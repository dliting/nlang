# 11. 并发

## 11.1 线程与载体

NLang并发构建在*虚拟线程*之上：由实现调度到*载体*线程（即操作系统线程）上的轻量执行上下文。一个程序的各上下文共享一个堆（§10.2）：每个上下文看到同样的对象。同一时刻恰好有一个上下文执行字节码，受实现内部的全局锁管辖；上下文切换只在安全点发生——函数入口与循环回边——且每个上下文最多运行有界数目的回边，之后另一个才可被派发。

`thread`标准库包（第17章）驱动上下文；它的声明位于标准库，其实现内建于虚拟机。

- `thread.spawn(f)`接受一个零参函数值（§7.4）：一个自由函数、一个绑定方法，或持有其一的变量。它启动一个新上下文并立即返回其句柄。类型为`func<void>`的委托产出`Thread`句柄；类型为`func<T>`的委托产出`Future<T>`句柄（§11.5）。
- `thread.join(t)`挂起调用上下文，直到目标上下文结束。多个上下文可以join同一目标；它们都会被唤醒。join一个已结束的上下文立即返回；把上下文join到自己身上是*宿主级*执行期错误（§9.1）。
- `thread.yield()`把调用上下文移到运行队列的队尾。
- `thread.id()`产出当前上下文的标识符：入口上下文是`0`，派生的上下文非零。
- `thread.sleep(ms)`挂起直到截止时间；`sleep(0)`是一次yield；负时长是*宿主级*执行期错误（§9.1）。截止时间是下界：睡眠者在宿主的定时器粒度之内醒来。

逃出派生上下文体顶部的异常把该上下文标记为*失败*；它既不传播到宿主，也不传播到入口上下文。失败经由`join`浮现——或经由该上下文`Future`上的`get()`（§11.5）——即原始异常对象，其类、`message`与`backtrace`都保持不变（§9.3）。

*载体*是运行上下文的操作系统线程。库默认是一个载体；宿主可以配置更多。一个载体运行上下文期间，其余载体等待：字节码执行保持互斥，所以语言代码从不为共享内存设防以对抗并发上下文。锁只在一个窗口释放——按原生应用二进制接口声明了阻塞段的原生调用（§22.7）——并在原生返回之前重新取得；未声明阻塞段的原生在整个调用期间持有锁。

入口上下文返回时，程序结束：仍在停泊或排队的上下文被丢弃而不再运行。若没有上下文可运行、没有定时器挂起、也没有原生调用被阻塞，实现把死锁报告为*宿主级*执行期错误（§9.1）而非无限等待。

挂起操作——对未完成目标的`join`、对未完成目标的`Future.get()`、有争用的`lock`、空通道的`recv`、满通道的`send`、`sleep`与`yield`——冻结上下文的完整状态：帧、局部变量、处理器状态（§9.2）与指令位置。停泊过的`try`体之后的`throw`仍能到达该体的`catch`；`finally`仍恰好运行一次；停泊过的`catch`之后的重新抛出仍重新抛出（§9.1）。这些规则在嵌套求值窗口内部同样成立——一次`toString`求值，或运行中触发的宿主回调：窗口挂起，等待期间其他上下文运行，之后原地恢复。唯一例外是没有在飞载体的宿主`call()`窗口（run之外发起）：那里挂起操作被拒绝为*宿主级*执行期错误（§9.1），`thread.spawn`以同样方式被拒绝——窗口等待期间没有任何载体可调度任何东西。

## 11.2 Mutex

`Mutex`是不可重入的互斥锁。它是一个*句柄类*：其实例包装实现管理的对象、其构造器与方法内建于虚拟机、其名字无需导入的内建类（§12.4）。

- `lock()`取得锁。另一上下文持锁期间，调用者在一个队列中停泊，并按到达序被唤醒。锁定调用者已经持有的互斥锁会永远停泊：没有东西能唤醒调用者，程序在§11.1的退出策略下结束——若没有别的东西能推进，就是§11.1的死锁报告；否则该停泊上下文在入口上下文返回时被丢弃。
- `unlock()`释放它。解锁调用者并未持有的互斥锁是*宿主级*执行期错误（§9.1）。
- `tryLock()`从不停泊：锁空闲时它取得锁并产出`true`，被持有时产出`false`。

跨`yield`或`sleep`持有互斥锁是合法的：持有者离开期间，互斥保证不失效。

## 11.3 Semaphore

`Semaphore`最多容纳N个上下文进入一个区段：互斥锁容纳一个，信号量容纳N。它由`concurrent`标准库包提供（第17章；需要导入，§12.4）：

- `Semaphore(n)`设置初始许可数。负的`n`让计数从亏空开始：`release`必须把它抬过零，任何`acquire`才能推进。`0`是合法的——信号切换形态，等待者在`acquire`处停下，直到后来的`release`放行。
- `acquire()`取一个许可。计数不为正期间，调用者以让出轮次的方式等待（§11.1）——协作式自旋，而非停泊——并发等待者之间的顺序是*未指明*的（§0.4）。
- `release()`归还一个许可：计数加一。没有所有权要求：没有配对`acquire`的`release`是合法的，且计数可以超过初始值。

> 实现注记。计划中的同步原语工作会把这种库形态替换为句柄类（§11.2）：`acquire`按到达序停泊，新增`tryAcquire()`，负的`n`成为*宿主级*执行期错误（§9.1）。

`concurrent`标准库包（第17章）还提供`WaitGroup`：`add(n)`累计未结单位，`done()`注销一个，`wait()`停泊直到计数到达零。约定是`add`先于`wait`、`done`与`add`配对：不配对的`done`会让`wait`提前放行，缺失的`done`会让它永远停泊——程序在§11.1的退出策略下结束。

## 11.4 Channel

`Channel<T>`在各上下文之间传递值。元素类型实参是必需的：它驱动发送时的装箱与接收时的拆箱，机制与`List<T>`相同（§4.10）；引用元素直接穿过。通道是句柄类（§11.2）。

构造有两种形态：`{}`创建无界通道；`Channel(n)`创建缓冲容量为`n`的通道——`0`表示无界，`n >= 1`给缓冲定界，负的`n`抛出`Exception`（§9.3）。

- `send(v)`把值追加到缓冲。无界通道上它从不停泊；有界通道上，缓冲满时它在一个队列中停泊，随槽位空出按到达序恢复。
- `recv()`在缓冲非空时取走头部值；否则停泊，直到某次`send`或某次`close`。
- `close()`关闭通道；它幂等，且缓冲中已有的值被保留。

关闭经由可捕获的`ChannelClosedException`（§9.3）被观察到。`close`之后，`recv`仍交付缓冲中的值；缓冲排空后，再`recv`抛出该异常，而关闭之后的任何`send`立即抛出它。停泊的等待者看到同样的边界：`close`先把缓冲排入停泊的接收者，然后用该异常唤醒其余的接收者与每个停泊的发送者。

## 11.5 Future

`Future<T>`是派生上下文返回值的取值句柄，由对`func<T>`委托的`thread.spawn`产出（§11.1）。

- `get()`停泊直到目标结束，然后产出其类型为`T`的返回值。若目标失败，`get()`重新抛出原始异常对象（§9.3）。多个上下文可以对同一个future调用`get()`；它们都以同一个值或同一个对象醒来。对已结束的future调用`get()`立即返回，且可以反复调用。一个上下文不能对自己派生的future调用`get()`：那次调用是*宿主级*执行期错误（§9.1），因为没有东西能唤醒该上下文。
- `isDone()`从不停泊：目标一结束——正常结束或失败——它就产出`true`。

## 11.6 允许的交错

单载体之下调度是确定性的：严格的先进先出队列配固定的回边预算，所以同一程序同一输入在每次运行中产出同样的交错，`sleep`的截止时间除外——它们跟随宿主的时钟（§11.1）。

多载体之下，派发可以重排：载体偏好它最后运行的上下文，所以哪个上下文先离开队列是*未指明*的（§0.4），且改变载体数目会改变交错。仍然得到保证的是同步之后的结果：`join`、`Future.get()`、通道交接与互斥锁的释放到取得，各自构成一条*happens-before*边——较早上下文在边之前做出的每次写，在边之后对较晚上下文可见。程序的正确性立足于这些边，绝不立足于交错；多载体程序断言的是同步之后的结果，绝不断言交错或时长。
