# 3.9 包与导入查找

## 3.9.1 文件角色

NLang以四种文件搬运代码。

- **`.n`——源文件。** 一个文件是一个编译单元（§3.1），也是代码同一性的单位——*包*。包的名字是它被发现时所在搜索根（§3.9.2）之下的相对路径，每个目录一个点分段；没有任何文件内语法为包命名。
- **`.ncu`——单元映像。** 一个包的编译产物。其中的跨包引用是*导入槽*——一个目标包路径加一个限定名——绝不是体（§3.9.3）。格式见第20章。
- **`.npkg`——包档案。** 单元映像的容器，每个包一个成员，每个成员以其包路径命名。一次项目构建产出一个带*入口记录*的档案，记录命名入口单元（§3.2）；库档案省略该记录——标准库以`stdlib.npkg`分发（§3.9.4）。格式见第21章。
- **原生宿主库。** 承载`native`实现的宿主动态库，由声明它的包命名，而该包必然是单段的（§7.5）。

包的名字只有一个来源——文件相对其匹配搜索根的路径——别无其他：

```nlang
// stdlib/io.n            -> 包"io"
// <根>/vendor/graphics.n（配-I <根>）-> 包"vendor.graphics"
// <根>/gfx/color/deep.n（配-I <根>）-> 包"gfx.color.deep"
import io;
import vendor.graphics;
import gfx.color.deep;
```

各单元没有提供入口（§3.2）的构建产出库产物：可被其他构建导入，不可运行。

*资料性：*`native`声明的宿主动态链接库（DLL，dynamic-link library）按包的**首段**命名（`nlang_<段>.dll`），因此多段包（`gfx.color.deep`）里的`native`无法命名宿主库，会在编译期得到诊断。

## 3.9.2 导入解析

一个有序目录集合——*搜索路径*——服务于编译期源码发现、运行期产物装载（§3.9.3）与原生宿主库（§7.5）。路径按此顺序组装，靠前的条目优先：

1. 每个`-I <dir>`命令行选项，按出现顺序；
2. 项目文件的`<ImportPaths>`条目；
3. 本地目录：项目、源码或模块所在目录；
4. 环境变量`NLANG_PATH`，在Windows上按`;`切分，在POSIX上按`:`切分；
5. 系统默认：标准库目录、可执行文件所在目录、当前目录。

条目会被规范化；一个目录被列出多次时保留其首次出现（路径在Windows上不区分大小写地比较）。每个工具都包含全部三个系统默认目录；它们的相对顺序是*未指明*的（§0.4）。

对包路径`a.b.c`的导入（§3.3）命名某个搜索根之下的源文件`a/b/c.n`。编译期：

- 若恰好一个根提供该文件，该单元被内联进本次编译（§3.1）；每个文件只内联一次，被内联单元的导入按同样的规则解析，直至不动点；
- 若两个或更多根提供它，那是点名各源路径的编译期错误：一个包名在一次构建中唯一，绝不静默遮蔽；
- 若没有根提供源码：单段路径`c`（§3.3）解析到一个外部产物——第一个持有`c.ncu`或`c.npkg`的搜索目录，同名时单元映像先于档案——其声明以桩的形式进入构建；构建内没有源码的带点路径是编译期错误，因为外部产物只承载单段名字（§3.3、§20.2）。

内联为发起导入的编译解析声明；它不复制任何体。编译产物以包路径点名其依赖，并在运行期与它们链接（§3.9.3）。

*资料性：*搜索路径在实际中如何配置与使用。命令行用法：

```text
ncc build app.n -o app.ncu -I C:\libs\mylib
nvm app.ncu -I C:\libs\mylib
ndb --machine app.ncu -I C:\libs\mylib
```

项目在`.nproj`中用`<ImportPaths>`持久化搜索目录（路径相对项目文件存储）：

```xml
<Project name="app">
  <Sources><File path="src/main.n"/></Sources>
  <ImportPaths><Dir path="../libs"/></ImportPaths>
</Project>
```

**在nide中配置**：全局搜索路径在「工具 → 选项 → 库搜索路径」，项目级路径在「项目 → 属性 → 库搜索路径」；两处都支持添加、移除、上移、下移与浏览目录，项目路径优先于全局路径。更改后会自动重建符号索引，代码补全与「转到定义」随之刷新。

**查看与跳转源码**：在编辑器中，对带包名前缀的符号使用「转到定义」——F12、F6或按住Ctrl点击（此时手形光标标出可跳转处）——即可打开对应`.n`并跳到声明处：`native`声明显示签名与文档，普通函数显示可编辑的实现。`import`语句的包名本身也是跳转目标——在其上使用「转到定义」即打开声明该包的源文件。按住Ctrl悬停时，可跳转的名称呈蓝色下划线（超链接样式）；光标停在可跳转处时，「编辑」菜单与编辑器右键菜单中的「转到定义」（F12）一并可用。跳转与补全可见的包覆盖标准库、已配置的库目录、打开工程的目录与各打开文件所在的目录；修改库后重新构建即生效。

## 3.9.3 模块同一性与装载

包的同一性就是那个点分名。一次构建对每个包名至多携带一个源码（§3.9.2），而编译产物中的每个类、结构体与函数都以其包限定名为键（`main.main`、`alib.Point`）；实现自有的内建保持其裸键（`Object`、`List`）。限定键就是链接的拼写——链接、流与各工具皆然。

运行期，装载器从入口产物出发，急切地走完导入闭包：被导入单元点名的每个包路径都在执行开始之前解析并装载。解析遵循搜索路径（§3.9.2）：入口档案自身的成员最先——与入口同批分发的兄弟单元——然后按顺序逐个搜索目录，同一目录内`<path>.ncu`文件先于任何`.npkg`的成员（档案按文件名顺序扫描）。首个匹配胜出，且每个包路径至多装载一次。

所有装载的单元以限定名链接进一个运行时模块：一次跨包调用到达被解析产物的体。作为单个模块导入的档案必须恰好暴露一个单元——一个入口记录，或恰好一个成员。

闭包问题——缺失的包、不可读的产物——被一次性收集并报告，列出搜索过的每个目录，而不是每次浮现一个失败。

### 限定名

包声明的一切都可以通过限定名访问——`包.成员`（点分包则是`包.子包.成员`）。导入只开放限定名：`import lib;`之后写`lib.f()`，裸名`f()`不会经由导入解析。（与调用方同目录的文件共享该目录的裸名池——同目录规则不变。）

限定类型名同样这样拼写：`alib.Point`、`gfx.color.deep.Shade`。与函数不同，类型在全程序内还可以裸名访问，无论由哪个包声明（§3.6）。末段相同的两个包（`a.io`与`b.io`）是两个不同的包，各自的函数与类型互不相串。

### 限定表键

*资料性：*限定键也是调试器与工具在任何指名符号之处的统一拼写：

- 断点写限定名：`b main.main`、`b mathutil.triple`；
- 回溯与停止行打印限定名：`#0  main.main (main.n:6)`、`Stopped: utils.helper.inner (helper.n:6)`；
- `ndisasm -func main.main`按同一拼写过滤；
- 函数类型的值格式化为其键：`func alib.twice`。

*资料性：*面向读者的值的格式化输出——对象的默认`toString()`（`Point@1a2b`）与调试器的值显示（`Point{x=2, y=5}`）——用**末段名**：限定键的最后一段，即源代码书写类型的原名。

限定键仍是链接（链接期、流、反汇编）的拼写；值的格式化输出展示的是类型本身，不是它的链接身份。

跨模块边界上重载同样按参数类型解析：当一个包声明了两个同名同参数数但参数类型不同的函数时，调用点按类型的选择会传到链接器，链接器把每处调用连到被选中重载自己的记录。因此导入的重载集精确链接，没有按名字＋参数数的歧义。见[重载解析](../../language-spec/overload-resolution.md#跨模块重载)。

### 流与字面量

`readStruct`/`readObject`以字符串取类型名。该字面量在**编译期**按本文件可见的包（自身包 + 已导入的包）解析为声明的限定表键，到达VM的永远不会是裸名。两个可见包声明同名类型时字面量有歧义——编译错误要求写限定形（`readStruct("alib.S")`）。对象流同样存限定类键：一个程序写出、另一个程序读入的对象必须来自相同的包布局，因为读取端按键直接查表。

### 限定类型上的泛型

内建泛型容器支持类型实参（`List<int>`、`Dict<string, int>`）。带类型实参的限定**用户**类型（`alib.Box<int>`）不是语言的一部分：解析器以syntax error拒绝该形状。

## 3.9.4 标准库引导

标准库以两种形态随工具链分发：`.n`源码，经标准库目录发现并在编译期内联，以及`stdlib.npkg`，每个库单元一个成员，运行期从可执行文件所在目录装载。两个目录都是系统默认搜索条目（§3.9.2），所以一次普通构建无需配置就能找到标准库。

一条规则决定什么无需导入即可见：语言核心与基础容器恒在作用域，其余一切都是导入单元点名的包（§3.3）。恒可见的名字由内建预置包声明——`Object`、§9.3的`Exception`家族、`String`、`Array`、`List<T>`、`Dict<K,V>`——即全部集合；程序使用任何其他标准库名字都要导入其包。流句柄类`ByteStream`与`FileStream`（§15.1）今天同样免导入——这是仅存的不对称，保留到它们的声明源迁移为止。

并发名字按它们回答的问题分属两包：

| 包 | 提供 |
| --- | --- |
| `thread` | 谁来跑、结果在哪取：`Thread`、`Future<T>`、`Promise<T>`与`thread.*`函数（§11.1、§11.5） |
| `concurrent` | 跑起来之后怎么配合：`Mutex`、`Semaphore`、`ReentrantMutex`、`AtomicInt`、`Channel<T>`、`ChannelClosedException`、`WaitGroup`（§11.2–§11.4、§11.6） |

标准库包像其他包一样导入（§3.3）；第14–18章描述它们所持有的单元。`.n`源码中的声明是每个包——包括预置包——的真源；实现把声明的native成员绑定到其内建实现。

*资料性：*NLang的库由**`.n`源文件**承载：标准库的`math.n`/`io.n`/`fs.n`/`thread.n`/`concurrent.n`随工具链分发，第三方库就是某个目录中的一组`.n`（可选搭配native动态库）。文件内用`native`关键字声明在NLang之外实现的函数（`native void print(string s);`）——这类声明只有签名与文档注释、没有函数体；没有`native`标记的普通函数则是可阅读、可修改的NLang实现。一个库可以同时包含两者（混合库，与Python/Java/C#相同）。面向库作者的完整写法见[开发第三方库](../../libraries/developing-libraries.md)。
