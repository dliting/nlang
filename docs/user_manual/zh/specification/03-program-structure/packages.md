# 3.9 包与导入查找

## 3.9.1 文件角色

NLang以四种文件搬运代码。

- **`.n`——源文件。** 一个文件是一个编译单元（§3.1），定义一个模块。模块路径是该文件相对其匹配搜索根（§3.9.2）的路径，每个目录对应一个点分段；没有任何文件内语法为模块命名。
- **`.ncu`——单元映像。** 一个模块的编译产物。其中的跨模块引用是*导入槽*——一个目标模块路径加一个限定名——绝不是函数体（§3.9.3）。格式见第28章。
- **`.npkg`——包档案。** 自描述的容器，打包该构建的成员：每个模块一份单元映像、以其模块路径命名，外加构建附带的原生宿主库、每个原生成员以其文件名命名（§29.3）。一次项目构建产出带*入口记录*的程序包，记录命名入口单元（§3.2）；可导入的库包省略该记录。标准库以十三个领域包分发，`io.npkg`、`math.npkg`都在其中（§3.9.4）。格式见第29章。
- **原生宿主库。** 承载`native`实现的宿主动态库，由声明它的模块命名，而该模块必然是单段的（§7.5）。

模块路径只有一个来源——文件相对其匹配搜索根的路径——别无其他：

```nlang
// stdlib/io.n              -> 模块"io"
// <根>/vendor/graphics.n（配-I <根>）-> 模块"vendor.graphics"
// <根>/gfx/color/deep.n（配-I <根>）-> 模块"gfx.color.deep"
import io;
import vendor.graphics;
import gfx.color.deep;
```

各单元没有提供入口（§3.2）的构建产出库包：可被其他构建导入，不可运行。

*资料性：*`native`声明的宿主动态链接库（DLL，dynamic-link library）按模块路径的**首段**命名（`nlang_<段>.dll`），因此多段模块（`gfx.color.deep`）里的`native`无法命名宿主库，会在编译期得到诊断。

## 3.9.2 导入解析

一个有序目录集合——*搜索路径*——服务于编译期源码发现、运行期产物装载（§3.9.3）与原生宿主库（§7.5）。路径按此顺序组装，靠前的条目优先：

1. 每个`-I <dir>`命令行选项，按出现顺序；
2. 项目文件的`<ImportPaths>`条目；
3. 本地目录：项目、源码或模块所在目录；
4. 环境变量`NLANG_PATH`，在Windows上按`;`切分，在POSIX上按`:`切分；
5. 系统默认：标准库目录、可执行文件所在目录、当前目录。

条目会被规范化；一个目录被列出多次时保留其首次出现（路径在Windows上不区分大小写地比较）。每个工具都包含全部三个系统默认目录；它们的相对顺序是*未指明*的（§0.4）。

导入模块路径`a.b.c`（§3.3）时，可由源码或已编译库提供。编译期按以下规则解析：

- 源码在整个搜索路径上优先于产物。源码匹配项是搜索根下的`a/b/c.n`。恰好一个匹配项时，该单元被内联进本次编译（§3.1）；每个文件只内联一次，其导入继续按同一规则解析，直至不动点。两个或更多源码匹配项是点名各路径的编译期错误——一个模块路径在一次构建中唯一，绝不静默遮蔽。
- 没有源码匹配项时，产物查找按顺序访问搜索目录。在一个目录内，先查`a.b.c.ncu`，再按文件名顺序查其中各库包的成员表。第一个存在提供方的目录胜出。包文件名不参与模块解析：任何库包中名为`a.b.c`的成员都可以提供该模块。单段与点分模块路径遵循同一规则。
- 胜出目录中两个库包都包含同一模块时是编译期错误，例如`Duplicate package 'a.b.c': '<first>.npkg' and '<second>.npkg'.`。带入口记录的程序包是可执行闭包，不是编译期导入面，因此此处忽略程序包。
- `import a.b.*;`这样的通配导入取源码模块与库包成员的并集，纳入名字等于`a.b`或以`a.b.`开头的模块。空并集是编译期错误。每个入选单元自身的导入继续解析到同一不动点，因此只出现在已编译映像中的依赖也会纳入。

命中的产物提供声明桩。源码内联同样服务于声明分析；两种形态都不会把库函数体复制进消费方的单元映像。编译产物记录其模块路径依赖，并在运行期与依赖的函数体链接（§3.9.3）。因此源码形态与产物形态开放同样的导入和限定名行为。

源码和产物都无法提供模块时，标准未找到诊断会点名模块与搜索路径补救方式。扫描中无法打开的每个包都会追加一条附注：

```text
Module 'a.b.c' not found. Check the project Sources list or -I import path.
Note: package '<path>/broken.npkg' could not be opened.
```

若某个包的成员表点名该模块，但成员映像无效，则改报模块加载失败，不会把它描述为不存在。库包成员路径同样参与未导入模块诊断：若`tp.sub`只存在于产物中，未导入就使用`tp.sub.Fn.f()`时，诊断仍会建议可用的`import tp.sub;`，不会建议无效的`import tp.sub.Fn;`。

*资料性：*搜索路径在实际中如何配置与使用。命令行用法：

```text
ncc build app.n -o app.ncu -I C:\libs\mylib
nvm app.ncu -I C:\libs\mylib
ndb --machine app.ncu -I C:\libs\mylib
```

项目在`.nproj`中用`<ImportPaths>`持久化搜索目录（路径相对项目文件存储）：

```xml
<Project name="app">
  <Sources><File path="src/main.n"/></Sources>
  <ImportPaths><Dir path="../libs"/></ImportPaths>
</Project>
```

**在nide中配置**：全局搜索路径在「工具 → 选项 → 库搜索路径」，项目级路径在「项目 → 属性 → 库搜索路径」；两处都支持添加、移除、上移、下移与浏览目录，项目路径优先于全局路径。更改后会自动重建符号索引，代码补全与「转到定义」随之刷新。

**查看与跳转源码**：在编辑器中，对带包名前缀的符号使用「转到定义」——F12、F6或按住Ctrl点击（此时手形光标标出可跳转处）——即可打开对应`.n`并跳到声明处：`native`声明显示签名与文档，普通函数显示可编辑的实现。`import`语句的包名本身也是跳转目标——在其上使用「转到定义」即打开声明该包的源文件。按住Ctrl悬停时，可跳转的名称呈蓝色下划线（超链接样式）；光标停在可跳转处时，「编辑」菜单与编辑器右键菜单中的「转到定义」（F12）一并可用。跳转与补全可见的包覆盖标准库、已配置的库目录、打开工程的目录与各打开文件所在的目录；修改库后重新构建即生效。

## 3.9.3 模块同一性与装载

模块同一性就是点分模块路径。一次构建对每个模块路径至多携带一个源码或产物单元（§3.9.2），而编译产物中的每个类、结构体与函数都以其全限定名为键（`main.main`、`alib.Point`）；实现自有的内建保持其裸键（`Object`、`List`）。限定键就是链接的拼写——链接、流与各工具皆然。

运行期，装载器从入口产物出发，急切地走完导入闭包：被导入单元点名的每个模块路径都在执行开始之前解析并装载。解析遵循搜索路径（§3.9.2）：入口档案自身的成员最先——与入口同批分发的兄弟单元——然后按顺序逐个搜索目录，同一目录内`<path>.ncu`文件先于任何`.npkg`的成员（档案按文件名顺序扫描）。首个匹配胜出，且每个模块路径至多装载一次。

所有装载的单元以限定名链接进一个运行时模块：一次跨模块调用到达被解析产物的函数体。程序包的入口记录选择入口单元与函数。没有入口记录时，装载器从首个成员序列化的入口键开始；按库形态产出的包没有入口函数，因此不可运行。

闭包问题——缺失的模块、不可读的产物——被一次性收集并报告，列出搜索过的每个目录，而不是每次浮现一个失败。

import依赖图必须无环：一个模块不能直接或经传递链import回自己。环——无论由本构建的单元构成，还是外部产物内部已存在——是编译期错误，诊断按环的顺序给出环上的模块路径。同一条规则也保证每个模块的声明只有一份可达拷贝：环只能靠互相引导对方的过期映像来链接，环上的每个类都会存在两份。

静态状态跨模块边界遵循§4.8.8的懒惰规则，而非加载顺序：加载只链接代码、什么都不初始化，静态成员的首次使用——无论来自声明它的模块还是经import——先触发该类自己的初始化器。无人触碰的模块什么都不初始化。

### 限定名

模块声明的一切都可以通过限定名访问——`模块.成员`（点分模块路径则是`模块.子模块.成员`）。限定名是**绝对模块路径**：它只指向一个模块，导入绝不重定基——`import my.*;`之后调用`foo.bar.x()`仍指向顶层`foo.bar`模块，绝不是`my.foo.bar`。因此嵌套模块路径之间经限定名不可能冲突，无论作用域里有哪些通配。

显式导入开放两种拼写：`import lib;`之后，限定名`lib.f()`与非限定名`f()`均可调用——导入把`lib`的函数加进本文件的非限定名池。通配导入仅开放限定调用。同目录文件无需任何导入即共享该目录的非限定名池。

每个成员声明的访问级别在门之上继续生效。`private`把成员限定在自身单元内；`protected`把类成员开放给子类体，外来子类同样在内（§4.8.2、§4.8.11），而对顶层声明——一包一模块之下——它与`private`的可达范围相同（§7.1）；`public`——顶层函数与类型的缺省——对每个过门的单元开放。被拒成员对查找不可见，而不是命中后再拒绝：外来私有类型在限定名中无法解析（报「Type 'Vault' is not a member of package 'lib'.」），外来私有函数在两条路径上都报标准未找到诊断。在自身单元内，每个成员不论访问级别都可达。

限定类型名同样这样拼写：`alib.Point`、`gfx.color.deep.Shade`。与函数不同，类型在全程序内还可以非限定名访问，无论由哪个模块声明（§3.6）；访问级别在那里以同样的方式过滤外来候选。末段相同的两个模块路径（`a.io`与`b.io`）标识两个不同模块，各自的函数与类型互不相串。

### 限定表键

*资料性：*限定键也是调试器与工具在任何指名符号之处的统一拼写：

- 断点写限定名：`b main.main`、`b mathutil.triple`；
- 回溯与停止行打印限定名：`#0  main.main (main.n:6)`、`Stopped: utils.helper.inner (helper.n:6)`；
- `ndisasm -func main.main`按同一拼写过滤；
- 函数类型的值格式化为其键：`func alib.twice`。

*资料性：*面向读者的值的格式化输出——对象的默认`toString()`（`Point@1a2b`）与调试器的值显示（`Point{x=2, y=5}`）——用**末段名**：限定键的最后一段，即源代码书写类型的原名。

限定键仍是链接（链接期、流、反汇编）的拼写；值的格式化输出展示的是类型本身，不是它的链接身份。

跨模块边界上重载同样按参数类型解析：当一个模块声明了两个同名同参数数但参数类型不同的函数时，调用点按类型的选择会传到链接器，链接器把每处调用连到被选中重载自己的记录。因此导入的重载集精确链接，没有按名字＋参数数的歧义。见[重载解析](../07-functions/overloads.md#跨模块重载)。

### 流与字面量

`readStruct`/`readObject`以字符串取类型名。该字面量在**编译期**按本文件可见的模块（自身模块加已导入模块）解析为声明的限定表键，到达VM的永远不会是非限定名。两个可见模块声明同名类型时字面量有歧义——编译错误要求写限定形（`readStruct("alib.S")`）。对象流同样存限定类键：一个程序写出、另一个程序读入的对象必须采用相同的模块布局，因为读取端按键直接查表。

### 限定类型上的泛型

内建泛型容器支持类型实参（`List<int>`、`Dict<string, int>`）。带类型实参的限定**用户**类型（`alib.Box<int>`）不是语言的一部分：解析器以syntax error拒绝该形状。

## 3.9.4 标准库引导

标准库以两种形态随工具链分发：`.n`源码，经标准库目录发现并在编译期用于声明分析，以及十三个库包，运行期从该目录装载。这些包合计包含十四个库单元：

| 包档案 | 模块成员 |
| --- | --- |
| `concurrent.npkg` | `thread`、`concurrent` |
| `io.npkg` | `io` |
| `math.npkg` | `math` |
| `fs.npkg` | `fs` |
| `tensor.npkg` | `tensor` |
| `net.npkg` | `net` |
| `http.npkg` | `http` |
| `url.npkg` | `url` |
| `system.npkg` | `system` |
| `gzip.npkg` | `gzip` |
| `regex.npkg` | `regex` |
| `json.npkg` | `json` |
| `web.npkg` | `web` |

标准库目录是系统默认搜索条目（§3.9.2），所以一次普通构建无需配置就能找到两种形态。包文件名描述分发领域；导入解析的是各包中列出的模块成员，不是档案文件名。

一条规则决定什么无需导入即可见：语言核心与基础容器恒在作用域，其余标准库模块都必须由导入单元点名（§3.3）。恒可见的名字由预置模块`lang`与`containers`声明——`Object`、§8.3的`Exception`家族、`String`与`Array`在`lang`中；`List<T>`、`Dict<K,V>`与`Set<T>`在`containers`中——即全部集合。这两个模块在编译期嵌入，没有`.npkg`运行期成员。程序使用任何其他标准库名字都要导入其模块，流句柄类`ByteStream`与`FileStream`（§14.6）也不例外。

并发模块按它们回答的问题分工：

| 模块 | 提供 |
| --- | --- |
| `thread` | 谁来跑、结果在哪取：`Thread`、`Future<T>`、`Promise<T>`与`thread.*`函数（§10.1、§10.5） |
| `concurrent` | 跑起来之后怎么配合：`Mutex`、`Semaphore`、`ReentrantMutex`、`AtomicInt`、`Channel<T>`、`ChannelClosedException`、`WaitGroup`（§10.2–§10.4、§10.6） |

标准库模块像其他模块一样导入（§3.3）；第13–27章描述它们。`.n`源码中的声明是每个模块——包括预置模块——的真源；实现把其中声明的native成员绑定到内建实现。

*资料性：*第三方库既可以分发为`.n`源码目录，也可以分发为一个或多个库`.npkg`档案；原生动态库或散装放在旁边，或作为档案成员随档案分发（§29.3）。两种形态使用同一组模块路径。文件内用`native`关键字声明在NLang之外实现的函数（`native void print(string s);`）——这类声明只有签名与文档注释、没有函数体；没有`native`标记的普通函数则是可阅读、可修改的NLang实现。一个库可以同时包含两者（混合库，与Python/Java/C#相同）。面向库作者的完整写法见[开发第三方库](../../libraries/developing-libraries.md)。
