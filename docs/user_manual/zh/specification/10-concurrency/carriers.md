# 10.8 载体与并行

执行模型——虚拟线程、载体、类别锁与数据竞争规则——见§10.1；它们产出的调度见§10.7。本节覆盖运行多少个载体，以及多于一个载体时哪些工作会重叠。

### 配置载体

*资料性：*NLang的并发单位是**虚拟线程**——你用`thread.spawn`启动的任务。虚拟线程很轻量，一个程序里可以同时存在成千上万个；它们不是操作系统线程。真正执行虚拟线程的是**载体**：承载虚拟线程运行的操作系统线程。库默认1个载体；`nvm`至多4个（`--carriers=N`，1..64）；嵌入宿主经`VmExecutor::SetCarrierThreadCount`选入。大量虚拟线程分时复用少量载体——与Go的goroutine、Java的虚拟线程同一族模型。

### 还有没有全局锁

*资料性：*NLang没有整机的全局解释器锁（global interpreter lock，GIL——如果你熟悉Python，那个意义上的锁在这里不存在）。存储保护遵循§10.1的类别锁模型：每类数据一把锁，对象字段访问则完全不加锁。容器与字符串的内部结构因此永远不会被并发破坏。

不加锁的类别也有代价：对象一经跨载体共享（经`spawn`实参或通道），其字段的并发读写就是**数据竞争**——可能读到写入一半的过渡值，但不会损坏内存。要协调共享可变状态，用`Mutex`（§10.2）。

### 哪些代码真并行

*资料性：*单载体下一切串行（虚拟线程只是分时轮转）。多载体下能同时执行的：

- **纯计算段**——只读写局部变量的代码：算术、比较、分支、局部赋值；
- **对象密集代码**——对象创建与字段读写无锁；
- **不同类别的存储操作**——容器操作与流操作互不等待，只有同类操作才排队。

程序的时间主要花在**阻塞式原生调用**（文件与网络输入/输出）里也另有收益：这类调用在原生签名里标注了阻塞声明（§25.7），执行期间发起调用的虚拟线程挂起、锁全部释放，其余载体照常运行其他虚拟线程（同时在阻塞中的原生调用数至多与载体数相同，超出时退化为排队）。不触碰共享存储的原生直调（如数学函数）既不等待也不占锁。宿主注册的回调一律按阻塞式协议执行，等待期间不占用任何载体。阻塞声明如何书写，见[原生函数](../07-functions/native.md)与[开发原生库](../../libraries/developing-libraries.md)。

### 确定性与调度

*资料性：*

- **单载体（库默认）完全确定**：严格先进先出（FIFO，first in first out）轮转，每个虚拟线程连续执行1000次循环回边才让位（仅当另有可运行的虚拟线程时）；同一程序在相同输入下产生相同的交错顺序。单载体测试可以断言交错顺序与终值。
- **多载体顺序未指定**：调度器可按任意顺序取出可运行的虚拟线程（为缓存局部性会优先取上次执行过的），改变载体数会改变交错。程序的正确性不依赖交错——只依赖`join`、通道与互斥的happens-before边（§10.7）。多载体测试只断言同步后的结果，不断言顺序与时长。

虚拟线程的切换只发生在**安全点**——函数入口与循环迭代边界这些可以安全暂停的位置。垃圾回收同样等各载体到达安全点后进行，程序观察不到停顿（§9.2）。`sleep`是带下界的调度提示：当所有虚拟线程都在等待时，睡眠者按操作系统定时器粒度唤醒（Windows上约15.6ms）。调试器停机时阻止新的虚拟线程开始执行，正在执行的段跑完后停住（见[已知限制](../reference/known-limitations.md)）。

缺省取向是保守的：除非实测出收益，否则不用动载体数。
