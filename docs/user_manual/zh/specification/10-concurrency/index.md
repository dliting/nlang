# 10. 并发

NLang把并发工作跑成*虚拟线程*：调度到一小撮*载体*线程上的轻量执行上下文。本章规定执行模型与每个并发名字的契约：上下文与`thread`操作（§10.1）、锁与计数器（§10.2、§10.3、§10.6）、消息传递（§10.4）、结果句柄（§10.5）与允许的交错（§10.7）在本页；载体配置与并行（§10.8）与挂起与调度限制（§10.9）各有独立页面。

## 10.1 线程与载体

NLang并发构建在*虚拟线程*之上：由实现调度到*载体*线程（即操作系统线程）上的轻量执行上下文。一个程序的各上下文共享一个堆（§9.2）：每个上下文看到同样的对象。上下文只在安全点让出其载体——函数入口或循环回边——且每个上下文最多运行1000次循环回边，之后另一个才可被派发。

并发名字分属两个标准库包（第17章），各自按名导入（§3.9.4）：`thread`（声明于`stdlib/thread.n`）回答谁来跑、结果在哪取——`Thread`、`Future<T>`、`Promise<T>`与`thread.*`函数；`concurrent`（声明于`stdlib/concurrent.n`）回答跑起来之后怎么配合——`Mutex`、`ReentrantMutex`、`Semaphore`、`AtomicInt`、`Channel<T>`、`ChannelClosedException`、`WaitGroup`。它们的声明位于标准库，其实现内建于虚拟机。

- `thread.spawn(f)`接受一个零参函数值（§7.4）：一个自由函数、一个绑定方法，或持有其一的变量。它启动一个新上下文并立即返回其句柄。类型为`func<void>`的委托产出`Thread`句柄；类型为`func<T>`的委托产出`Future<T>`句柄（§10.5）。
- `thread.join(t)`挂起调用上下文，直到目标上下文结束。多个上下文可以join同一目标；它们都会被唤醒。join一个已结束的上下文立即返回；把上下文join到自己身上是*宿主级*执行期错误（§8.1）。
- `thread.isFailed(t)`从不停泊：目标以未捕获异常结束之后它产出`true`——运行期间与正常结束之后都是`false`。`thread.failure(t)`产出失败目标的原始异常对象，即`join`重新抛出的同一个实例；目标尚未失败时产出`null`。这次读取本身就算观察到失败，§10.1的运行结束报告不会因它触发。
- `thread.yield()`把调用上下文移到运行队列的队尾。
- `thread.id()`产出当前上下文的标识符：入口上下文是`0`，派生的上下文非零。
- `thread.sleep(ms)`挂起直到截止时间；`sleep(0)`是一次yield；负时长是*宿主级*执行期错误（§8.1）。截止时间是下界：睡眠者在宿主的定时器粒度之内醒来，且睡眠者按截止时间排序唤醒。

逃出派生上下文体顶部的异常把该上下文标记为*失败*；它既不传播到宿主，也不传播到入口上下文。失败经由`join`浮现——或经由该上下文`Future`上的`get()`（§10.5）——即原始异常对象，其类、`message`与`backtrace`都保持不变（§8.3）。没有任何上下文观测到的失败不会无声丢失：运行结束时实现把它报告到错误输出，每个未观测的失败上下文一行。

*载体*是运行上下文的操作系统线程。库默认是一个载体；`nvm`至多启动4个载体，接受`N`从1到64的`--carriers=N`；嵌入宿主经`VmExecutor::SetCarrierThreadCount`选入。执行不被一把全局锁串行化：存储保护按*数据类别*分组，每类一把锁——容器（`List`、`Dict`）、同步原语（mutex、信号量、通道）、流，以及字符串维护。同类操作互相串行，不同类同时进行，堆与字符串的分配不需要全局锁。对象字段读写不加锁，所以对象一经跨载体共享——经`spawn`实参或通道——其字段的并发读写就是*数据竞争*：可能读到写入一半的过渡值，但不会损坏内存。容器与字符串的内部结构因此永远不会被并发破坏，共享可变状态用`Mutex`（§10.2）协调。声明了阻塞段（§22.7）的原生调用在等待期间释放它持有的锁，让其他上下文运行；未声明阻塞段的原生在不持锁的情况下运行，其存储操作经自守护回调逐次取得类别锁。

入口上下文返回时，程序结束：仍在停泊或排队的上下文被丢弃而不再运行。若没有上下文可运行、没有定时器挂起、也没有原生调用被阻塞，实现把死锁报告为*宿主级*执行期错误（§8.1）而非无限等待。

挂起操作——对未完成目标的`join`、对未完成目标的`Future.get()`、有争用的`lock`、空通道的`recv`、满通道的`send`、`sleep`与`yield`——冻结上下文的完整状态：帧、局部变量、处理器状态（§8.2）与指令位置。停泊过的`try`体之后的`throw`仍能到达该体的`catch`；`finally`仍恰好运行一次；停泊过的`catch`之后的重新抛出仍重新抛出（§8.1）。这些规则在嵌套求值窗口内部同样成立——一次`toString`求值，或运行中触发的宿主回调：窗口挂起，等待期间其他上下文运行，之后原地恢复。唯一例外是没有在飞载体的宿主`call()`窗口（run之外发起）：那里挂起操作被拒绝为*宿主级*执行期错误（§8.1），`thread.spawn`以同样方式被拒绝——窗口等待期间没有任何载体可调度任何东西。

## 10.2 Mutex与ReentrantMutex

`Mutex`是不可重入的互斥锁。它是一个*句柄类*：其实例包装实现管理的对象、其构造器与方法内建于虚拟机。各并发句柄类由其所在的包声明（§3.9.4）——`Mutex`属`concurrent`，`Thread`与`Future<T>`属`thread`——所以它们的名字经包导入进入作用域，与其他包类无异。

- `lock()`取得锁。另一上下文持锁期间，调用者在一个队列中停泊，并按到达序被唤醒。锁定调用者已经持有的互斥锁会永远停泊：没有东西能唤醒调用者，程序在§10.1的退出策略下结束——若没有别的东西能推进，就是§10.1的死锁报告；否则该停泊上下文在入口上下文返回时被丢弃。
- `unlock()`释放它。解锁调用者并未持有的互斥锁是*宿主级*执行期错误（§8.1）。
- `tryLock()`从不停泊：锁空闲时它取得锁并产出`true`，被持有时产出`false`。

跨`yield`或`sleep`持有互斥锁是合法的：持有者离开期间，互斥保证不失效。

`ReentrantMutex`（同属`concurrent`）是同一契约的可重入形态：持锁的上下文可以再次`lock()`而不停泊，属主计数随之累积，`unlock()`只在计数归零时释放锁。在两个上下文之间它的行为与`Mutex`完全一致。它服务于方法取锁又互相调用的类；没有这种形状的代码取普通`Mutex`即可。

## 10.3 Semaphore

`Semaphore`最多容纳N个上下文进入一个区段：互斥锁容纳一个，信号量容纳N。它是`concurrent`标准库包的句柄类（第17章；需要导入，§3.9.4）：

- `Semaphore(n)`设置初始许可数。负的`n`是*宿主级*执行期错误（§8.1）。`0`是合法的——信号切换形态，等待者在`acquire`处停下，直到后来的`release`放行。
- `acquire()`取一个许可。没有许可可用期间，调用者在一个队列中停泊；`release()`把许可直接交给队首的等待者，按到达序。
- `release()`归还一个许可。没有所有权要求：没有配对`acquire`的`release`是合法的，且计数可以超过初始值。
- `tryAcquire()`从不停泊：有许可可用时它取走一个并产出`true`，否则产出`false`。

`concurrent`标准库包（第17章）还提供`WaitGroup`：`add(n)`累计未结单位，`done()`注销一个，`wait()`停泊直到计数到达零。约定是`add`先于`wait`、`done`与`add`配对：不配对的`done`会让`wait`提前放行，缺失的`done`会让它永远停泊——程序在§10.1的退出策略下结束。与句柄类不同，`WaitGroup`是包源码中声明的普通NLang代码，构建于`Mutex`与`Channel`之上。

## 10.4 Channel

`Channel<T>`在各上下文之间传递值。元素类型实参是必需的：它驱动发送时的装箱与接收时的拆箱，机制与`List<T>`相同（§4.12）；引用元素直接穿过。通道是`concurrent`的句柄类（§10.2）。

构造有两种形态：`{}`创建无界通道；`Channel(n)`创建缓冲容量为`n`的通道——`0`表示无界，`n >= 1`给缓冲定界，负的`n`抛出`Exception`（§8.3）。

- `send(v)`把值追加到缓冲。无界通道上它从不停泊；有界通道上，缓冲满时它在一个队列中停泊，随槽位空出按到达序恢复。
- `recv()`在缓冲非空时取走头部值；否则停泊，直到某次`send`或某次`close`。
- `close()`关闭通道；它幂等，且缓冲中已有的值被保留。

关闭经由可捕获的`ChannelClosedException`（§8.3）被观察到。`close`之后，`recv`仍交付缓冲中的值；缓冲排空后，再`recv`抛出该异常，而关闭之后的任何`send`立即抛出它。停泊的等待者看到同样的边界：`close`先把缓冲排入停泊的接收者，然后用该异常唤醒其余的接收者与每个停泊的发送者。

## 10.5 Future与Promise

`Future<T>`是一次计算的返回值的取值句柄——由对`func<T>`委托的`thread.spawn`产出（§10.1），或由`Promise`产出。它是`thread`的句柄类（§10.2）。

- `get()`停泊直到目标结束，然后产出其类型为`T`的返回值。若目标失败，`get()`重新抛出原始异常对象（§8.3）。多个上下文可以对同一个future调用`get()`；它们都以同一个值或同一个对象醒来。对已结束的future调用`get()`立即返回，且可以反复调用。一个上下文不能对自己派生的future调用`get()`：那次调用是*宿主级*执行期错误（§8.1），因为没有东西能唤醒该上下文。
- `isDone()`从不停泊：目标一结束——正常结束或失败——它就产出`true`。
- `Future.selectAny(futures)`接受一个`Future`值数组，停泊到任一成员定局，产出定局成员的下标——多个成员都已定局时取最小下标。失败的成员同样定局：获胜下标不携带异常，观测失败是获胜者上`get()`的职责。其余成员继续运行。空数组、`null`成员、多于64个成员、以及调用上下文自己派生的成员，是*宿主级*执行期错误（§8.1）。

`Promise<T>`（同属`thread`）是用户构造的完成源——派生future的对偶，服务于一个上下文算出、多个上下文等待的值。`promise.future()`铸造取值句柄：可重复铸造，每次铸造共享同一定局。`complete(v)`以值`v`定局；`completeExceptionally(e)`以异常对象`e`定局。恰有一次调用定局——先到者胜，后续调用无效果地产出`false`——每个等待者以该值醒来，或由`get()`把`e`重新抛入。

## 10.6 AtomicInt

`AtomicInt`（`concurrent`的句柄类）包装一个整数，其操作是原子的：每次读取、判定与写入构成一个不可分割的步骤，所以不同载体上的上下文绝不在一个操作内部交错。

- `AtomicInt(initial)`设置初始值；`AtomicInt()`为零。
- `load()`产出该值；`store(v)`替换它。
- `getAndSet(v)`替换该值并产出替换前的值。
- `compareExchange(expect, v)`仅当当前值等于`expect`时存储`v`，产出存储是否发生。
- `getAndAdd(delta)`加法并产出之前的值；`addAndGet(delta)`加法并产出新值；`incrementAndGet()`与`getAndIncrement()`是增量为一的形态，分别产出新值与之前的值。

命名跟随Java的`AtomicInteger`：`getAndX`产出操作之前的值，`xAndGet`产出操作之后的值。原子量只覆盖一个值：由多个字段组成的状态，或任何判定跨越多于一次调用的读-判-写，都属于`Mutex`（§10.2）的背后。

## 10.7 允许的交错

单载体之下调度是确定性的：严格的先进先出队列配固定的回边预算（1000），所以同一程序同一输入在每次运行中产出同样的交错，`sleep`的截止时间除外——它们跟随宿主的时钟（§10.1）。

多载体之下，派发可以重排：载体偏好它最后运行的上下文，所以哪个上下文先离开队列是*未指明*的（§0.4），且改变载体数目会改变交错。仍然得到保证的是同步之后的结果：`join`、`Future.get()`、通道交接与互斥锁的释放到取得，各自构成一条*happens-before*边——较早上下文在边之前做出的每次写，在边之后对较晚上下文可见。程序的正确性立足于这些边，绝不立足于交错；多载体程序断言的是同步之后的结果，绝不断言交错或时长。

### 并发模型：阻塞式书写，无异步着色

*资料性：*NLang属于**虚拟线程**一族（同Go、Java虚拟线程）：写并发代码就像写普通顺序代码——遇到等待就「停下让位」，调度器在挂起点之间交错推进各个虚拟线程。这套模型下「单线程的异步」就是默认形态：库默认只有一个载体，`thread.spawn`出的多个任务在一条执行线上轮流跑，等定时器、等通道、等彼此，与JavaScript事件循环解决的问题相同，只是写法是阻塞式直书：

| 单线程异步（JavaScript）写法 | NLang对应写法 |
|---|---|
| 事件循环 | 调度器运行队列（默认单载体） |
| `setTimeout(f, 100)` | `thread.spawn(f)` + `thread.sleep(100)` |
| `await promise` / `Promise.all` | `f.get()` / `thread.join(t)` |
| 回调嵌套 | 直接顺序书写 |

因此NLang没有也不需要`await`关键字：函数不做异步着色，没有状态机变换；`f.get()`就是诚实的阻塞式等待——挂起当前虚拟线程，完成值就绪后原地续行。要到多个载体上真并行（纯计算段与对象字段访问直接重叠，容器、字符串、流、同步原语各持各的锁，每类数据一把），用`SetCarrierThreadCount(n)`显式选入（见[载体与并行](carriers.md)）。

### 选型导引

*资料性：*从你要做的事出发，而不是从工具清单出发。安装包自带的`examples/conc_*.n`把下表每一行都走了一遍：

| 你想… | 用 |
|---|---|
| 启动一个后台任务 | `thread.spawn(f)` |
| 取回任务的返回值 | 派生带返回值的函数 → `Future<T>` → `get()` |
| 手工构造并完成一个`Future` | `Promise<T>`（`future()`分发，`complete`先完成者获胜） |
| 等任意一个先就绪 | `Future.selectAny(futures)`（返回获胜下标） |
| 在任务之间传值 | `Channel<T>`（send/recv/close） |
| 保护共享可变状态 | `Mutex`（lock/unlock/tryLock） |
| 方法组合或递归体内加锁 | `ReentrantMutex`（可重入，见[ReentrantMutex](../../language-spec/concurrency-reentrant-mutex.md)） |
| 单值计数器/标志位的原子更新 | `AtomicInt`（load/store/compareExchange，见[AtomicInt](../../language-spec/concurrency-atomic.md)） |
| 限制同时进入某段代码的任务数 | `Semaphore(n)` |
| 等一批任务全部完成 | `WaitGroup`（add/done/wait）或逐个`join` |
| 一次性唤醒一组等待者 | `Channel.close()`广播 |
