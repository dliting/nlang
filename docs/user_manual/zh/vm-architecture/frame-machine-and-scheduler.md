# 帧机与调度器

虚拟机的解释器是**帧栈机**：NLang函数调用不再依赖C++递归，而是显式的调用帧栈，由一个迭代循环分派操作码。这一改造是并发能力的地基——要挂起一个执行中的上下文，必须把它的整条调用栈冻结成数据；递归解释器把调用栈活埋在C++栈里，做不到这一点。

## 帧机

每次NLang函数调用压入一个调用帧，`OP_Return`弹出并写回结果；解释循环反复分派栈顶帧的指令，NLang调用深度不再消耗C++栈。函数嵌套深度上限（1000层）语义不变，改为帧计数。两个有界的例外仍是C++递归：`toString`求值的嵌套运行（上限64层）与嵌入宿主的`call()`入口（不可再嵌套）。

调用帧记录（见[栈帧布局](stack-frame-layout.md)）携带：

- 局部变量缓冲区与接收者、参数槽；
- 返回目的地（调用方槽偏移，或宿主提供的外部单元）；
- 恢复点（`pc`）与源码行号；
- 异常处理器状态（当前活跃的`catch`处理器栈）——它属于帧，因此跨停泊自然保留。

## 挂起机制

停泊不引入新操作码。线程内在函数需要让出时抛出一个虚拟机私有的挂起信号（一种不走NLang异常路径的C++异常），解释循环外层捕获它，帧栈原样保留、整体移入该上下文的停泊记录。恢复就是把帧栈搬回调用栈、从各帧记录的恢复点继续执行——局部变量、处理器状态、指令位置都与停泊时一字不差。

内在函数的实现遵循「完成或挂起」规约：要么把本次操作完整做完，要么在做出任何可观察变更之前挂起；不存在做了一半的停泊。

抢占复用同一机制：指令回边计数达到配额（常量`DEFAULT_SCHEDULER_TRIP_BACKEDGES`）且另有可运行上下文时，抛出抢占信号，载体把当前上下文重新排到运行队列尾。**单上下文程序因此逐位不变**——没有其他上下文时配额永不触发。

嵌套求值窗口（`toString`求值、嵌入宿主`call()`）里不允许停泊：挂起请求被转换为可捕获的运行期错误，先于一切既有兜底处理。这保证了窗口的调用约定（调用即返回值）不被破坏。

## 调度器

调度器维护每个上下文的记录：标识符、状态（可运行、停泊于定时器/join/互斥体/通道接收、已完成、已失败）、停泊帧栈、`Thread`对象与失败异常的堆引用、唤醒时刻、以及完成结果值。

- **运行队列**：先进先出。载体循环反复取出队首上下文执行，直到它返回、停泊或被抢占。
- **定时器表**：`thread.sleep`的停泊按唤醒时刻排序；专用定时器线程（首次睡眠时启动）把到期的睡眠者放回运行队列，全部载体停泊或阻塞在原生调用中时截止时刻同样生效。
- **上下文生命周期**：`thread.spawn`在派生时即铸好目标上下文的根帧（委托的接收者入帧槽0），因此垃圾回收的精确根集从上下文诞生起就覆盖它。上下文完成时唤醒全部等待者；未捕获异常则标记失败并保留异常对象，等待`join`重抛——失败不外泄到宿主。
- **退出策略**：main上下文返回即整个运行结束，其余上下文静默丢弃。队列排空而main仍未完成时，虚拟机报告死锁而不是空转。

## 与垃圾回收的衔接

停泊上下文的帧栈是根集的一部分：参数与返回值槽经声明表扫描，其余帧槽（含求值暂存区）经每函数的句柄位图扫描。机制与动机详见[垃圾回收设计](garbage-collection-design.md)。

## 调试器边界

调试钩子（语句级回调、断点、异常触发）**只为main上下文触发**：派生上下文的执行静默通过钩子。调试视图（调用栈、局部变量查看）也只反映当前停在调试会话中的上下文。这是K1的已知边界——多上下文调试属后续阶段（见[已知限制](../language-spec/known-limitations.md)）。
