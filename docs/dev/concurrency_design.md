# 并发能力总体设计（统一帧栈基底）

- **文档定位**：并发能力（多线程虚拟线程 + 协程）的立项级架构规格与分期路线。
  首个内核增量 K1 的实施计划以本文件为权威依据。
- **输入**：用户独立完成的并发技术调研（虚拟线程/协程主流模型、抢占机制、
  调度架构、双模型共存、CPU 亲和性；调研原件存本地 dev 树未入库，结论已
  消化进本文的对照表）。本设计**参考而非照搬**该调研。
- **裁定原则**：用户指示——不迁就现状结构、不做向下兼容，选达成目标最
  合适、最优雅的方案；从用户与架构师双视角解决本质问题。
- **状态**：K1–K8已交付（0.10.0–0.10.22，实录见第四节）；百万并发性能线K9–K11立项（2026-10-27，见第九节）。

## 一、目标形态

同步阻塞风格的轻量虚拟线程，共享对象、FIFO确定性调度；函数不做异步着色，
`Future.get()`/`thread.join`的阻塞式等待就是全部等待形态（`await`关键字
已裁定不需要，0.10.3落地）。嵌入式宿主零新增线程负担（K1阶段运行仍完全
发生在进入`Execute`的线程上）。

## 二、架构裁定：统一帧栈基底，否定纤程

解释器从「递归 C++ 栈」改造为「显式帧栈机」：每个执行上下文拥有自己的
帧栈（堆上 `CallFrame` 序列），解释循环 `RunFrames()` 迭代分派，调用压
帧、返回弹帧，**NLang 调用不再消耗 C++ 栈**。虚拟线程 = 一个帧栈上下文 +
抢占式调度策略；协程形态由阻塞调用（`Future.get()`/`thread.join`等）的
自然挂起承担，无需独立机制、无需函数染色。
**机制层一套**；语法面最终裁定无需`await`关键字——阻塞式等待即等价物
（0.10.3落地，用户手册并发模型页同款表述）。

否定纤程（fiber，Windows Fiber/ucontext 栈切换）的三条理由：

1. **规模**：纤程栈创建时定长连续，百万级任务内存不可行（1M × 64KB =
   64GB）；帧栈上下文挂起仅保存活跃帧（帧内均为 8 字节槽，NLang 无栈上
   数组），与 stackless 状态机同数量级。
2. **双系统**：纤程路线必须并行维护「栈切换虚拟线程」与「编译期状态机
   协程」两套挂起系统，调研文档中 P1 级的双模型隔离规则、两套同步原语、
   跨模型锁死锁（评级中高风险）全部由此而生；帧栈路线一套机制消解全部。
3. **平台黑话**：挂起纤程无法可移植回溯（调试）、无法从外部取消（必须
   恢复到其上才能 unwind C++ RAII）、切换遇 C++ 异常在飞为未定义行为。

成熟先例：Lua 协程（每协程一个 `lua_State`，堆上 CallInfo 栈，协程近乎
免费）、Erlang BEAM（每进程堆栈）。两者均为小型虚拟机工业一致答案。

**内存表述纪律**：帧栈挂起保存整帧 `localsSize`（含已死局部变量），非
「仅跨挂起点活跃变量」；与 stackless 的差距靠「帧小」收敛，不宣称等价。

## 三、K1 范围（首个内核增量，v0.10.0）

**做**：帧栈化改造（语义保持，语言层零变化）→ 挂起原语 → 单载体调度器
（零 OS 线程、零新增同步原语，空闲 `sleep_until` 最近定时）→ `thread`
内建命名空间（`spawn`/`join`/`yield`/`sleep`/`id`）+ `Mutex`/`Channel`
内建类 → GC 跨挂起根集。

**不做（K1 非目标）**：OS 线程与 GIL（K2）；`await`/`Future`/有返回值
spawn/有界通道（K3）；上下文级 RNG、非阻塞 stdin、spawned 上下文调试
（K1 已知限制）；文法与字节码格式改动（`thread.xxx` 走既有命名空间限定
调用，`OP_CallIntrinsic` 复用字符串方法发射模式，`NCU_FORMAT_MINOR`
不变）。

关键决策（两轮对抗性审查后定稿）：

| # | 决策 | 要点 |
| --- | --- | --- |
| 1 | 帧机表示 | `CallFrame{localsBuf(每帧自有 vector，push 时定尺寸→data() 移动稳定), pResult+resultDstOff, pc, handlerExcStack}`；`RECURSE_LIMIT` 语义/报错不变，改帧计数上限 |
| 2 | 挂起 = 无新操作码 | `ParkSignal`（不继承 `std::exception`）由线程内在函数抛出、循环层捕获、帧原样保留；内在函数须「完成或挂起」二态；`catch(...)` 全库审计前置；toString 嵌套/嵌入 `CallByName` 内挂起 → 可捕获基础异常拒绝 |
| 3 | 抢占复用挂起 | 回边安全点旁查配额（`DEFAULT_SCHEDULER_TRIP_BACKEDGES`），仅当另有 Runnable 上下文时抢占 → 单上下文程序逐位不变；FIFO+配额=确定性调度 |
| 4 | GC 根集 = 精确 + 保守带 | 非运行上下文每帧精确扫 `func->locals`+`pResult`，再对 `[paramCount×8, localsSize)` 带做保守值测试（字符串/堆双域守卫，只过标不漏标）；运行上下文安全点同样带扫描（即第六节存量 GC 漏标缺陷的修复）；编译期精确位图留作 K2 优化 |
| 5 | 语言面 | `thread` 为保留命名空间（无需 import、用户包名 `thread` 编译期拒绝）；spawn 限零参 `func<void>`（状态用绑定方法句柄 `obj.method` 传递）；join 多 joiner 皆唤醒、Failed 时向 joiner 重抛原异常对象；Channel 无界缓冲、send 永不挂起、close 后空 recv 返 null、send 抛；Mutex FIFO、不可重入、unlock 未持有抛基础异常 |
| 6 | 主退出策略 | main 返回即结束，挂起上下文静默丢弃（隐式 join-all 会让一个睡眠者挂死所有脚本退出；Go 同款语义） |
| 7 | 调试器边界 | `IDebugHooks` 只为 main 上下文触发，`IVmDebugView` 仅当前上下文（否则 main 停在 join 时调试会话收到错误上下文的回调）；完整多上下文调试 K4 |

## 五、对调研文档的采纳与偏离

| 调研结论 | 处置 |
| --- | --- |
| 字节码安全点抢占优于信号抢占 | **采纳**（回边安全点旁查配额） |
| GMP 三层架构 + 工作窃取 | **延后裁剪**：K1 单载体、K2 GIL 多载体，工作窃取/亲和为 K4；GMP 的 P/M 分离是「多载体阻塞卸载」问题，进入 K2 时再评估 |
| stackless 编译期状态机协程 | **偏离（最大项）**：帧栈基底使「协程」退化为调度策略，编译器状态机改写、表达式临时值跨 await、finally 双拷贝等全部难点消失；`await` 保留为语法标记（K3，后续裁定不需要，见第四节K3行） |
| 双模型语法层隔离 + Future 桥 + 两套同步原语 | **不再需要**：一套机制一套原语；Future 在 K3 作为取值便捷面保留，非隔离桥 |
| 阶段一 GIL + 多 OS 载体先行 | **重切**：GIL 的前提是多线程共享堆，现状每执行器独立堆且零同步原语；先在单载体零数据竞争环境把「挂起 + 根集」做对（K1），OS 并行第二刀（K2） |
| 阶段二 M:N 抢占式虚拟线程 | **采纳**为 K1+K2 合并终点 |
| 百万级并发/创建开销 ≤10μs | **目标降档后于2026-10-27恢复立项**：K9–K11以三片增量消除定时器/创建路径/回收三项规模化瓶颈，验收与门位置见第九节（百万停泊挂得住 + 创建≤10μs + 定时器O(log n) + GC摊还成本基线化） |
| FFI 不可完美抢占（行业共性） | **采纳**：K1 native/嵌入调用运行期拒绝挂起；阻塞钉住载体为已知限制 |

## 六、存量 GC 漏标缺陷（本设计派生发现）

`f(g(), h())` 形调用中，`g` 的结果对象在实参装配期**仅**存活于调用帧
evalArea 暂存槽（`EmitCallArgs` 全实参就绪后才拷贝 `callParamBase`），
而 `MarkPhase` 只扫 `func->locals` 声明表——`h` 的入口/回边安全点可触发
回收，产生阈值依赖的悬垂堆句柄。**独立于并发工作即应修复**；K1 以保守
带扫描顺带修复，修复前先写 RED 复现（不可复现则降级为仅停泊上下文带扫
描），CHANGELOG 记缺陷修复行。

## 七、对抗性审查记录（两轮）

- **第一轮（攻架构裁定与三个实证修正）**：裁定维持，两处表述收窄（帧
  内存「同数量级」非「等价」；统一为机制层，`await` 语法面仍 K3）。三
  个实证修正全部采纳：「挂起无需新操作码」（附加挂起原子性/`catch(...)`
  审计/恢复点三条实现规约）、「保守带替代编译期位图」（逐挂起点位图无
  法覆盖下层帧活跃暂存区，帧级带扫描可以；健全性=只过标）、「存量漏标
  缺陷加先决复现门」。
- **第二轮（攻计划完备性）**：调用方全集 grep 钉死（`ExecuteFunction`
  10 处 + 委托引擎，无调试器求值入口）；补调试器钩子 main-上下文过滤
  （决策 7）；回溯等价性论证补全（`m_unwindFrames` catch 即清 → 钉死测
  试覆盖未捕获路径 + `Exception.backtrace` 字段两形态）；spawn 根帧即
  构造消除 rooting 空窗；补非目标清单/确定性测试规约/验收示例。

## 九、百万并发性能线（K9–K11，2026-10-27立项）

第五节的"百万级降档"是K1/K2时期的过渡裁定；并发机制的结构正确性此后已由
0.10.0–0.10.22兑付（帧栈基底、GIL多载体、精确根集、原生同步句柄家族），
剩余的是三条已被代码检视与9.2调研钉死的规模化瓶颈：

1. **定时器线性表**：`VmSchedulerTimer`以`std::vector`存定时器，服务与
   最近到期查询均为O(n)全表扫描——百万停泊者下每次唤醒决策都全表扫。
2. **创建路径逐帧堆分配**：每帧自有`localsBuf` vector，spawn成本随上量
   退化为分配器压力（对象分配已有每载体免锁空闲链表，帧缓冲是缺失一环）。
3. **回收全注册表扫描**：每轮回收扫全部上下文注册表，成本与上下文总数
   线性相关，停泊型负载无法摊薄。

本线以三片增量逐个消除，恢复"百万级并发 + 创建开销≤10μs"的原始设想为
可验收目标。

### 9.1 验收（B档水位）

**挂得住**：100万停泊上下文（sleep停泊为主、通道停泊为辅）完整跑完、
退出码0、无崩溃无挂死；稳态内存实测入档，预算值在K9基线后钉死（按每
上下文约1KB级估算，预估0.5–1.5GB）。

**开销门三项**（绝对数字以本地基准为准，登记进9.6基线表）：

1. **创建≤10μs**：C++测试宿主内预热后连续spawn（至进入可运行队列为止）
   取中位数，基准脚本报p50/p99。
2. **定时器操作O(log n)**：1万/10万/100万定时器阶梯的服务总成本按
   n·log n比例校验，不做绝对墙钟断言。
3. **GC摊还成本量化**：100万停泊下单次回收成本与触发频率，记录为回归
   基线。

**门的位置**：绝对数字由`tools/`本地基准脚本产出并标注机型与日期；
ctest挂缩比性能哨兵（阈值10倍余量，拦截数量级退化）与万级挂起正确性
（含gc-stress变体）。百万级形态只进本地基准，不进ctest（3分钟超时上限
与机器差异决定）。

### 9.2 调研结论与出处（2026-10-27联网调研）

| 结论 | 出处 |
| --- | --- |
| Go运行时定时器为每-P四叉最小堆（`timerHeapN=4`），插入/删除/到期O(log n)、最近到期O(1)原子免锁查询；停止定时器僵尸标记惰性删除，僵尸超表长1/4强制整理；早期单全局堆曾是瓶颈 | [golang/go `src/runtime/time.go`](https://github.com/golang/go/blob/master/src/runtime/time.go) |
| Java虚拟线程栈块是普通堆对象，GC作为堆对象图遍历而非独立根集；JEP示范百万虚拟线程（吞吐约百万任务/秒）；调度器明确不做时间片抢占——"百万级下时间共享是否仍有效并不清楚"；海量任务下每任务固定开销须锱铢必较（削减初始缓冲与thread-local使用） | [JEP 444](https://openjdk.org/jeps/444) |
| BEAM进程创建即约327字（含233字初始堆），默认进程上限32768、可调至2.68亿；定时器内置于VM（`send_after`直走ERTS，远快于进程形态的`timer`模块）；每进程独立小堆使回收成本与全局规模解耦——NLang共享堆不照搬，作评估参照 | Erlang/OTP Efficiency Guide（erlang.org/doc/efficiency_guide） |
| 海量定时器高换手场景时间轮O(1)占优，最小堆O(log n)更简单且足够；Akka/Flink/Tokio均按此选型 | Varghese & Lauck, *Hashed and Hierarchical Timing Wheels*（SOSP 1987，Linux内核时间轮来源） |

### 9.3 K9：定时器堆化 + 规模基准设施（0.10.23）

**做**：

1. 基准设施先行：`tools/`规模基准脚本（1万/10万/100万阶梯），度量创建
   耗时、单次回收成本、定时器服务成本、稳态内存；**对改造前现状采集
   基线**登记进9.6。
2. 定时器表`std::vector`线性扫描 → 全局四叉最小堆：键`(wakeAt,入队序号)`，
   相同时刻到期按入队序唤醒（保持FIFO确定性）；`NearestWakeAt`变O(1)
   堆顶窥视；取消的定时器惰性标记，僵尸占比超1/4整理（Go同款规则）。

**不做**：每载体定时器堆（Go拆per-P为免锁竞争，NLang定时器操作本在全局
锁下，单堆即可）；时间轮（堆更简单且足够，见9.2）。

**验收**：基线表建立；定时器服务成本在阶梯上呈O(log n)比例；既有定时器
语义（确定性唤醒序、饥饿修复）回归全绿；缩比哨兵与万级挂起正确性入ctest。

### 9.4 K10：创建路径与停泊内存（0.10.24）

**做**：

1. 帧槽缓冲池化：`CallFrame::localsBuf`每帧`std::vector`分配改走每载体
   空闲链表模式（0.10.16已立的对象分配纪律，帧缓冲是缺失一环）。
2. 停泊内存分解测量（上下文对象/注册表节点/帧缓冲/运行队列节点），
   紧凑化手段按数字定，不预设。

**不做**：跨载体帧池（沿用每载体纪律）；停泊帧死局部收缩（收益限于栈顶
帧未用后缀，与"内存表述纪律"冲突面大，除非测量证明必要）。

**验收**：创建≤10μs门（p50）；百万上下文稳态内存入预算（预算值依K9
基线钉死）；对照9.6基线回报创建路径收益。

### 9.5 K11：GC定向优化（0.10.25，数字裁决）

本片承诺：依据9.6基线落地一项定向优化**或**记录"当前成本可接受"结论
收线，二者皆合法验收；具体方案过设计门 + 对抗性审查后才动手。

**对抗性审查级约束（先记入，防方案走偏）**："上次回收后未运行的停泊上下文
跳过扫描"对标记-清除不健全——停泊帧持有堆引用，任何一轮回收跳过这些帧，
被引用对象即被误回收成悬垂引用。要让"跳过"成立必须分代化：停泊帧视为老
年代，以记忆集记录其指向的新生对象，帧槽写入加屏障记录新引用（JDK对虚拟
线程栈块同款处理）。领先候选即此；K9数字若显示停泊型负载分配稀疏、摊还
成本可接受，则无改动亦合法。

**正确性验证**：gc-stress变体与无旗标自然回收形态双跑（沿用gc-stress压窗
纪律）；有改动时对照9.6基线回报单次回收成本收益。
