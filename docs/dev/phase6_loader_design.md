# Phase 6 运行期包加载与链接设计（nlink）

状态：设计稿 v1（2026-10-01），细化 `docs/dev/phases_567_design.md` §2 阶段 6 的
第 1–4 项（逐单元产码、未解析引用表、`.npkg` 归档、链接器）。
用户裁定（2026-10-01）：第三方独立扩展是硬需求；热加载是未来可能项；不做向下兼容；
易用性与可扩展性并重。因此链接发生在**运行期**（nvm 包加载器），构建期只做类型检查
与打包——本设计取代 `phases_567_design.md` §2 中「链接器在 ncc 打包步骤内」的旧表述。

## 1. 总体架构

三个组件、一条链接链：

| 组件 | 职责 |
| --- | --- |
| ncc（编译＋打包） | 对着第三方包的**签名表**做类型检查（签名来自搜索路径上 `.npkg` 的成员表，等价 javac 对 jar 编译）；产出携带**符号引用表**的 `.ncu`；把本项目各模块打包成程序 `.npkg` |
| `.npkg`（包归档） | 头部（包名、格式版本、标志位、成员数；程序包多一条入口点记录）＋成员表（模块路径 → 偏移/长度/校验和）＋若干 `.ncu` 成员 |
| nvm（运行期） | **包加载器**：定位并加载闭包内全部 `.npkg`；**链接器**：闭包加载完成后统一解析全部符号引用，回填各模块解析表；**执行器**：跨模块访问经解析表间接寻址 |

核心原则：自研模块与第三方包走**同一条加载路径**（Java 模型：应用与库都经类加载器）。
程序 `.npkg` 不内嵌第三方代码；第三方以独立 `.npkg` 形态存在于包搜索路径上，
可独立升级，并在未来支持热加载（重载包＋失效解析表槽位；远期可参考 Erlang
双版本代码服务器的形态）。

## 2. `.ncu` 格式 v2.0（不向下兼容）

- 模块头：模块点分路径、格式版本 2.0；**无入口点**（入口记录在 `.npkg` 头部）。
- 模块局部表：函数、类型（class/struct/enum/interface）、字符串常量，各自模块内
  下标从 0 起。
- **符号引用表**（新）：每条跨模块引用一个记录，字节码操作数改为引用记录下标：
  - 函数调用：`(类别=函数, 目标包路径, 名字, 形参数)`——形参数是粗指纹，
    与既有导入桩规则一致；精确签名冲突由编译期签名表检查拦截。
  - 类型引用：`(类别=类型, 目标包路径, 类型名)`——供 `.ncu` 内类型描述符的
    类型槽位定址。
  - 字段访问：`(类别=字段, 类型槽位, 字段名)`——**按名字记录、链接时定址为
    目标布局偏移**；库重排字段不要求重编消费方（签名兼容即可）。
- 模块内部引用：直接局部下标，热路径零间接。
- 不进入符号引用表的部分：字符串常量是值（模块内驻留）；方法调用按裸方法名经
  接收者派发（现状不变）；流类型名字面量在编译期定身（阶段 5 语义保留）。

## 3. `.npkg` 格式 v1.0（新格式）

- 头部：包名、格式版本 1.0、标志位、成员数；程序包额外携带入口点记录
  （模块路径＋函数 `main`；`.nproj` 指定入口源文件，缺省 `main.n`）。
- 成员表：模块路径（点分）→ 偏移/长度/内容校验和（校验和算法随实施计划确定，
  阶段 7 的依赖记录复用同一实现）；成员按路径排序——同输入
  同字节（打包确定性）。
- 成员：`.ncu` 映像原样内嵌。
- 扩展性：未来字段（包版本、依赖清单——阶段 7 的输入）以版本号递增引入。

## 4. nvm 加载与链接流程

1. 加载程序 `.npkg`：读头部（入口点记录）与成员表。
2. **闭包加载（急切）**：沿各 `.ncu` 的导入清单，在包搜索路径上定位每个第三方
   `.npkg`，加载其成员表与成员；包可依赖包，递归进行；搜索路径顺序即优先级，
   与源码发现、native DLL 同一条链（`include/nlang/common/LibrarySearchPath.h`）。
3. **统一符号解析（急切，闭包加载完成后一轮完成）**：遍历全部模块的符号引用表，
   逐条在目标包/模块的局部表中定址，回填该模块的**解析表**槽位（解析表与符号
   引用表平行：一条记录一个槽位；类型槽＝目标 CompiledClass 下标与字段偏移；
   函数槽＝目标函数下标）；**所有未解析项一次报清**。
4. 执行入口点。

解析时机论证：两级都急切是易用性最优解——缺包、缺符号、版本不符、可见性违规
在任何用户字节码执行之前一次报清；解析表结构保留懒解析的优化空间（时机后移，
结构不变），也为热加载预留「重载包＋失效槽位」入口。循环依赖天然支持：
先全量加载、后统一解析，与阶段 5 互可见语义一致。

## 5. 与既有机制的衔接

- **native DLL**：维持现状（首次调用触发 `nlang_<库名>.dll` 加载），与字节码
  链接相互独立；「`native` 限单段包」诊断在阶段 6 解除（库身份出现后，包 → 库
  有确定映射，见 `phases_567_design.md` §2 阶段 6 第 7 条）。
- **`_package.n` 可见性**：双重执行——ncc 编译消费方时只对导出面做类型检查；
  nvm 加载时校验被引用符号确属导出面（表查询，纵深防御）。
- **确定性**：`.ncu` 字节保持确定；`.npkg` 因成员排序而确定——
  `check_ncu_determinism.py` 扩展出 `.npkg` 字节复现检查。
- **stdlib**：维持源码形态（消费方构建期内联），不制作运行期 stdlib 包（范围裁剪）。

## 6. 错误处理（全部发生在任何用户字节码执行之前）

| 错误 | 诊断（全部一次报清，不只报首条） |
| --- | --- |
| 缺包 | `Package 'vendor.graphics' not found on the package search path; searched: <列表>` |
| 格式版本不符 | 指名包与两方版本号（`.npkg` 与 `.ncu` 各自校验） |
| 符号未解析 | 指名包、模块、符号＋引用方模块 |
| 可见性违规 | 指名引用方与被引用的非导出符号 |
| 入口点缺失 | 程序包无入口点记录或记录的函数不存在 |

## 7. 易用性

- 一条命令两种形态：`ncc build -p proj` → `obj/*.ncu` ＋ `outputDir/proj.npkg`；
  `ncc run proj.npkg`。库与程序同命令，程序多入口点记录。
- nide：运行/调试 `.npkg`；包搜索路径沿用项目设置（Tools → Options ＋
  Project → Properties 的既有层）。
- 加载/链接诊断在任何用户字节码执行之前完成，一次报清。

## 8. 测试

- 加载器：闭包加载、搜索路径次序、缺包/缺符号/版本不符/可见性违规的诊断
  全量报清（子进程门，参照阶段 1 的 UB 实测教训）。
- 打包确定性：同输入 → 同 `.npkg` 字节。
- 端到端关键能力：第三方包以 `.npkg` 形态（**无源码在场**）被消费方编译
  （签名表）与运行（运行期链接）——本设计的存在理由，必须有专项。
- 解析表槽位回填语义的单元测试（热加载的使能结构）。
- 既有 e2e 全量保持绿（977/6 基线）。

## 9. 版本号

- `.ncu` 格式 **2.0**：符号引用表、无入口点，语义变更不向下兼容。
- `.npkg` 格式 **1.0**：新格式。
- 加载器对 `.ncu` 2.0 / `.npkg` 1.0 之外的版本一律拒绝并指名两方版本号。
