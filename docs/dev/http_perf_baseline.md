# HTTP性能对拍基线（2026-11-12）

本文是`stdlib/http.n`的服务器与四个主流HTTP服务器在同等配置下对拍结果的入库快照。
这份快照在v0.13.6网络与HTTP性能优化落地之后刷新：2026-11-10那份快照暴露的「每请求约15 ms
固定延迟」已定位为VM网络等待路径的量子并被修掉（修法即设计文档裁定D1，提交`2053fb5b`），
第5节保留完整的排查与处置记录，并附本轮落地后的复测对照。对拍设施本身在`tools/http_perf/`，
随时可以重跑刷新数据（配方见第6节）；本文的数据不会随代码自动更新，引用时以文中记录的实测环境为准。

## 1 结论摘要

- **1连接下差距仍大，但不再是两个数量级**：1连接、0字节响应，NLang 1686 RPS（每秒请求数），参考实现从
  4478（nginx）到13684（Rust）RPS，相差2.7到8.1倍；P50延迟0.56 ms对0.07到0.21 ms。2026-11-10快照的同格
  是64 RPS、对参考侧71到229倍、P50 15.51 ms：那个15 ms的固定量子随D1修复消失，没有回来（第5节限流扫描
  复测）。
- **高并发下与本轮nginx同量级，比编译型运行时仍差一到两个数量级**：128连接、0字节响应，NLang 4865 RPS，
  nginx 4919（NLang为其0.99倍）、Node 14891（0.33倍）、Go 69308（约1/14）、Rust 73592（约1/15）。
  nginx这一格用的是出厂默认的文件缓存设置，给同一探针补上`open_file_cache`文件句柄缓存就能把它抬到4万RPS
  量级（第4条，这项A/B只测到32连接），所以0.99倍只说明「与本机可复现的nginx参考水位同量级」，不说明与调过的
  nginx同级。
- **吞吐上限从等待量子移到了每请求服务率**：全局限流下吞吐不再钉死在约315 RPS——不限流实测5209.9 RPS，
  是修前的15.8倍；限流扫描8档的P50全部落在0.68到0.92 ms、跟着限流值走，15 ms台阶在任何一档都不出现。
  高并发行的P50（6.47到36.46 ms）现在随连接数增长的排队，与Node 128连接行7.87 ms同形，不再是与负载无关的
  固定台阶。
- **大body下追平甚至反超nginx**：8 KiB行4连接NLang 4869 RPS，为nginx 4227的1.15倍；128连接8 KiB行4896，
  为nginx 4607的1.06倍。而NLang自己的0 B、1 KiB、8 KiB吞吐平台都停在约4.9k RPS——挡住的是每请求服务率，
  不是body搬运本身（第6条把1 KiB格的下降登记为待裁定）。
- **短连接仍落后**：同是32连接、0字节、关长连接，NLang 2106对nginx 2801（0.75倍）、Node 3446（0.61倍）、
  Go 4890（0.43倍）、Rust 4726（0.45倍）；开长连接时对Go／Rust的差距重新拉大（0.08倍）。修前是短连接把差距
  压小（2488对nginx 2467，1.01倍），因为量子把开长连接的NLang也钉在原地；D1之后长连接的服务能力恢复了
  （2501→4807），差距的形状回到「服务能力决定」。
- `http.n`两处每响应的次要成本（分两次写、每次响应重新格式化`Date`头）本版已清偿（D3 `7c2c9376`、
  D4 `9b8e19e2`，第5节末）；剩余的脚本侧成本（逐头装配响应头、正文的第二次拷贝）按设计文档D9列为
  第0级候补，尚未动手（第5节末）。

## 2 对拍方法

**设施**：`tools/http_perf/`。`run_baseline.sh`编译并启动五个服务器、按阶梯跑两轮、把每次测量的原始JSON
落到输出目录；`parse_results.py`把原始JSON汇总成第3节的表；`*.in`是各服务器源码与配置模板，
`srv_rust/`是Rust探针的cargo工程（`Cargo.lock`钉住依赖包crate的版本，`rust-toolchain.toml`钉工具链1.99.1）。

**压测端**：oha 1.16.0（独立进程，与被测方无语言耦合）。固定4个生成线程（`--worker-threads 4`），
每请求超时10 s（`-t`），两边都关闭压缩（`--disable-compression`），每行先3 s预热再测15 s。

**五个服务器的配置**——「同等配置」的具体含义：

| 服务器 | 版本 | 实现形态 | 并行度 | 空闲连接 |
| --- | --- | --- | --- | --- |
| NLang http.n | git `2026891d` | 纯NLang脚本（`stdlib/http.n`，无native模块、无DLL），每连接一个虚拟上下文 | 载体4（另设1载体敏感度行） | 30 s |
| Node http | v25.3.0 | 内置`http`模块 | libuv单线程 | 30 s（`keepAliveTimeout`），`headersTimeout` 60 s |
| nginx静态 | 1.31.8 | 静态文件服务（`root`直接回同一body） | 1个worker，`worker_connections 4096` | 30 s；`keepalive_requests`抬到100000000 |
| Go net/http | go1.27.3 | 标准库`net/http` | 每连接一个goroutine，运行时按逻辑核调度 | 与其余探针一致 |
| Rust axum/tokio | 工具链1.99.1 | axum＋hyper＋tokio（主流crate组合，即Rust榜单条目的搭法） | tokio每逻辑核一个worker | 无空闲超时（hyper默认，本轮跑不满故不显现） |

五个探针提供同一组路径（`/b0`、`/b1024`、`/b8192`）与同一组长度的body，响应一律带`Content-Length`而
不靠关闭连接定界（Go／Node／Rust探针显式写这个头，NLang的`http.n`与nginx静态模块按body长度自动写，
前者见`stdlib/http.n:1165`），都只绑127.0.0.1（18081到18085），响应体的构造都在测量窗口之外完成
（NLang探针在首个请求即预热窗口内建好缓冲区，其余探针用预分配的常量：Go在包初始化时`bytes.Repeat`、
Node在模块加载时`Buffer.alloc`、Rust是`&'static`常量切片）。

**负载阶梯**：`full`＝每个服务器标签每趟11行——0 B与1 KiB在1／4／32／128连接下各一行（8行）、8 KiB只在
4与128连接各一行（2行）、再加一行关闭长连接的0 B 32连接；`small`＝4行（0 B与1 KiB在4与32连接）；
`quick`＝3行。敏感度标签不跑完整阶梯：NLang 1载体自动降为`small`那4行（4与32连接正是载体数起作用的地方），
nginx sendfile on只跑0 B 32连接一行。每趟共60个测量点，两趟共120次测量。

**降噪协议**：两趟反序（趟1按nlang→node→nginx→go→rust，趟2倒过来），两个敏感度标签在两趟里都排在队尾、
不参与反序；表里「两趟散布」列给出同一行两趟结果的相对差；每行开跑前用WMI读机器负载，超过25 %就等5 s重试，最多20次。

**oha的收尾语义**：每个测量点每趟的JSON里，`errorDistribution`的`aborted due to deadline`条数都不超过
该行的连接数——通常恰好等于，连接在收尾时已经空闲的行会少几条（本次120个JSON里83个恰好等于、37个更少、
没有一个更多），而`successRate`全是1.0。这是oha在`-z`时长到点时掐掉在途请求的正常行为，不是请求失败；
汇总脚本在三种情况下报警：开跑前负载超限（`contended`）、任一趟`successRate`不足1.0、或中止数超过
「连接数×趟数」；本次120行的`contended`全是0、`successRate`全是1.0、中止数没有一条超过上限，一条都没触发。

## 4 公平性说明

1. **nginx列不代表Linux上的nginx**。本轮只跑1个worker（`worker_processes 1`）：这是五个服务器里最低的
   并行度之一（Node同样是单线程事件循环，Go与Rust每逻辑核一个worker，NLang 4个载体线程）。只跑1个worker是为了
   让五个服务器都只占一个执行流，不代表Windows上nginx通常就这么跑。发送路径方面，同一body下`sendfile on`只比
   `off`高3.4 %，落在这一格自己的两趟散布之内（第3节的nginxsf行，一个格子的趋势；上一轮同一A/B高1.4 %，当时
   两边散布都不到0.5 %，两轮之间方向都不一致），据此推断Windows nginx没有拿到Linux上那条高性能发送路径，
   但两轮都没有直接证据。因此NLang在128连接上对
   nginx那0.99倍是在自己多线程、nginx单线程的条件下拿到的。把它当作「同机可复现的参考水位」读，
   不当作nginx的水位读。第4条还记录了本轮nginx用的是出厂默认的文件缓存设置，那一项对静态文件路径的影响
   比上面这两点更大。
2. **Rust标准库没有HTTP服务器**，Rust列读作「用这套主流crate搭出来的服务能拿到什么」，不是「Rust语言的属性」。
3. **实现类别不同**：NLang服务器是纯脚本实现的HTTP/1.1，参考实现分别是C（nginx）、V8上的JavaScript（Node）、
   Go运行时、编译产物的Rust。脚本要跨一层VM与GC，这个差距本身不是NLang的协议实现质量问题。
4. **nginx用静态文件对拍动态handler**：省掉了handler成本，也受Windows文件与发送栈限制；已在配置里把出厂的
   `keepalive_requests 1000`抬到极大，否则测的是nginx的主动断连重连churn，而不是它的服务能力。响应头也不等价：
   长连接下一个0字节200响应在网线上的状态行加响应头，nginx是249字节、8个响应头字段，NLang的`http.n`是75字节、
   2个字段（`Content-Length`与`Date`）——nginx每响应多写174字节，多带`Server`、`Content-Type`、`Last-Modified`、
   `Connection`、`ETag`、`Accept-Ranges`，这一项让nginx一侧的每请求成本略高。静态文件路径本身则让nginx吃了亏：
   nginx出厂默认不缓存文件句柄（`open_file_cache`默认off），本轮配置也没写它；同一探针补上该缓存之后，
   同一0字节路径的RPS在1连接是4413对14217（3.2倍）、4连接是5409对35812（6.6倍）、32连接是5468对41447（7.6倍），
   32连接的P50从5.66 ms降到0.72 ms。补的是`open_file_cache max=20000 inactive=60s`加三条配套指令，其中
   `open_file_cache_valid 60s`与`open_file_cache_min_uses 1`本身就是官方文档的默认值，只有
   `open_file_cache_errors on`改了默认值（默认off），而它管的是缓存404这类错误结果，对全是200的这条路径不起作用。
   增益在1连接就已经出现，说明它是每请求打开文件的成本，不是排队效应；两种配置的响应全部是200，也不是靠缓存
   304或404换来的。该探针off侧的中位数4413／5409／5468是2026-11-10那轮测的（本轮未重跑），与本轮主表nginx
   同格的4478／5316／5050最大相差7.7 %（32连接那一格，本格自己的两趟散布就有11.4 %；1连接那一格只差1.5 %），
   可见它测的是同一件事，但绝对值不能跨轮混读。于是nginx列要读作「出厂默认配置下的nginx静态水位」：这条缓存
   开关在2026-11-10那次探针里把32连接的nginx抬到41447 RPS，本轮主表NLang同格4807，相差约8.6倍（两边来自
   不同轮次，只作量级参考）；这项A/B只测到32连接，128连接那一格没有实测，所以NLang对nginx那0.99倍（128连接）
   不足以说明NLang与调过的nginx同级。复测脚本
   `tools/http_perf/probe_fairness.py`（不属于那120次测量，本轮未跑；该开关要不要并入对拍默认，见第7节）。
5. **压测端与服务器同机**（16逻辑核），生成端与被测端争CPU。每行前的负载守卫只能拦住「开跑时机器明显忙」，
   不能保证行内没有干扰。两趟反序让偏置对称，但两趟差超过10 %的有23行（上一份快照是6行）：最高51.4 %
   （nginx 1 KiB 128连接），其后46.2 %（rust 1 KiB 1连接）、41.6 %与41.2 %（rust 0 B 32与4连接）、40.1 %与
   39.4 %（nginx 1 KiB 32与1连接）；NLang自己的6行最高20.4 %（0 B 32连接关长连接行），参考侧占了17行，
   说明本轮整机漂移比上一轮更大。这与设计文档第八节风险项8「高并发行下降的归因未定」直接相关，
   本轮所有高并发行的读数都只读量级与趋势，不读小数。
6. **0字节响应不是现实流量**。真实响应有头部也有body，1 KiB与8 KiB行更接近现实；0 B行的意义是把协议开销
   与服务开销分离。修掉量子前，NLang在1／4／32／128连接下的1 KiB对0 B比值是1.00／1.06／0.97／0.96——量子
   把两边都钉在15 ms档上，测不出body成本；修完之后同一组比值变成0.56／0.64／0.67／0.70，1 KiB响应的每响应
   服务成本露了出来，比0 B低三到四成。参考侧同格：Go的比值1.03／0.97／1.06／1.00几乎不动，Node（0.97／0.79／
   0.96／0.91）与nginx（0.73／0.90／0.82／0.77）居中，rust（0.78／0.98／1.20／0.95）的散布与其46.2 %的两趟
   散布同量级。NLang的比值是各方里最低的一组，说明数据搬运进入了服务率的关键路径，与第5节E5的预算方向一致。
   一个矛盾登记在此：8 KiB行NLang 4连接4869对0 B的4863、128连接4896对4865几乎不动，而8 KiB body加响应头约
   8267字节超过合并写上限JOIN_CAP 8192（`stdlib/http.n:834`），已退化为两次写——所以8 KiB的持平不能记在
   合并写（D3）头上。这些比值都是单次读数，相关格子的两趟散布在4.9 %到17.5 %之间，一轮不足以裁定它是真实的
   拷贝成本还是整机漂移，已排入下一个任务在同一探针下裁定。
7. **输出目录里`versions.txt`记录的工具链版本有一行会误导**：`cargo: cargo 1.81.0 (2dbb1af80 2024-08-20)`是
   盒子默认工具链，括号里是cargo自己的提交号与发布日期而非rustc版本，因此这一行看不出真正参与编译的工具链。
   实际编译用的是`rust-toolchain.toml`钉住的1.99.1——在crate目录内问`cargo --version`得到的是
   `cargo 1.99.1 (5f94df478 2026-08-27)`。`run_baseline.sh`已改成在输出目录里生成的crate目录内查询（那里有
   `rust-toolchain.toml`的副本）。本轮重跑已在crate目录内直接记下`cargo 1.99.1 (5f94df478 2026-08-27)`，
   旧记录里那行误导作废，新快照的`versions.txt`可直接读。

## 5 「每请求15 ms」排查与处置全程

### 已测事实

判据实验是把请求**用全局限流稀疏化**（oha `-q`）：0字节响应、4连接、`--carriers=4`，脚本
`tools/http_perf/probe_pace_ab.sh`，每档预热2 s后测8 s（下表每档一次独立运行，与主表的15 s双趟不可直接比数；
下表读数是修复前的`8c22831d`二进制，修复后的复测见本节末「落地复测」小节）。

| 限流QPS | P50 ms | 实测RPS | 成功请求（8 s内） |
| --- | --- | --- | --- |
| 10 | 0.96 | 10.1 | 80 |
| 50 | 0.91 | 50.0 | 400 |
| 100 | 0.91 | 100.1 | 799 |
| 200 | 0.92 | 199.8 | 1598 |
| 500 | 15.16 | 314.6 | 2515 |
| 1000 | 15.20 | 309.7 | 2477 |
| 2000 | 15.16 | 315.8 | 2526 |
| 不限流 | 15.11 | 328.8 | 2631 |

三点结论。其一，请求处理路径本身约0.9 ms，没有负载时看不到15 ms。其二，饱和点在约315 RPS：限流500／1000／2000
三档与不限流的实测吞吐几乎相同（310到329 RPS），8 s窗口里成功请求也都是2477到2631条，再抬高限流值只是把
多压进来的请求留在压测端排队。其三，超过饱和点后每请求固定背上约15 ms，且与响应体大小无关
（0 B与1 KiB的P50同为15 ms量级）。

这与主表自洽：1连接64 RPS≈1000/15.6；4连接321（是4×64＝256的1.25倍）；32连接2501（是32/15.6＝2051的
1.22倍）；128连接5852（128/15.6＝8192的71 %）——单请求量子之外还有一层并行度上限，两者叠加。

本机系统时钟增量实测为156250×100 ns＝15.625 ms（`GetSystemTimeAdjustment`，探针`tools/http_perf/probe_clock_hold.ps1`；
该字段报的是系统时钟的更新间隔，与某个进程自己申请的分辨率无关，见下文「只是佐证」），比观测量15.11到15.20 ms高约3 %；
实测值也从没落到过这个刻度的整数倍上。**这只说明疑似同源，尚未证明因果。**

**E4读数（2026-11-11，机器锁内，未打补丁的二进制，标签`rawbase`）**。裸套接字探针（`tools/http_perf/probe_raw_ab.sh`，只有
`net`、没有`http.n`：接受、整缓冲扫头终止符、写回一个固定0字节响应、keep-alive）重测四个连接档：

```
rawbase_1c       rps=       64  p50=  15.60 ms  p90=  16.12 ms  p99=  16.78 ms
rawbase_4c       rps=      313  p50=  15.41 ms  p90=  16.09 ms  p99=  16.64 ms
rawbase_32c      rps=     2533  p50=  15.33 ms  p90=  16.08 ms  p99=  16.62 ms
rawbase_128c     rps=     9953  p50=  15.33 ms  p90=  16.13 ms  p99=  16.81 ms
```

15 ms量子在裸套接字地板上同样存在：这一档的P50就是`E5`成分表要减掉的地板值，`http.n`服务器同档实测P50减去它，
得到的就是脚本层与协议层的成本——这就是`E5`分解表要核对的目标。1连接行两边都是64 RPS、P50逐格吻合，脚本层成本
在低并发档不显形；128连接行裸的9953 RPS是`http.n`实测5852的1.7倍，脚本层的成本余量集中在高并发档。`E4`不含任何
`http.n`代码，因此它与`E0`的差只可能来自parking路径（该地板是修正前登记形态的产物，E2落地后已不成立；E5的减法口径见下文E2读数小节的差值说明）。

### 已排除

- **载体数／CPU并行度**：1载体257 RPS对4载体321 RPS，量子一样，只是吞吐变了。
- **运行时里的显式睡眠**：`src/`内没有`timeBeginPeriod`调用，也没有`Sleep()`或`sleep_for()`调用——搜到的
  只有名字里带`Sleep`的`thread.sleep`内建，而它本身也是经`ParkForTimer`登记的定时器等待
  （`IntrinsicsThread.cpp:373`），不是系统睡眠调用。带超时的等待只有载体退出宽限的条件变量`wait_for`
  （`VmCarrierPool.cpp:140`）与IO轮询超时，都不在每请求路径上。载体取任务用的是无超时的条件变量等待
  （`VmScheduler.cpp:118`、`:188`、`:253`），没有轮询量子。
- **IO轮询切片长度本身**：把`kIoPollSliceMs`由10改成1并重建VM（`VmSchedulerIo.cpp:24`），
  1／4／32／128四行与基线的差是+0.4 %、+0.8 %、−3.1 %、+0.6 %（64.8对64.5、324对321、2425对2501、
  5889对5853），其中三行落在各自的两趟散布内，1连接那一行差0.4 %而散布是0.2 %。一格一行，合起来仍是
  「看不出变化」。
  实验脚本`tools/http_perf/probe_slice_ab.sh`把`NVM`钉成`build-dev/src/tools/nvm/Release/nvm.exe`，重建日志
  （当时写在临时区`temp/t15_build_slice1.log`，属一次性证据，未入库）记录了`VmSchedulerIo.cpp`→`nlang_vm.lib`→`nvm.exe`的重编重链早于那四行的测量，
  所以对比的确实是改过并重建后的二进制。**但这条实验能排除的只是「切片长度是旋钮」**：1 ms与10 ms都小于一个
  15.625 ms的时钟刻度，如果机制是「任何带超时的等待都被时钟刻度向上取整」，改成1 ms本就不会有变化，
  所以它并未排除该机制。（第一轮报告把它当成对该机制的否证，属过度解读，在此更正。）

这三条排除的是「并行度不够」「运行时里睡了一觉」「切片长度是个旋钮」。**它们都不排除领头假设——
「任何带超时的等待都被15.625 ms的时钟刻度向上取整」。**

### 只是佐证、不构成排除

- `timeBeginPeriod`的申请是**进程级**的：Windows 10 2004（build 19041）之前全局生效，之后只惠及申请进程自己
  （官方文档仍是全局口径，这次变更没有公告，只有社区实测记录了它）。本机2026-11-10直接验证过：持有申请的进程
  自身`Thread.Sleep(1)`的中位耗时由15.56 ms降到2.00 ms，同一时刻另一侧不申请的进程仍是15.59 ms，而两边的
  `GetSystemTimeAdjustment`增量都读作156250——那个字段看不出申请。所以PowerShell里的持有者改不到nvm进程的
  分辨率，此前那组进程外对照实验从未真正改变自变量，它对这条假设既不支持也不否定。探针
  `tools/http_perf/probe_clock_hold.ps1`一次跑出上面那三个观测量。
- 运行时里没有每请求的显式睡眠，只排除了「有人`Sleep`了15 ms」；被超时取整出来的等待看起来同样「没有睡眠」。

### 未排除的候选与下一个判据实验

判据实验E0已跑完（读数见本节末），它把领头假设的一半从「未排除」升为「已证实」：一个不带VM、不带GIL、
不带载体、不带脚本的纯C++服务器，只把兴趣登记的时机从轮次边界挪到停泊时刻，15 ms量子就整格消失。
剩下的未排除项因此收窄成一句话——**真服务器凭什么在32与128连接下仍让轮询空转到超时**（控制组在那个
连接档不空转）——这句已经由E2裁定（读数见本节末）：32连接那一格多出的那段正是登记时机，登记挪到停泊时刻后该格不再被超时终结；128连接那一格修正前就已钉在自身吞吐上限约5.8k RPS，其P50从来不是等待量子，那一格剩下的上限归E5的成分表。下列各条按代价排序，编号沿用docs/dev/net_http_perf_design.md§3.3的实验编号：

1. **E1：在nvm进程内调一次`timeBeginPeriod(1)`**（临时一行、重建、重跑1／4／32／128四行）。E0已在
   VM之外证实「轮次由带超时的等待终结、该超时被15.625 ms刻度向上取整」这条机理，同一检查在控制组里
   也已做完（下文E1a读数：申请1 ms分辨率，量子由15.55 ms落到10.33 ms），所以E1不再是该机理的判据，
   只回答一个次要问题：VM那一侧的量子是不是同一把刻度取整的。按控制组的读数预期它把VM的量子从
   15.5 ms调到10 ms切片附近、RPS从64调到97附近。**这仍不是修法**，修法是按裁定D1把登记移到停泊时刻；
   D2「不常驻`timeBeginPeriod`」的理由不受影响，E1a还给它添了一条独立证据（见该节末句）。
2. **E2：按D1把VM的兴趣登记移到停泊时刻**（切片与时钟刻度都不动），重跑同一组行。这是唯一能定修法的
   实验，也是判定上面那句「VM凭什么仍空转」的判据：E0只在VM之外预证了形态，VM内的载体排队与脚本
   耗时是否另有加持，只能改VM来量。
3. **E3：在D1之上把无截止形态的轮询超时改为不限**，看登记本身能否打断在途等待——E2见效的机理归因靠它。
4. **E4：VM内的裸socket探针**（只用`net`模块回固定字节，绕开`http.n`）。E0已经分掉「VM／纯native」这一层，
   所以E4的作用收窄为分离VM内的脚本层成本。
5. **E5：每请求分段计时**，给0.9 ms的服务时间出成分表；D3、D4、D5各能削多少，看这张表。**已跑完（2026-11-11，临时插桩，饱和与限流两档各测1与128连接，读数见本节末E5读数小节）**：成分表落在该小节，D3、D4、D5的削减上界、128连接吞吐上限的归账与「GC与分配停顿」一行的缺口都在那里；「GC与分配停顿」一行为声明过的未插桩缺口。

TCP侧的延迟确认与Nagle交互（H3）已由E0排除为量子的来源：同一台机器、同一`oha`参数、同一份native代码、
同样开`TCP_NODELAY`，只差登记时机，一边15.55 ms一边0.08 ms——同一套TCP交互下量子可以是零，量子不是TCP自己
产生的。至于量子的具体来源是不是「10 ms切片被15.625 ms刻度向上取整」，同一份控制组里改一次分辨率就能判，
比在VM里做便宜——已经做完，读数见下文E1a：改分辨率，量子的分母跟着从刻度换成切片。

**E0读数（2026-11-11，机器锁内，每格两趟）**。控制组`tools/http_perf/control_server.cpp`只编译四个翻译单元
（`control_server.cpp`＋`src/vm/IoPollerWindows.cpp`＋`src/3rdparty/wepoll/wepoll.c`＋
`src/native/net/net_platform_windows.cpp`），不链VM库；`oha`参数与主表同款（测15 s、预热3 s、生成线程4、
请求超时10 s、禁压缩），0字节响应。两趟之差：带量子的那两格（轮次边界形态的1与4连接）RPS差≤0.8 %、P50差
≤0.08 ms，其余各格0.8 %到9.6 %（128连接最抖，P50两趟差最大0.19 ms）——吞吐越高本机抖动越大，但不影响
量子与量级的判定。下表每格取两趟的中位数（两趟时中位数与平均值同为中点，与主表口径一致），写作「RPS／P50 ms」：

| 连接数 | NLang http.n（主表4载体行） | 控制组·轮次边界登记 | 控制组·停泊时刻登记 |
| --- | --- | --- | --- |
| 1 | 64／15.51 | 64／15.55 | 11035／0.08 |
| 4 | 321／15.18 | 257／15.59 | 33043／0.12 |
| 32 | 2501／14.80 | 66682／0.44 | 57735／0.53 |
| 128 | 5852／21.47 | 63812／1.90 | 64869／1.84 |

公平性说明两条：控制组不设截止时刻（真服务器的轮询超时取「最近截止」与切片之小者，那一形态由E3考察）；
每响应的活儿也比真服务器少得多——解析止于空行、响应是一串固定字节，所以0.08 ms是I/O与唤醒形态的下限，
不是服务器改完后的目标值。每连接一个OS线程而不是虚拟上下文，这是「把VM摘掉」这个变量的本体，不是不公平项。

四条读法。

- **1连接那一行是本轮最干净的一条证据**：一个不带VM、不带GIL、不带载体、不带脚本的纯C++服务器，把兴趣
  登记放在轮次边界时，每请求延迟与真服务器只差0.04 ms（15.55对15.51），RPS同为64。而64＝1000/15.625，
  正是本机时钟刻度的倒数。量子与VM无关，在native层就能整格复现——这是§3.3判决矩阵的第一支：
  轮次边界形态复现台阶、即时登记形态不复现。
- **4连接那一行的257＝4/15.625**，比真服务器的321低两成。真服务器多出的正是主表已记录的「一轮服务多个
  连接」的批量合并（主表注：321是4×64＝256的1.25倍）；控制组每连接一个OS线程、各停各的，一轮里不合并，
  所以它给出的是「每轮只结一个量子」的裸值。这条差异不影响读法，反而印证量子的分母就是那个刻度。
- **登记移到停泊时刻，四个连接档全没有台阶**：1连接11035 RPS／P50 0.08 ms，与主表Node的11687／0.08、
  Go的12023／0.08同档；4连接33043／0.12在Go的37412／0.10与Node的20043／0.19之间；32连接57735／0.53、

- **128连接上限归账（E1与E2留的账）**：饱和128连接P50 21.32 ms≈排队16.98＋共享形态工作4.94，端到端均值22.03对四段之和21.91只差0.5 %。吞吐5809 RPS乘限流档工作0.61 ms＝每秒3.55 s CPU，超过「每秒至多约1 s脚本CPU」（`VmScheduler.h:8-9`的GIL口径）三倍有余。两种读法只剩一种能被GC／停顿插桩区分（本补丁没有）：高并发下每请求GIL实占约0.17 ms（1连接段值里的native读、`fill`停泊与发送等待都释放GIL），或者GIL串行口径对本形态不成立。无论哪种，128连接的限额在「每请求脚本成本×连接数」的总吞吐侧，不在单请求等待路径——裸探针同档25986 RPS给出的4.5倍成本余量同向印证。D9候补项P1的启用条件（窗口数组分配与GC压力占比）在本表只有代理读数：native暂存每请求2.79至3.03次，脚本堆的8 KiB窗口数组分配次数与GC停顿未插桩，定量判定留给插桩后的复测。
- **「GC与分配停顿」一行**：按§2.4的声明交付为缺口——本补丁未插桩GC停顿本身；已插桩的代理量只有native暂存分配（写侧恰好每响应1次；读侧128连接饱和1.79次/请求低于1连接的1.87，粘包合并所致，spec担心的「暂存分配被算进脚本段」已排除：它每请求2至3次、单价是`malloc`量级，撑不起解析段0.27至3.9 ms的任何一档）。脚本堆的窗口数组与`Date`格式化数组、头部累积数组的分配次数都在脚本侧，未插桩。

与门槛的关系（判定归v0.13.6的验收，本表只交读数）：spec §2.2的「1连接行预计约1070 RPS、仍差门槛8 %」算的是D1落地前的0.91至0.96 ms限流档；D1落地后限流166 QPS的P50实测0.68 ms（p90 1.08、p99 1.40），1连接闭环实测1798到1827 RPS，都已优于0.855 ms／1170 RPS的门槛线——门槛线1在预设脚本项（D3、D4、D5）未动的情况下已过，「脚本层削减是达标必要条件」的前提随E2的读数失效；脚本层削减剩下的意义是把1连接行从门槛线以上继续推向与Node同量级（还差6.4倍，见读法二的上界）。

### http.n每响应的次要成本（本版已清偿两处、剩余登记）

旧快照核实的两处代码位置，本版都已处理：

- **分两次写已合并**：D3 `7c2c9376`把头部与小body合并为一次发送（`writeHeadAndBody`，`stdlib/http.n:1027`）：
  头＋body不超过JOIN_CAP 8192字节（`stdlib/http.n:834`）时拼成一份写一次，超过或body为0字节时退化为原来的
  两次写。8 KiB body加约75字节头部约8267字节，超上限、仍是两次写——第4节第6条登记的「8 KiB格对0 B持平」
  正是这个形态。
- **`Date`头按秒缓存已落地**：D4 `9b8e19e2`（`stdlib/http.n:1169`-`:1179`）：每秒只调用一次`HttpDate.format`
  （`stdlib/http.n:651`起），同一秒内直接复用缓存字符串；旧记录里「13次字符串串接加两次数组分配」每响应一次
  的形态只在跨秒的那一个响应上发生。

剩余两处按设计文档D9列为第0级候补，本版未动手，下一个任务按D9的启用→复测→停止流程推进：

- **响应头逐响应装配**：`stdlib/http.n:1189`的逐头循环每响应跑一遍，其中逐响应不变的文字（状态行、
  定长字段、CRLF分隔）可以预编码。E5成分表「响应头装配＋写」段限流档每请求0.13到0.16 ms，装配部分按读法二
  记在第0级另账。
- **正文被拷两次**：先逐字节拼进合并缓冲区（`stdlib/http.n:1034`-`:1036`），发送时再拷进native发送暂存缓冲。
  E5的native暂存分配计数（写侧每响应恰1次）是它的代理读数；可削上界在读法二的0.45 ms池以内。

E3在它之上只改一处：把`NextIoTimeoutMs()`里`if (!any)`分支（`VmSchedulerIo.cpp:183-184`）的
`return kIoPollSliceMs;`改成`return -1;`（不限等），重建时序与E1一致——先编打补丁的`nvm`、测、按行
精确删回（不要`git checkout --`：它会丢掉该文件全部未提交改写）、再重建回去；`git status --porcelain src/`
为空才算还原干净：

```bash
tools/gate.sh --shared e3-build temp/t31 cmake --build build-dev --config Release --target nvm   # 打补丁的nvm
tools/gate.sh e3-infinite temp/t32 bash tools/http_perf/probe_slice_ab.sh E3
tools/gate.sh --shared e3-revert temp/t31b cmake --build build-dev --config Release --target nvm  # 删回补丁之后
```

E3的两种预期结局都算正证：要么挂起仍被登记唤醒、P50保持亚毫秒（`GATE e3-infinite: PASS`带读数，
本次即此支），要么服务器一条都不回话——探针过不了就绪检查（`probe_slice_ab.sh:70-78`的40次`curl -sf`
×0.5 s），stderr打`server never answered on …; see …/slice_E3.log`并以rc=1退出，门禁判
`GATE e3-infinite: FAIL rc=1`。后一种FAIL形态是本判据预期内的正证（挂死＝挂起本身要靠注册唤醒），
按正证记录，不触发「任一门禁失败全批作废重扫」。

E4裸套接字地板探针不依赖主测量产物——脚本自己渲染`probe_raw_server.n.in`并编译`probe_raw.ncu`，全程只占机器锁。
标签口径同本节标题：改动前用`base`，本版改完后用`post`（与`probe_slice_ab.sh`的标签口径一致，两趟地板不会互相覆盖）：

```bash
tools/gate.sh e4-raw temp/t22 bash tools/http_perf/probe_raw_ab.sh base
tools/gate.sh e4-raw-post temp/t43 bash tools/http_perf/probe_raw_ab.sh post   # D1落地后的修正地板，E5减法用这张
```

可调环境变量：`PERF_RAW_PORT`（默认18086）、`PERF_RAW_CONNS`（默认`1 4 32 128`）、`PERF_CARRIERS`，以及共用的
`PERF_DUR`／`PERF_WARM`／`PERF_THREADS`／`PERF_REQ_TIMEOUT`。

E5成分表需要打临时插桩补丁（内容见§5末E5读数小节开头：`http.n`的四段计时与每2000请求的stdout打印行、
`net.n`的`_perfStat`声明、`net_tcp.cpp`的两个native分配计数与`net_native.cpp`的注册；快照`temp/e5_patch.txt`
是一次性证据，不入库）。打完补丁必须全量重建——`nlang_stdlib_package`随全量构建重打，探针的`http.n`从包里取，
只重建`--target nvm`会让包里的`http.n`停在旧版；测完还原补丁再全量重建回去，否则工作树干净而二进制仍带插桩：

```bash
git apply temp/e5_patch.txt
tools/gate.sh --shared e5-build temp/t33b cmake --build build-dev --config Release
tools/gate.sh e5-sat temp/t33 bash tools/http_perf/probe_slice_ab.sh e5sat                                       # 饱和档，PERF_SLICE_CONNS="1 128"
PERF_SLICE_CONNS="1 128" PERF_OHA_EXTRA="-q 166" PERF_DUR=90s tools/gate.sh e5-throttle temp/t34 bash tools/http_perf/probe_slice_ab.sh e5thr
git apply -R temp/e5_patch.txt
tools/gate.sh --shared e5-revert temp/t36 cmake --build build-dev --config Release
```

重跑的三个坑：`PERF_DUR`／`PERF_WARM`必须带单位后缀（`90`会被`oha`的参数解析拒绝，探针把两条`oha`调用的
stdout与stderr都重定向到`/dev/null`，clap报错被吞掉——实测轮没跑、上一趟的旧JSON还在，读数就原样重印出旧数字，
假绿；探针已在实测轮前删`$OUT/slice<标签>_<连接数>c.json`堵这条，见`probe_slice_ab.sh:59-62`）。
`PERF_OHA_EXTRA`只对实测轮生效（预热不限流），`-q 166`是全局限速（与§5限流表同一机制），不是实施计划
逐连接6 ms的模型——128连接下它是相邻连接约770 ms的全局间隔，两种口径的分解裁定见计划台账Task 4。
成分表读数取`slice_<标签>.log`里2000请求批的批间差分（解析脚本`temp/e5_batches.py`，一次性），并用`fill`
等待指纹分离预热与测量段；限流档窗口要拉到`90s`——166 QPS下15 s只有约2.5 k请求，会被预热的约16 k吞掉。
还原后核对`git status --porcelain src/ stdlib/`应为空；若残留M行而`git diff`对同一文件为空，那是`git apply`
重写文件时换行符与索引存储形态不同造成的幻影（内容一致），`git checkout -- <文件>`恢复索引表示即可——
这些文件还原后本应等于HEAD，checkout丢弃的正是补丁改写本身。

定时器分辨率探针只读不测吞吐，不必占机器锁：`powershell -File tools/http_perf/probe_clock_hold.ps1 -Seconds 120`。

每次测量的原始JSON与`results.md`都在`temp/http_perf/`（临时区，不入库）；本文是入库的那份快照，
重跑出新数据后用上面那条命令重生成——要改正文就改模板，别改生成出来的那份；想留多份带日期的快照，
把命令的第三个参数换成新文件即可。

本版「落地复测」小节的三组重跑另有三条口径。限流扫描`probe_pace_ab.sh`的8档输出JSON文件名固定
（`pace_q*.json`与`pace_unlimited.json`），同一目录重跑会互相覆盖，多趟必须用`PERF_OUT`给每趟指一个不同
输出目录——q200的5次复测各走门禁前缀`t70`至`t74`，第二趟落在`spread2/`子目录，正文表格读数取第一趟；
`probe_slice_ab.sh`的标签就是输出文件名，`slicepost1`与`slicepost2`天然分开两趟（切片代码未改，两趟纯粹
重测取散布）；`probe_raw_ab.sh post`直接覆盖了D1时代的同名JSON，旧四值的读数只在正文里留存——覆盖之前
要先确认正文已经记下它们。

## 7 与排期的关系

本文的母问题——15 ms量级的每请求延迟——在2026-11-10快照里立项进v0.13.6「net/http库性能优化」（见roadmap），
本版已落地：D1 `2053fb5b`定位并修掉了VM网络等待路径的时钟刻度问题（15.625 ms量级，定位全程见第5节），
D3至D7依次落地，`http.n`的两处每响应次要成本由D3（分两次写）与D4（`Date`按秒缓存）清偿（第5节末）。
本版三项判据的验收结论在设计文档§七，本文第5节「v0.13.6验收判定」小节与之互为镜像：量子项与量级门槛达标；
脚本成本项未达标，D9第0级两项（预编码响应头、去正文二次拷贝）留给下一个任务，按「启用→复测→不超过该档
散布或不足1 %即停」的循环推进——停止条件来自用户裁定：继续优化，直到改进效果不明显。落地复测的跨探针
