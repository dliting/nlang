## 1. 共同模型（三阶段共用，一次说清）

**名字**

```
<项目源码根>/utils/helper.n   → 包 utils.helper → import utils.helper;  utils.helper.help()
<搜索根>/gfx/color.n          → 包 gfx.color    → import gfx.color;     gfx.color.Rgb
<搜索根>/io.n                 → 包 io           → import io;            io.print(...)
```

起点两处：项目＝`.nproj` 所在目录（`ncc/main.cpp:284` 已在填），库＝`-I` 搜索根
（`ncc/main.cpp:56-58`）。单文件编译时起点＝该文件所在目录，结果与今天的文件名退化档
相同（`one.n` → 包 `one`），但不再是特例分支。
限定符＝包名原文（末段重复就写更长那段），无末段简写、无 alias 语法。

**产物三层**（`.ncu` → `.npkg` → native DLL）

| 层 | 粒度 | 名字从哪来 | 落点 |
| --- | --- | --- | --- |
| `.ncu` | 一个源文件＝一个编译单元；其路径给出包名 | 成员路径＝包名 | obj 目录（`.nproj` 里已有、ncc 从没用的 `intermediateDir`，`ProjectFile.h:12/18`；nide 侧 `ProjectModelXml.cpp:248/286/310` 已在读写） |
| `.npkg` | 一个包链接打包（多文件集合，相当于一个库） | 头部成员表：成员路径＝包名；程序与库的差别**只在头部有没有入口点记录** | `outputDir` |
| native DLL | 一个库 | `nlang_<库名>.dll`，符号＝完整限定名 | 搜索目录 |

`.npkg` 头部有一张成员名表（就是归档自己的目录），所以 `import a.b.c;` 定位＝在搜索根逐个
开 `.npkg` 头查成员 `a/b/c`——**不需要额外的包索引，也不需要扫源码目录**。

### 命名与可见性模型（2026-10-01 用户裁定，此前口头讨论未成文，现记录）

1. **包名按路径自动派生**：`${project_root}/a/b/c.n` 的包名就是 `a.b.c`，通过
   `import a.b.c;` 引用。源文件的路径即其包名，文件内不再有任何命名语法。
2. **项目内部引用**：同一个项目中，内部包一律从**项目源码根路径**引用——
   「路径从哪里开始数」由项目源码根路径（`.nproj` 所在源码根）指定。
3. **跨项目引用**：一个包整体打包成一个 `.npkg`，相当于一个库；消费方通过
   **包搜索路径**引入（搜索根列表，与源码发现同一条路径链）。
4. **可见性声明**：每一级路径下可以放一个 `_package.n`，声明**当前这一级路径**中
   各包（文件）的导出规则（对外可见性）；缺省全部导出，可以改写默认规则。
   `_package.n` 不一定在根上——它只管自己所在这一级，不管子树。
   （此项落在阶段 7；「只管本级」的裁定同时解答了下文阶段 7 待裁决第 4 条。）

**依赖方向**：名字必须先是唯一的、且类型与函数同规则，未解析引用才能「先记名字、链接时定址」；
对象与文件一一对应后，依赖记录才退化成「一条来源路径＋一个校验和」。所以 5 → 6 → 7。

## 2. 三个阶段

### 阶段 5「包名与类型身份」（＝原 4e，详细设计见 `docs/dev/phase5_design.md`）

做：名字唯一来源＝路径；**每个源文件的成员挂进自己的包容器**（今天只有写了 `namespace`
的库文件才有容器，项目模块全挂在 root 上，`ModuleRegistry.cpp:293-300/377-385`）；
VM 类型表改用限定名（与函数表同规则）；撞名一律诊断、不 first-wins；`entryPoint` 进产物；
`.ncu` 格式 12→13；删 `namespace`；类型路径有自己的语法范畴；连带面（stdlib／测试／
langservice／nide／文档）一次改完。
不做：产物粒度（仍是整项目一份合并 `.ncu`）、`.npkg`、可见性、依赖记录。

### 阶段 6「目标文件与打包」（新阶段）

做，按依赖顺序：

1. **逐包产码**：`MergeTransUnits`（`ModuleBuilder.cpp:233-258`）在产码前就把所有 TU 的 AST
   合成一棵树，所以今天只能有一份产物。改为解析／类型检查后**不合并**，每个包各自跑一遍
   `VmBackend`，输出一份 `.ncu`。
2. **未解析引用表**：跨包的函数／类型引用在 `.ncu` 里按名字记账（限定名＋需要的下标类别）。
3. **`.npkg` 归档**：成员路径＝包名，头部带成员名表。格式自有版本号。
4. **链接器**：按名字解析引用并把按下标的操作数定址。半条链路已在跑，直接升级而非新写：
   `Import.cpp:164-168` `RemapBytecode`（补 11 类按下标的操作数）、`TypeDesc.h:90`
   （struct/class 下标从产方编号改消费方编号）、`Import.cpp:231` 起每模块一张
   `PerModuleRemap`（stringMap/classMap/structMap）。差别是触发时机从「导入时合并」
   改成「链接时定址」。
5. **入口点搬家**：`entryPoint` 从 `.ncu` 移到 `.npkg` 头部。规则：`.nproj` 指定入口源文件
   （缺省 `main.n`）→ 该文件的包里的 `main()`。不新增关键字。
6. **命令面**：`ncc build -p x.nproj` 产出 obj 目录下的一组 `.ncu` ＋ `outputDir` 里一份
   `.npkg`；`ncc run x.npkg`。打包库与产出可执行是**同一条命令**，不新增动词。
7. **native 面收口**：DLL 按库命名、符号按完整限定名；解除阶段 5 的「`native` 只允许单段包」
   诊断（库身份出现后，包→库有确定映射；今天的「按第一个点切分」实现在
   `VmExecutorNativeHost.cpp:146-152`）。
8. **格式号**：`.ncu` 语义变（一包一份 ＋ 未解析引用表 ＋ 不再有 `entryPoint`）→ 再抬一次；
   `.npkg` 新格式自带 1.0。

### 阶段 7「依赖、过期与可见性」（＝原 4d ＋ `_package.n`）

做：`.ncu` 记录来源文件路径与内容校验和（对象＝一个文件后，这就是全部信息）；nide 侧
过期检测＋增量编译（只重编变化的源文件）；`runNccBuild` 异步化；`_package.n` 目录级对外
可见性（缺省全导出、只写导出／导入语句、跨库边界才生效）；`ndb` 读库源码。
其中 `runNccBuild` 异步化与 `ndb` 读库源码与产物格式无关，任何时候都能做。

## 3. 待用户裁决（四条，均给了默认，不阻塞阶段 5 开工）

1. **顺序** 5 → 6 → 7（默认照此）。
2. **阶段 5 期间带点导入名只解析到源码库**：预编译二进制仍按「文件名＝导入名」定位
   （`ModuleBuilderImports.cpp:283`）。带点名字落到二进制上是阶段 6 `.npkg` 成员表的事。
3. **程序与库共用 `.npkg`**，区别只在头部有没有入口点记录；不给两种扩展名。
4. **`_package.n` 的子树空洞**：一个目录里的文件管不了整棵子树——`internal/` 隐藏后
   `internal/net/pool` 仍可导入。要么加一条「整棵子树对外」的规则（Go 的 `internal/`），
   要么接受只管本级。
   **已裁定（2026-10-01，见 §1 命名与可见性模型第 4 条）：接受只管本级**——
   `_package.n` 只声明自己所在这一级的导出规则；子树各层要收窄就各放各的 `_package.n`。
