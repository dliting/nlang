## 一、引言

一趟T1实测7598秒（2小时06分38秒，`temp/mg-t1b/gates/`各腿判决文件的mtime跨度），而其中真正花在「判定改动对不对」上的时间被两类开销吃掉：一是腿内串行（e2e单进程串行、ctest无`-j`），二是超时判定本身按「空机数」写死——登记处注释自陈得很清楚（`tests/CMakeLists.txt:825`的`idle machine — Debug 187.5 s, ASan 908 s (4.84x compile-heavy factor)`、`:1634`的`multiplies these families' wall time by 2.7x-8.7x`）。空机数性质正是门禁机器锁的三条理由之一（`tools/gate.sh:20-27`：计时敏感、桌面焦点链、`%TEMP%`），于是「怕并发把计时搅乱」反过来要求「整台机器一次只跑一条测试腿」。

代价已在本次收尾中实测到两笔。一笔是排队：一处纯Python改动（`tests/e2e/run_e2e_tests.py`）排在机器锁后等待40分钟以上，拿到锁后又连续被跑器的陈旧守卫拦下两起——构建树里陈旧的Debug版`ncc.exe`与Release版`ndb.exe`各一次——四条腿都以rc=2假失败收口（`ncc`两起见`temp/mg_t1_untagged.out:1`、`temp/mg_t1_probe.out:1`，`ndb`两起见`temp/mg_t1_tagged.out:1`、`temp/mg_t1_untagged2.out:1`；跑器在只给两个位置参数时把`ndb`默认成Release版，见`tests/e2e/run_e2e_tests.py:519-521`）。等待没有换来正确性，只换来排队。另一笔是帽本身：同一条目、同一构型、同一提交，裸调用跑器判红、经门禁腿调用判绿，差别只在一条`--timeout`旗标（F-10）。

用户裁定（2026-11-20）：删掉门禁的机器锁；性能判据不依赖墙钟绝对值，改用相对时间（先测出本机基准性能，涉及超时的测试按该基准做相对估算）；性能测试与非性能测试分离，普通开发阶段只跑非性能测试，版本收尾跑性能测试；重复与浸泡类用例的强度用统一的「性能测试系数」表达（缺省100轮，系数2则200轮），并按构型分别定轮数；功能类也尽量少花时间，示例型验收程序需要时作为examples跑即可，不进每轮。

本文是该裁定的概要设计（Spec）：钉死判定模型、三个轴的口径、去锁后的互斥边界、可程序化守卫与实施顺序；逐任务细化留给实施计划。文风与结构仿`docs/dev/gate_write_dir_lock_design.md`。

## 二、目标与范围

### 2.1 本版做

- 把超时判定从「按经验写死的绝对秒数」改为「参考耗时×工作量比×机器标量×安全系数」的预算判定，并把「挂死看门狗」与「性能预算」拆成两个各管一件事的机制；
- 建立逐条目×构型的参考表（入仓、可`--record`重录、带默认行与例外行、带类别列），配套棘轮与完备性守卫；
- 三轴分离并各自可核对：类别轴（性能类/功能类按断言性质划）、排期轴（T0/T1/T2/性能环境）、强度轴（工作量系数）；
- 削减功能类的工作量：`nd_resolve_stress_tests`的浸泡轮数按构型分别登记、示例型验收程序退出每轮，并给出判定「工作量该取多少」的通则；
- 删除门禁机器锁与`--shared`标志，保留并泛化具名资源互斥，把「必须互斥」的面收窄到取证支持的程度；
- 补齐去锁的前置根治：跨进程共享的全局状态（注册表设置键）、被覆盖的scratch环境、有界等待的三类时间用法（判据、放弃阈值、时序型激励，见D-12第4条）。

### 2.2 本版不做

- 不改测试断言的内容与判决语义；「断言不得依赖时间」的裁定（2026-11-14）继续成立，本文把它细化为三类（判据不依赖时间、放弃阈值读标量、时序型激励窗口读标量且须登记为例外，见D-12第4条）。第三类不是放松判据：它覆盖的是「被测性质本身就是时序」的条目，全文只有`test_threads.cpp`那一处，且要求登记加失败文案自带归因；
- 不改T0/T1/T2的层定义与判决行字形（`GATE <腿名>: PASS|FAIL`）；只补慢条目的成员口径、回补规则与守卫。层定义不动不等于腿集合冻结：某类别在现有腿里根本没有载体时，收口批必须补一条腿（本版补`T2-perf`，见D-6），否则「版本收尾跑性能测试」这条裁定只是没有执行体的文字；
- 不实现腿内并行与e2e分片本身（属2026-11-20 T1提速批的Task 2-4）；本文只规定该负载形态下预算如何派生、机器标量在何种负载下采样，不承担实现；
- 不引入「按时间目标自动决定迭代次数」的机制（Google Benchmark式）：工作量由人按环境决定，不由机器速度反推（理由见D-4）；
- 不做向下兼容：`--shared`旗标与机器锁一并删除，仓内调用点与文档同批改（AGENTS：当前无需向下兼容），调用点清单见第十节。

## 四、判定模型

**D-1 预算公式。** 每个条目在某构型下的性能预算秒数按一条公式计算，公式是唯一的判定入口，任何腿不得另立口径：

```
工作量比[条目] = 本轮工作量 / 参考工作量[条目]          (≥ 1)
看门狗帽[构型][条目] = max(参考秒数 × 工作量比 × WATCHDOG_MULTIPLIER, MIN_WATCHDOG_S)
预算秒数 = clamp(参考秒数 × 工作量比 × 机器标量 × SAFETY_MULTIPLIER,
                 MIN_CAP_S,
                 看门狗帽[构型][条目])
```

工作量比必须同时进看门狗帽：系数为2时工作量翻倍，只抬预算而不抬看门狗，看门狗会在预算判「慢」之前先把合法长跑杀掉，公式退化成「系数只能调小」。

常量：`SAFETY_MULTIPLIER = 2`、`WATCHDOG_MULTIPLIER = 10`、`MIN_CAP_S = 60`、`MIN_WATCHDOG_S = 2 × MIN_CAP_S = 120`、`SCALE_BAND_MIN = 0.25`、`SCALE_BAND_MAX = 4.0`、`DEFAULT_WORK_FACTOR = 1`、`SLOW_MIN_REF_S = 300`。两道地板都是必需的：参考1秒的条目按`参考×10`只有10秒，会低于预算下限而使clamp的下界大于上界；把看门狗地板设为预算地板的两倍，是为了让两者永不可能叠成同一个数（叠equal时「越预算」与「越看门狗」文案无法区分，D-2的拆分失去意义）。三个倍率之间的关系是可核对的不变量：`WATCHDOG_MULTIPLIER > SAFETY_MULTIPLIER × SCALE_BAND_MAX`（10 > 2×4），它保证带内任何机器标量下性能预算先于看门狗触发，挂死与慢不会互相伪装。

自洽校验：`nd_resolve_stress_tests`按100轮计的ASan参考约589秒（本轮实测200轮1178.8秒的一半），`589×2=1178`秒落在今天手工写死的1260秒帽之下、只差6%；而登记处注释的空机读数是另一口径（`:825`的Debug 187.5秒/ASan 908秒，按200轮），折算100轮再乘安全系数得908秒。两个样本同为秒级量级但相差约30%，差别正是「空机」与「有负载」——这条差异本身是参考表必须记录测量形态（D-3）的理由，也是安全系数不能小于2的依据。

**D-2 看门狗与预算分离。** ctest条目的`TIMEOUT`属性在配置期从参考表派生成**看门狗帽[构型][条目]**——D-1那条`max(参考秒数×工作量比×WATCHDOG_MULTIPLIER, MIN_WATCHDOG_S)`，不是少了地板的裸积，否则`参考秒数×工作量比`较小的条目会派生出低于`MIN_WATCHDOG_S`地板的帽、与D-1自相矛盾——其中工作量比的工作量侧取自登记处按构型给的轮数、系数侧在配置期读`$ENV{NLANG_TEST_WORK_FACTOR}`——F-4已证明ctest没有运行期缩放旋钮，系数只能进配置。它不含机器标量，配置期没有标量。抬系数而不重configure该树，看门狗仍停在缺省系数那条线上：系数2的合法长跑实测可到`8×参考`，`10×参考`的kill线只剩1.25倍余量，一台普通的慢机器就会被杀在预算判「慢」之前、报成`TIMEOUT_WATCHDOG`「挂死」——正是D-1要禁止的互相伪装。因此守卫五核一条等式：`TIMEOUT == max(参考秒数 × 本轮工作量比 × WATCHDOG_MULTIPLIER, MIN_WATCHDOG_S)`——与D-1的帽公式是同一条含地板全式，被地板顶住的条目按地板值核对，裸积会在它们身上误判红（`TIMEOUT`从`ctest --show-only=json-v1`读、系数从环境读），不符即红并写明处置是「先重configure该树（只重生成`CTestTestfile.cmake`，不重编）」，而不是让红灯指向挂死。它的职责只剩一个：真挂死时把进程杀掉并给出可归因的失败。真正判「慢」的是门禁层在腿跑完后按实测逐条目耗时与预算的比对，超时原因分两种文案：`TIMEOUT_WATCHDOG`（挂死，越过看门狗帽）与`TIMEOUT_BUDGET`（相对本机慢到超出预算）。两者同落一个条目时`TIMEOUT_WATCHDOG`优先、事后预算比对跳过已被看门狗杀掉的条目：倍率不变量（D-1）保证预算严格低于看门狗帽，所以被杀的条目必然同时越预算，但杀进程才是该趟的物理事实——一条目出两条判决文案，正是D-5要禁的「告警说A、杀进程是B」的镜像形态。这条拆分同时满足两点：判定与实际帽不再脱钩（F-9的Bazel #12411教训），且「帽是校准产物不是断言」这一既有定性不再被误用成性能门槛。

e2e跑器与自研包装脚本（`tools/qtest_progress.py`等）是自己写的代码，运行期读得到标量，因此**内联**判定：超预算即当场终止该条目并计FAIL，不必等跑完。两类消费点的差别只在「能不能拿到标量」，判据同源同公式。

标量缺位（裸调用、不经门禁校准）时消费语义只有一条：**倍率取`SCALE_BAND_MAX`**，即带内允许的最慢机器，并在失败文案末尾注明「未做本机校准（缺标量），处置是经门禁跑或导出`NLANG_GATE_MACHINE_SCALE`」。取宽而不取紧是有意的：机器可能确实慢到那个程度，裸调用在一台慢机器上不该成片假红而同窗的门禁腿还是绿的；代价只是真挂死的条目在快机器上要多等到宽帽才被内联终止，而ctest形态的挂死仍由看门狗帽封顶、与标量无关。这条回落同样适用于D-12第4条读标量的等待阈值——全仓不得再出现第二种「无标量」回落口径（否则advisory与判决又脱钩，D-5）。e2e形态的构型输入在缺位时同理只有一条回落：裸调用没有显式参数入口，构型只能按二进制路径猜——D-3已证Debug与ASan的工具路径都含`/Debug/`，所以猜测只有两值（路径含`/Release/`判Release，否则判Debug，ASan按Debug计价）、取参考行时按`e2e-`前缀的构型键取（跑器恒属e2e宇宙，D-3的构型列前缀规则），且判决文案必须打印「假定构型X（按路径猜测）」把这个口径透明化。门禁腿的构型恒为显式参数（D-3），这条猜测永不参与门禁判决。

ctest腿的预算判定读junit逐条目耗时，因此参考行必须记下与判定同源的计时口径：同一并行形态、同一`--repeat`形态下记录（第八节守卫十），否则「串行录的参考」去比「并行跑的实测」，标量会把争用误算成机器慢。

**D-3 参考表。** 新增`tests/gate_time_reference.txt`（入仓、文本、机器可读），列为`构型 条目名 参考秒数 参考工作量 类别 测量形态 哨兵 理由`。`条目名`有三种作用域：条目名本身、清单文件名（`manifest.txt`/`examples_manifest.txt`，仅e2e构型有意义）、以及`default`（该构型全部条目的默认）。作用域按条目行＞清单行＞`default`行取最近的一条。在设有`default`行的构型里（e2e清单2158条目靠它），逐条目行下文统称**例外行**；清单行不算例外，它给的是整份清单的默认值而非某个条目的偏离。`理由`是最后一列、取到行尾（允许空格），两种情形必填：例外行必须写明「为什么偏离默认」，`参考秒数`>`SLOW_MIN_REF_S`（阈值定义在D-7）而仍标`常规`的行必须写明「为什么它仍留在每轮」；空理由由守卫六判红——例外若不需要理由，例外就成了默认值的另一种写法。ctest构型逐条列、没有`default`行，故只有第二条规则适用。构型维度就是四个ctest构型加e2e跑器的三种清单形态：三棵判定树（Debug单测、IDE、ASan），加发布扫荡树的Release构型——后者只在`NLANG_PERF_TESTS=ON`形态下参与登记（D-6的`T2-perf`段），该构型的消费者有两处——该腿的预算判定（消费集合就是它`-R`过滤后的条目，即perf名集合）与开跑前的标量校准（D-4的哨兵集合）——故只登记这两个集合的参考行（perf行供预算、哨兵行供校准），守卫八的ON/OFF差集同时充当perf行的完备性核对，哨兵行的完备性由守卫一的派生集合核对；e2e构型是三种清单形态（Debug、ASan、Release）。`构型`列的取值一律带宇宙前缀，七个值为`ctest-Debug`/`ctest-IDE`/`ctest-ASan`/`ctest-Release`与`e2e-Debug`/`e2e-ASan`/`e2e-Release`：行的宇宙归属由前缀直接给出，不靠条目名落在哪个名字集反推——两侧名字集今天实测互斥（147个ctest条目名∩2202个清单行名为空集），将来条目与清单行撞名也不会串宇宙，守卫一与守卫十一都按带前缀的`(构型, 条目)`键配对——F-2证明「构型」必须是参考表的维度而非一张倍率表：换构建树几乎不改耗时（中位0.96），换消毒器却逐条目跨0.90–8.13（中位4.83），单一标量表达不了后者，把倍率表塞进公式会造出一张谁也信不过的假表。

`类别`列取值枚举为`常规`/`慢功能`/`演示验收`/`性能`四类，是排期轴的唯一真源（D-7），按构型×条目分别标注；`examples_manifest.txt`的44条目整片标`演示验收`（标在清单行上——性质来自清单本身，那份清单就是D-9第3类所述「跑通一个真实程序」的验收面），不必44条例外行，守卫按条目名所属清单核对这一标注。`--record`重录实测时**必须保留人工标注的`类别`、`参考工作量`、`哨兵`与`理由`四列**，只刷新`参考秒数`与`测量形态`——否则一次重录就把排期决定与认领理由一起冲掉，慢条目悄悄回到每轮、例外行悄悄变成无理由的默认值偏离。

`测量形态`列记录制该参考时的并行度与是否独占机器；守卫据此拒绝拿串行参考判并行实测（D-2末段）。

参考表由`--record`模式生成实测后落盘：新增条目必须随附一次记录，缺参考行的条目由守卫判红（见第八节），不允许静默回落默认值——回落会把「新条目很慢」这件事藏起来。`--record`的粒度必须是「构型×条目」的单行重录（选定构型下只跑那一条目即可刷新它的`参考秒数`与`测量形态`），整轮重录只是它的批量形态；若只能整表重录，加一条测试就要在锁内付一整轮（本轮实测约2小时），这条规则就付不起，实际结局是开发者攒到版本尾统一补录、期间完备性守卫长红或被临时开后门。示例清单只有44条目（文件46行含注释）、e2e清单2158条目（文件2600行含注释），故e2e构型靠`default`行加少量例外行即可，ctest构型条目少、逐条列。e2e跑器无法从二进制路径分辨自己是Debug还是ASan构型：两条路径**都**含`/Debug/`（实测`build-asan/src/tools/ncc/Debug/`下有`ncc.exe`与`clang_rt.asan_dynamic-x86_64.dll`），跑器注释`run_e2e_tests.py:521-522`自陈「ASan builds the Debug config」，`gate_tier.sh:169`给ASan腿传的也正是Debug构型路径。该子串因此只能分辨「非Release」，分辨不了消毒器——F-10的乘3分支据此把ASan按Debug计价，而F-2实测ASan相对Debug中位4.83倍（>3），这条错计价正是跑器帽偶发偏紧的来源。结论不变但理由反了过来：构型必须由门禁层显式传入参数，不得由跑器猜路径。

`tests/gate_time_reference.local.txt`是按同格式覆盖参考行的本机文件，不入库。它是**出带机器**的修正手段，不是每台机器的必需前置：判红只绑一个条件——本轮标量出`[SCALE_BAND_MIN, SCALE_BAND_MAX]`。新克隆尚无该文件而标量在带内时照常判决（参考表本身入库，带内的机器无需修正；把它写成前置会让每台新机器首跑必红，而那种红没有任何可处置内容）。出带时本次判红并把本轮实测提为该文件的候选行（人核对后转正），而不是把判决降级为advisory——降级等于「这台机器上门禁不成立」被读成「门禁通过」。

**D-4 机器标量由哨兵条目自校准。** 每条腿开跑前，按该腿将要使用的并行形态实跑5–8条已登记为哨兵的快条目，标量取「实测/参考」的中位数，经环境变量`NLANG_GATE_MACHINE_SCALE`发布给本腿的所有消费者。哨兵选型标准：参考秒数不超过`MIN_CAP_S/2`（30秒，保证校准自身不会被自己的帽杀掉）、判决不依赖时间、耗时形态覆盖进程启动／编译／文件IO／GC四类、凡参与标量校准的构型都有该哨兵的参考行——四个ctest构型无一例外：`T2-perf`也是腿、同样「开跑前现采」没有豁免，它的哨兵参考行与perf行一并登记在`ctest-Release`下（D-3、守卫一）。不写独立基准程序：本项目测试的耗时形态是进程启动、GC、文件IO与Qt事件循环，独立基准的负载形态永远与被测物不同构（这是用户裁定里「1分钟基准」的落地形式）。

**每条腿开跑前都现采**，缓存只在同一条腿的消费者之间共享（同一条腿的ctest进程、e2e跑器与包装脚本必须看到同一个标量，D-5）。跨腿复用本版不做：复用的隐含前提是「争用与采样时刻无关」，而这条前提恰恰不成立——先跑的腿在空机上采到标量、后跑的腿撞上第二个会话，就会成片判`TIMEOUT_BUDGET`假红，D-15的advisory还会据此建议下调参考（方向正相反）。要复用就得先有一个与墙钟无关又可核对的争用指纹（本机活跃负载、并发会话数都在瞬时变化），本版拿不出可靠指纹，就宁可付采样费：哨兵按选型标准每条参考不超过30秒、按本腿将要用的并行形态并发跑，墙钟上界约等于一条最慢哨兵，一条腿几十秒，比一轮误判的红灯便宜。若实施实测表明这笔开销不可接受，再引入跨腿缓存，且必须同时给出可核对的争用指纹定义——缺了它，缓存就是把别的时刻测出的争用当成本腿的事实。

采样必须在**与真实运行同形态的负载**下做，否则标量是假数：ASan腿在`-j 4`下的争用与Debug腿在`-j 8`下不同，故每条腿按自己将要使用的形态现采。别的会话同时在跑门禁时，本腿现采的哨兵读到的正是**本腿**实际面临的争用，这是想要的行为而非污染；但它只说本腿，不能拿去判另一条腿（上段），也不说明这台机器在该形态之外有多快或多慢。

**与F-9的张力必须正面回答。** 主流框架不用机器基准算超时，是因为它们不承诺「同一提交在任何机器上给出同一种判决」；本仓要的正相反——换机器不该翻红。标量的职责因此仅限于「把参考换算到本机」，并被带门限制、不外推：标量出`[SCALE_BAND_MIN, SCALE_BAND_MAX]`即判该腿红并报「参考表对该机型无效」，处置是按该机型重录参考（或用D-3的本机覆盖文件），而不是让标量无限外推——外推会把「这台机器根本不适合跑这条腿」伪装成「某条目偶发超时」。带门的量程要说清：`[0.25,4.0]`是16倍宽容带，职责是拦「这台机器根本不适用这份参考表」的灾难性错配，不是逐条目负载偏斜的护栏——F-2实测换构建树逐条目中位0.96而换消毒器跨0.90–8.13，说明单一中位标量对偏斜条目必然偏乐观，那类条目出预算时归D-15的人判与第十一节的风险行处置。把带门说成「保证判决不受争用影响」是夸大，本文只在「机器速度换算」这一维上用标量，争用面由D-13的调度消解与逐条目例外行承担。**跨机可移植性目前只是设计假设，尚无第二台机器的实测**：实施顺序第1步要求在至少两台机器上各录一轮同构型参考，比较逐条目倍率分布，若出带条目多，则参考表按机型分文件而不是靠单标量外推。

工作量**不**由机器速度反推（与Google Benchmark的取向相反）：机器快慢只影响预算，跑多少轮由人按环境定（见D-8）。理由是确定性优先：同一提交在任何机器上必须跑同样多的工作、给出同样多的覆盖，否则「这台机器上没撞上」不能成为结论。

**D-5 一致性铁律。** 任何进入公式的缩放因子，必须同时是被比对的那一个。落地为两条禁令：判定代码与帽生成代码读同一份参考行与同一个标量（同一函数计算，禁止旁路）；advisory（建议下调参考）与实际判决读同一个数。违反其一就是F-9里Bazel #12411的同型错误：告警说的是A，杀进程的是B。F-10是同一错误在本仓的现行形态：旗标改了帽，判决就换了口径。

## 五、三个轴

**D-6 类别轴：按断言性质划，不按耗时划。** 只有断言性能量（吞吐、延迟、毫秒预算）的条目算性能类。现存仅一对：`regex_redos_perf_compile`/`regex_redos_perf_run`，只在`NLANG_PERF_TESTS=ON`时登记，即发布收口所建的那棵树（`tests/CMakeLists.txt:3074-3083`）；它断言的是墙钟预算——fixture内建毫秒帽按Release读数校准（最坏形状1203毫秒、扫描3096毫秒，帽约6.5倍于实测，合计约52秒被断言的工作），180秒ctest帽只是「引擎完全无视内建帽」时的兜底（`:3062-3065`）。性能类的排期**不能**只由登记条件决定：登记在哪棵树与谁跑它是两件事。实测`tools/gate_tier.sh:212-221`的T2由四条T1腿（`:214`复用`t1_legs`，全是`-C Debug`的ctest与e2e）加`T2-asan-e2e-full`（`:215`）、`T2-release-build`（`:217`，一条`cmake --build`，不跑ctest）、`T2-release-e2e`（`:219`）与手册五腿组成，全部T0/T1/T2腿里没有一条跑`-C Release`的ctest——`regex_redos_perf_*`今天在任何腿上都不跑。登记处注释（`:3058-3061`）把该跑的命令行写在文件里，注释不是腿：用户裁定「版本收尾，进行性能测试」需要一个载体，否则绿色T2里性能类一条也没跑。本版据此新增一条收口批的腿：`T2-perf`——发布扫荡树配置带`-DNLANG_PERF_TESTS=ON`（选项定义在`CMakeLists.txt:69`），跑`ctest --test-dir <树> -C Release -R "^regex_redos_perf"`，登记处注释里那两行命令行自此有腿执行。`T2-perf`不建第四棵树：它复用`T2-release-build`建好的那一棵（`tools/gate_tier.sh:217-219`的两条腿本就同树），只把那棵树的`NLANG_PERF_TESTS`缓存改成ON。复用成立是因为该选项只决定登记、不参与编译：`CMakeLists.txt:69-70`是它的定义，`tests/CMakeLists.txt:3074-3083`把`add_test`包在`if`里，改配ON不触发重编译。复用的代价也必须一并结清：VS多配置生成器不按条目的`CONFIGS`属性过滤（登记处注释`:3055-3058`记下的221.42秒实测就是perf条目在同树`-C Debug`下跑出来的），缓存一旦ON，perf条目也会出现在`-C Debug`的枚举里。结清方式是**除`T2-perf`以外的每条ctest腿都把perf条目名集合放进自己的`-E`**。名集合取自守卫八的ON/OFF配置差分，差分居独立scratch目录算、不碰扫荡树缓存，也不依赖参考表：perf行缺参考条目也不会漏进别的腿。腿的判决因此与缓存状态无关：`-E`恒带，ON缓存只多出被排除的条目。收口批末把缓存改回OFF是收尾动作，让裸`ctest`回到与仓内缺省一致的状态，不是判决前提。专门再建第四棵树可以省掉这手排除，代价是一整棵构建树对价几串`-E`，不值。示例验收面**不需要**新腿，且它的问题方向相反：实测`tools/gate_tier.sh:165`的`T1-debug-e2e`与`:219`的`T2-release-e2e`都不给`NLANG_E2E_MANIFEST`赋值，而跑器在该变量缺省时把`examples_manifest.txt`作为第二趟附加进来（`tests/e2e/run_e2e_tests.py:285-294`），44条目今天就随这两条腿各跑一遍（合并批台账按2157＋44＝2201的条目账核对过该形态；那是合并批当时的清单口径，其后的两条新增与一条改名使现清单为2158行，两笔账差不矛盾）。于是示例面面对的不是「无载体」，而是「D-9第3类要求它退出每轮、它现在却在T1里」——处置见D-7末段的e2e侧机制。

本版另立**载体闭合**通则：`类别`≠`常规`的每个条目必须被至少一条T2腿实际跑到，按该腿真正消费的条目集合核对（含`-E`/`-R`过滤结果与跑器的示例第二趟），违者由守卫十一判红。「登记在哪棵树上」与「收口批会跑它」是两件事，两文都不管就静默漏跑——性能类今天的处境就是这条通则的反例。要更长的长跑（工作量系数>1）放专门环境按需跑，不在收口批付费。普通开发阶段不跑性能类。

`nd_resolve_stress_tests`（浸泡）与`mnist_mlp_run`（示例验收）是「慢的功能测试」或「演示验收」，仍是功能面——不得用「慢」冒充「性能」把正确性覆盖一起跳掉。

这一分离在仓内已有先例：`regex_redos_{compile,run}`这对正确性条目早已把墙钟断言摘掉，注释的理由与本文一致——「三棵树跑同一个带墙钟帽的fixture就是拿机器负载下注」，并记下2026-11-20的47584毫秒越45000毫秒帽事故，只留300秒兜底帽（`:3040-3051`、`:3066-3073`）。同一注释还记下ASan相对Debug只有约1.76倍（空机171.9秒/302.7秒，`:3045-3046`），说明连同一族在不同构型间的倍率也远不是常数，与F-2一致。D-2做的就是把「断言不依赖墙钟、帽只兜挂死」这一取向从单条目推广到全部条目。

守卫：性能类成员用**配置期差分**核对——在`NLANG_PERF_TESTS=ON`与`OFF`下各configure一次（只configure不构建，差分居独立scratch目录算、不碰扫荡树缓存），两次`ctest --show-only=json-v1`的条目名差集必须等于参考表中`类别=性能`的行集合（这些行登记在D-3新增的发布扫荡树`ctest-Release`构型下），且T0/T1的任何腿都不跑这些条目（守卫八；名集合同时进除`T2-perf`外每条ctest腿的`-E`，即上段树复用的结清手段）。不采「grep毫秒字面量」那种谓词：`waitFor(pred,5000)`的5000、Qt的105处`QTRY_*`默认5秒界与25处`qWait*`都是内建毫秒值，可按D-12第4条它们是「放弃阈值」而留在常规轮——按字面量标注会把整个并发族与Qt族赶出每轮，按语义标注又机器核不了，只剩注释维护。残余风险（某条常规条目偷偷断言墙钟）由D-12第3、4条的判据纪律加advisory grep兜：grep只告警不判红，判红只落在配置期差分这类可核事实上。

**D-7 排期轴：慢的功能条目移出每轮，但必须可回补、可核对。** 慢集成员**登记在参考表的`类别`列**（每构型×条目一行一标注，见D-3），而不是`tools/gate_tiers.txt`——后者的选择器宇宙是e2e清单的条目名、语义是「包含」（`tier <腿名> selector <正则>`，且要求每条清单行至少被一个选择器命中），既装不下ctest条目名宇宙，也与「排除」语义相反，硬套会逼出双重否定。腿按该列派生`-E`正则：T0与T1的**四条**ctest腿（`tools/gate_tier.sh:194`的T0-unit、`:164`的T1-debug-unit、`:166`的T1-ide-ctest、`:167`的T1-asan-unit）排除该构型下类别≠常规 的条目；T2的复用形态不带这层按`类别`的排除（`:214`复用四条腿，T2内不带`-E`才是ctest慢条目逐构型的载体闭合，守卫十一）。perf名集合的`-E`各腿在哪个层都带（D-6的树复用段），与类别排除互不冲突：perf条目的载体是`T2-perf`自己。标记规则机器可核，避免「谁顺手标一下」：参考秒数> `SLOW_MIN_REF_S`（300）的条目必须标`慢功能`，或在其参考行的`理由`列写明「为什么它仍留在每轮」；演示验收类不看耗时一律标（它退出每轮的理由是性质而非耗时）。

例外行不是「先挂着」的挡箭牌，准入标准只有一条：`理由`必须证明**按D-9通则已无可削的工作量**——轮数已按构型给到断言面下限、耗时来自构型性质（消毒器开销、真窗口焦点链）而非重复。削得动却没削的条目，处置是削工作量而不是登记例外；写不出这条理由就标`慢功能`走甲/乙回补。

「例外表规模不可预估」的担忧本轮已可钉死：三棵树里实测超过300秒的ctest条目只有三条——`nd_resolve_stress_tests`（ASan 1178.8秒，D-8按构型给轮数后约177秒，落到阈值之下）、`mainwindow_tests`（ASan 589.1秒，按D-7在ASan构型标慢功能）、`threads_tests`（ASan 305.53秒，Debug 70.57秒、IDE 70.35秒）。本轮唯一需要「仍标常规」理由行的ctest条目因此只有`threads_tests`一条，理由形态现成：并发族各用例一遍即断言、无重复轮数可削，ASan对Debug的4.33倍（305.53/70.57）来自消毒器开销而非工作量。登记处注释里的旧读数不能充当本轮参考：`:3045-3046`的Debug 171.9秒/ASan 302.7秒（约1.76倍）是2026-11-14的样本，且当时fixture里还挂着45000毫秒内建帽（同注释记下11-20那次47584毫秒越帽之后已摘掉）；本轮实测是Debug 55.19秒、ASan 147.65秒（2.68倍），`regex_redos_run`因此落在阈值之内、不需要例外行。两处数字都被本轮实测取代，第十节把该注释列进同步面、由参考表当真源。

ASan构型不排除`nd_resolve_stress_tests`是对本文初稿的改判。初稿把它在ASan轮标成慢功能（100轮约589秒），理由是「该腿只在改动触及内存风险族时才付费，而那些族（stabilizer/concurrency/serialization）已覆盖它猎的所有权与容器路径」——这条理由站不住：族口径覆盖的是那些路径的**功能面**，而本条目提供的是无法替代的那一维——在**看得见**所有权错误的构型下反复撞它。把soak从消毒器构型移出，等于让唯一能当场定位该缺陷的构型不做压力，Debug构型的soak只能撞见消毒器也无能为力的那部分。代价按D-9规则2用轮数收（ASan当场即报，不必靠重复放大窗口；Debug无消毒器，轮数保持100），而不是按排期移出。

回补规则：慢条目退出的是「每轮都跑」，不是「改动命中时也不跑」。每个慢条目必须有甲乙之一的**可核对**回补路径，两者都没有即守卫六判红：

- **甲（族回补）**：在`tools/test_families.txt`有族归属——该族的src规则覆盖它所测的源码，且其`unit`片段（ctest条目名正则）或`e2e`片段（清单条目名正则）命中该条目名，于是T0的影响映射（`tools/test_impact.py`，输出`unit <regex>`/`e2e <regex>`）命中该族时该条目回到本轮。当前该文件里没有tensor族，`mnist_mlp_compile`/`mnist_mlp_run`（都是ctest条目，`tests/CMakeLists.txt:3008-3016`）因此无人认领；须补一条tensor族，src为`src/native/tensor/**`、`stdlib/tensor.n`与`examples/mnist_mlp/**`（都是现存路径；此前草案写的`src/vm/native_tensor*`不存在，属幻影glob，守卫九拦的就是这类），`unit`片段取`native_tensor|mnist_mlp`。
- **乙（例外行认领）**：没有合适的窄族时，在参考表的例外行里用`理由`列写明「它退出每轮后由哪些本轮会跑的条目覆盖」。

甲路径有一个必须写死的交互：映射命中该族时腿命令会同时带`-R <映射并集>`与`-E <慢集>`，而ctest里排除优先——F-12实测`-R alpha`跑两条、再加`-E alpha_one`只剩一条。两个旗标一起挂会把回补静默抵消。规则是先从慢集里减去本轮被映射命中的条目名，再拼`-E`。

`nd_resolve_stress_tests`两构型都留每轮，因此它既不需要甲也不需要乙——它退出每轮的从来不是排期，而是强度（200轮→Debug 100轮/ASan 30轮）。它也不进任何族：影响映射的保守语义是「未映射→回退全量Debug单测」（`tools/test_impact.py:5-6`），该文件的curation规则同样写明覆盖面宽的叶子不配族、正是为了让T0回退全量单测（`tools/test_families.txt:4-7`）；给它配一条窄族反而把「少跑」变成「只跑窄族」，覆盖净减少。甲乙两路径与`理由`列都落在入仓文件里、空即红，「少跑」因此不是口头承诺而是可判红的核对。

Qt界面族在ASan单测腿的排除出自2026-11-20 T1提速批实施计划的D-7裁决（裁决：T1的ASan单测腿优先排除Qt/qtest界面族，T2的ASan全量腿承接）。那份计划文档（`docs/superpowers/plans/2026-11-20-t1-gate-speedup.md`）按仓规本地独占、不入库，裁决内容在此完整重述，作为上表依据列的出处。该排除今天在代码里还不存在：`tools/gate_tiers.txt`没有覆盖这四条的选择器，`tools/gate_tier.sh:98-99`的ctest腿也不带`-E`，同腿的实测日志里`mainwindow_tests`以589.15秒通过、其余三条都在5秒内；提速批落地时它的形态先是`gate_tiers.txt`的慢集选择器。本文不重开裁决本身，只改它的**登记位置**：排期成员的唯一真源是参考表的`类别`列，因此该族在ASan构型的行标`慢功能`、Debug与IDE构型的行仍标`常规`——该列本就按构型×条目分别标注，正好表达「只出ASan腿」这一形态；提速批若先落地，本文实施第4步把该族从选择器迁进该列并撤下选择器，否则由该步直接登记。两处各存一份成员清单必然漂移，这正是本文D-7把慢集从`gate_tiers.txt`移开时用过的同一个理由。该裁决自身的代价记在第十一节风险行：该族的内存面发现从T1的ASan腿移到T2。

**e2e侧的排期机制是清单子集化，不是跑器旗标。** 跑器按清单逐行跑，没有`-E`这类排除入口；仓内已有的两处先例都是「派生临时清单＋`NLANG_E2E_MANIFEST`」——`tools/gate_tier.sh:198-199`的T0子集与`:125-126`的ASan子集。三条规则据此定死：

- **排除**：按`类别`过滤只发生在T0的派生e2e子集（`tools/gate_tier.sh:205`，它本就是派生物）；整份清单形态的三条腿（`:165`的`T1-debug-e2e`、`:215`的`T2-asan-e2e-full`、`:219`的`T2-release-e2e`）**一律不按`类别`过滤**。理由是载体闭合按`(构型, 条目)`配对（守卫十一）：三条全扫腿在e2e宇宙里分别是Debug、ASan、Release的唯一载体，若某构型的唯一腿再把该构型标了`类别`≠常规 的行排除掉，那些行在该构型就没有载体、守卫十一判红。排除规则与载体规则互相顶，标注动作本身就不可排期。具体的触发点离阈值只有一步：`stdlib_regex_size`本机实测293–297秒（F-10），`SLOW_MIN_REF_S`是300，一轮记录抖动就能把它推过阈值；按本条规则，标注结果不再改变任何腿的形状，那条Debug行安心标常规。示例面退出每轮同样不走`类别`列：T1腿改设`NLANG_E2E_MANIFEST`为**整份`manifest.txt`**，跑器一收到该变量就不再附加示例第二趟（`tests/e2e/run_e2e_tests.py:289-294`）——示例面按性质退出（D-9第3类），不按耗时标注。这条限制的代价要写明：e2e慢条目只从T0轮次排除、按映射命中回补，T1的全扫e2e腿照跑它们；e2e侧的墙钟收益来自分片（`docs/dev/gate_tiering_design.md`的既定设计），不来自类别过滤。不在跑器里加排除旗标的理由与ctest不用标签同型：排除集每轮随影响映射与构型变，派生文件是现有管线里唯一有先例、且守卫能按同一算法复算的形态。
- **回补**：T0的e2e子集本就是派生物（`:205`），组合式与ctest的「先减慢集再回补」等价——本轮行＝「`类别`=常规的行」∪「映射输出的`e2e`正则命中的行」，按清单原序去重。慢条目因此仍满足甲/乙回补要求，守卫六对e2e宇宙按这条式子核对，不需要模拟跑器内部。
- **载体**：T2腿真正消费的条目集合按同一算法算，且全扫腿没有第二种形态（上一条已定：不按`类别`过滤）——不设`NLANG_E2E_MANIFEST`的腿＝`manifest.txt`＋`examples_manifest.txt`两趟，设了该变量的腿＝那份文件。守卫十一按`(构型, 条目)`配对：e2e腿的构型取腿命令行显式携带的`--config`参数（D-3），仅按条目名集合对上不算，构型没配对的同名条目不构成闭合。示例面的收口载体是`T2-release-e2e`，且它是唯一消费示例趟的腿：`T1-debug-e2e`设整份清单变量后示例趟退出，ASan腿今天就不跑示例趟（`:215`显式设了清单），本版不改这一点——示例断言的是「跑通一个真实程序」，其内存面由所属功能族在ASan腿覆盖。`examples_manifest.txt`的清单行因此只在`e2e-Release`构型登记参考行，`e2e-Debug`与`e2e-ASan`不设那些行：没有腿消费它们，硬登记反而是守卫一的多余行。守卫十一按这些集合核载体闭合（D-6）。

**D-8 强度轴：工作量系数。** 重复/浸泡类用例的本轮工作量按`参考工作量 × NLANG_TEST_WORK_FACTOR`计算（缺省1，**校验须拒绝小于1**——小于1意为「跑得更少但帽不变」，会把覆盖缺口伪装成提速）。系数由人经环境变量给，不进构型表、不进命令行（同一份语料在专门环境里换个环境变量就是另一档强度，无需第二套用例）；换档之后ctest形态须重新configure那棵树，让看门狗跟着系数走（D-2），守卫五核对不一致即红。帽的线性项吃这个比值，因此系数调大不会把自己的帽顶破——这正是把线性项写成「工作量比」（以条目自身单位计：轮数、条数）而不是「倍率旋钮」的原因：构型基线轮数与性能系数都能抬工作量，帽跟着抬，二者不会互相伪装成回归。

两件事必须写清，否则「按构型调轮数」没有落点。**谁来给工作量**：构型基线由登记处给——`tests/CMakeLists.txt:1646`已按`CMAKE_CXX_FLAGS MATCHES "fsanitize=address"`区分消毒器树（ASan默认帽家族正靠它），同一分支给该条目的`ENVIRONMENT`设`NLANG_TEST_ROUNDS=<该构型的例行轮数>`；强度系数由人经`NLANG_TEST_WORK_FACTOR`给。二者相乘即本轮工作量。读不到环境变量时的回落值必须是真正可跑的正确数字（缺省即该条目的无消毒器例行值），不能回落成0轮或1轮那种「看起来通过」的形态。**谁来核对**：不靠约定，靠自报——被测物必须把本轮实际工作量打印出来（`rounds=30`一类），判定侧断言「实际工作量 == 参考工作量 × 系数」，不符即红。预算与帽都跟着工作量走，因此只有自报值能揭穿「设了系数/轮数、被测物没读」这类静默失效——它正是把覆盖缺口伪装成提速的那条形态。守卫五的桩条目探针验的就是整条链路：系数翻倍→自报轮数翻倍→预算与看门狗帽同步翻倍。

`nd_resolve_stress_tests`的具体裁定：例行轮数200→100（Debug构型；ASan构型经`NLANG_TEST_ROUNDS`取30，机制见上节），六形态轮转的覆盖面不减（`tests/test_vm/test_nd_resolve.cpp:411-451`每轮都对六个3–4行源逐个`buildSource`并`CHECK`诊断文本，判定逐轮成立、与墙钟无关）。轮数唯一的用途是提高撞上被弃`ConcreteParamList`所有权错误的概率（该文件注释自陈），而ASan在错误发生当场即报，不需要用重复放大窗口。实测代价按构型分别折算（线性外推自200轮的195.3秒与1178.8秒）：Debug取100轮约98秒（占T1-debug-unit 552.55秒的35.3%→17.7%），ASan取30轮约177秒（占T1-asan-unit 3656秒的32.2%→4.8%）。ASan轮数低于Debug是D-9规则2的要求（消毒器当场即报，不需要用重复放大窗口），不是省时间时顺手砍；两构型的轮数各写进自己那行的`参考工作量`列（D-3）。

**D-9 功能类工作量通则：按「该用例断言什么」定工作量。** 三类性质对应三种工作量口径，登记处注释须写明属于哪一类：

1. 断言确定性质（拒绝某诊断、算出某值、给出某诊断文本）：一遍即可，重复不增加覆盖；
2. 撞非确定性缺陷（所有权、释放后使用、竞态）：轮数只为提高撞上概率，在消毒器构型下应显著低于无消毒器构型（当场即报）；竞态族另按既有裁定独立压测百次以上，不由每轮soak冒充；
3. 演示与验收型程序（`examples/`下）：不进每轮。它们断言的是「整套语言与标准库能跑通一个真实程序」，覆盖广而单一，回归面靠单元族与e2e族兜；需要时作为examples跑，收口批覆盖。`examples/mnist_mlp/main.n:30`的`epochs = 40`与README里冻结的准确率基线因此**不削减**——示例本体是随包发行的教学与验收材料，削减它是为了迁就测试排期而牺牲示例价值，方向错了。

张量运算本身的正确性覆盖不在mnist里：真源是`tests/test_native_tensor/`下按SIMD分派的条目（三构型均登记，且在F-1的无帽清单里），本文给它们补参考行后即有预算与看门狗，并由D-7的tensor族回补规则覆盖。

## 六、去锁与互斥

**D-10 删除门禁机器测试锁。** `tools/gate.sh`的测试锁认领/释放/陈旧接管/等待行（`acquire`/`release`/`sweep_stale`/`wait_round`与`holder_*`）整套删除，`--shared`旗标同时删除（它存在的全部理由是「只构建不测量所以可以并行」，锁没了这个区分就没了）。F-7已核对：三条锁理由中`%TEMP%`与焦点链两条已作废或无载体，「计时敏感」有载体但由D-12第4条按三类分别处置，不再有赖于「整台机器串行」。保留的机制只剩写目录/资源claim家族（`norm_path`/`wdir_key`/`derive_write_dirs`/`acquire_wdirs`/`release_wdirs`），改名为按资源名认领，`LOCK `行文案与判决行纪律不变（`LOCK`前缀永不与判决行混淆这一条是有价值的，保留）。

**D-11 保留具名资源互斥，两层各管各的范围。** 跨会话（两个worktree两个会话）之间靠门禁层的具名claim；ctest的`RESOURCE_LOCK`经实测只在**单个ctest进程内**互斥、跨进程完全重叠（F-11），且文档从未把跨进程范围写成承诺——所以两层都要，各管各的层，且任何跨会话的互斥需求一律走门禁层claim，不得挂到`RESOURCE_LOCK`上。本版登记两类资源：

- `nide-gui`：真起窗口且带焦点/`QTRY`断言的界面族条目加`nide_deploy_check`共9条：`mainwindow_tests`、`editor_tests`、`dialogs_tests`、`syntaxhighlighter_tests`、`compilelogbrowser_tests`、`runerrorbrowser_tests`、`terminal_tests`、`searchpath_integration_tests`、`nide_deploy_check`（实测`mainwindow_tests` ASan 589.1秒，其余各<40秒）。口径按各测试文件的main形态（是否真起窗口`QApplication`）实测划定，不按宏名划：`mainwindow_tests`根本没有`QTEST_MAIN`，`:4331-4338`是镜像`QTEST_MAIN`控件分支的自定义main（QtWebEngine要先设`AA_ShareOpenGLContexts`），按「main宏」字面划线恰好会把最该挂锁的这条划出去。这9条都起真窗口（`QTEST_MAIN`或上述自定义main），而`recentstore_tests`、`settingsstore_tests`、`debug_client_tests`、`projectmodel_tests`、`searchpathargs_tests`、`solutiontreemodel_tests`、`debug_protocol_tests`用`QTEST_GUILESS_MAIN`——无窗口即无焦点链，不进该锁（`test_projectmodel.cpp:1485-1488`与`test_searchpathargs.cpp:87-89`的注释还说明为何必须用GUILESS）。清单以条目名逐条声明，不写正则——写正则会让「新加一条界面条目没进锁」静默发生。
- `build-dir:<规范化目录指纹>`：同树不同配置的并发重建会抢同一份`CPackConfig.cmake.tmp`，这是v0.13.8收官批的实测事故（`docs/dev/gate_write_dir_lock_design.md`一）。

claim必须在**腿组装层**声明，不能指望从命令行推导：四条ctest腿都写成`cd <tree> && ctest -C Debug`的shell串（`tools/gate_tier.sh:98-99`），`derive_write_dirs`看不到任何路径。同理，并发的e2e腿必须在组装层按分片标签声明自己的scratch资源——跑器已支持`NLANG_E2E_SCRATCH_TAG`按标签分目录（`tests/e2e/run_e2e_tests.py:127`，2026-11-20 T1提速批Task 1），资源层按同一标签认领才能把「分片互删scratch」这类冲突也归因到`LOCK`行。

**D-12 前置根治：先去真实互斥，再谈并行。** 五件事必须先做完，否则去锁只是把冲突从「锁挡住」变成「偶发变红」：

1. `test_mainwindow.cpp:611-617`的org/app钉死（F-8）改成按构建树派生，做法照`tests/CMakeLists.txt:44-51`的scratch token——同一份测试代码在两棵构建树里读不同键名。不这么改，`nide-gui`锁就必须覆盖`nide_deploy_check`与IDE腿的每一次跑，去锁收益当场折掉一半；
2. **13条ctest条目的scratch环境被覆盖**（F-7）：包装函数设的`TMP`/`TEMP`被后续`set_tests_properties(... ENVIRONMENT ...)`整体冲掉。修法是用一个合并环境名的辅助函数统一设属性（把scratch的`TMP`/`TEMP`与其它条目自有变量合并成一份），而不是在每个调用点手工重复一遍——手工重复正是这类覆盖事故的成因。不修，这13条并发时会共用同一个`%TEMP%`；
3. `tests/test_vm/test_net_scheduler.cpp:142`的`CHECK(steady_clock::now() - t0 < 1500ms)`改成不依赖时间的断言（等条件成立再断言状态/顺序），而不是给它读标量——读标量等于承认「这个断言的正确性取决于机器快慢」，那正是2026-11-14裁定否掉的方向。这条改写需要一个可观察钩子，不是一行机械替换：现在的`WaitUntilRunnable`（`:32-39`）只轮询`state==Runnable`，而「非到期唤醒」这一性质今天恰恰只能靠墙钟区分。因此要么给调度器暴露唤醒原因（定时器到期／外部唤醒／虚假唤醒），要么明确降级判据并接受丢掉「非到期唤醒」这一维——降级须在实施计划里写明丢掉了什么性质，不得静默；
4. **有界等待的三种时间用法分开处置**：`test_gcworldstop.cpp:47`的`waitFor(pred, timeoutMs)`被14处`CHECK(...)`当判据用（第3条同型的墙钟依赖，F-7），`tests/test_nide/`的105处`QTRY_*`与89处`QSignalSpy`等待面。裁定分三类，前两类是二分：

- **判据**（条件最终是否成立、事件顺序是否正确）不得依赖时间——改成条件等待，挂死交给看门狗；
- **放弃阈值**（等多久就不再等、把挂死报成失败）本质是预算而非断言，读机器标量；标量缺位时按`SCALE_BAND_MAX`换算，与D-2的预算回落同条规则，不另立「常量地板」这种会漂移的第二口径。

这两类同时满足2026-11-14裁定与本设计：判据在任何机器上同结论，阈值只决定「多久放弃」。台账「QTRY超时须改读scale」这条前置项（`.superpowers/sdd/2026-11-20-t1-gate-speedup/progress.md:24`）在成文时被静默丢掉，此处恢复并按上述口径细化。Qt侧还有一处落点必须先做：`QTRY_*`的5秒界内嵌在Qt宏里，105处调用点没法逐点传参，所以得先写一个读`NLANG_GATE_MACHINE_SCALE`的项目本地等待封装，再逐点替换——实施计划里这两步分开登记，否则改动面会被低估成一行。

第三类是**判据的形式是顺序、但被测性质本身是时序**的条目，两分法套不住它：`test_threads.cpp:3820-3861`的错峰测试断言的是输出序列的先后（`p0<p1<p2`、`pb<p2`，`:3854-3859`），形式上与墙钟无关，可它依赖的激励是50/150/250毫秒的睡眠与20000次忙循环的比例关系，登记处注释（`:3810-3819`）自陈窗口按机器负载手工放大、靠「忙循环与睡眠窗在负载下同向缩放」才成立。它既不是放弃阈值，也改不成条件等待——「给定CPU供给下定时器按截止时刻先后醒来」就是被测内容本身。裁定给第三条路：激励窗口按机器标量换算（与预算同一个源，D-5），条目在参考表登记例外行、`理由`列写明「时序敏感：判据依赖激励窗口的相对比例」，失败文案把这条理由一并打出来，使红灯自带归因而不是伪装成「你的改动坏了」。这是本文唯一允许时间进入判据链的形态。可程序化的部分是登记面：凡带「时序敏感」标注的条目必须有带理由的例外行（守卫六），参考表里没有该行的条目不得声称时序敏感；「判据是否真的依赖时间」属代码评审判据，不伪造成grep守卫（同D-6末段对谓词可判定性的口径）。本文勘察到的这类条目只有`test_threads.cpp`这一处（`tests/test_vm/test_stdlib_concurrency.cpp:5`的文件头注释自陈其断言只用顺序与终值，属第一类），代价要说明白：该条目在极端争用下仍可能翻红，因为被测性质依赖CPU供给，这一残余消不掉，只能显式登记并交D-15人判；
5. ICMP回显ID一条**已结案、无需改动**：ID由操作系统管理（F-8引证），门禁形态下两条相关条目并发不会互相错认应答。曾按「未取证→保守挂锁」处理，现按取证结论撤销该保守假设。

**D-13 争用优先用调度消解，不用算术掩盖。** 同层条目互抢产物目录、共用默认CWD、共用注册表这类冲突，解法是给独立产物目录、显式`-o`、`-p no:cacheprovider`、资源锁与并行度旗标（F-9的CTest官方立场）；把预算乘大来吸收争用是掩盖问题，会把真实的串行下限藏起来。算术缩放只用于一维：同一份工作在这台机器上需要多久。

## 七、失败语义

**D-14 超时就是失败，不自动重试。** 两种超时文案（D-2）都判FAIL。`--repeat after-timeout:1`只允许登记在**已取证的偶发条目**上，登记处须写明证据（哪一轮、哪个条目、原始日志路径），不得作为通用护栏——重试会把「稳定的慢」变成「看不见的慢」，并把覆盖成本翻倍。lit对失败/超时条目在耗时档案里记负数（F-9）正是同一考虑：污染历史数据的样本不能当好数据用。

**D-15 参考值只降不升。** 实测低于`参考×SAFETY_MULTIPLIER/2`时advisory建议下调参考；实测超预算而确认是真实慢化（改动确实更重），处置是人改参考行并在提交信息写理由，而不是在代码里加临时倍率。这条棘轮防止参考表被一次次「顺手放宽」磨成没牙的守卫。

参照对象要按原始出处说清差别，否则会误以为本仓在照抄Bazel：Bazel的`--test_verbose_timeout_warnings`文档明说它「does not affect a test's timeout value, merely warns」，其触发与建议比例只在源码`TestTimeout.java`里（低于下一较短类别帽的一半建议换更短类别、达到本类别帽的90%建议换更长类别），也就是说**它的建议是双向的**，放宽同样会被建议。本仓选择「只降不升」是对该形状的有意收紧，理由独立：参考行入仓即是团队契约，收紧不需要理由、放宽必须带提交信息与理由（F-9复核清单）。同理，本仓不采纳Bazel那条advisory与实际帽脱钩的缺陷形态（#12411）：advisory必须读判决所用的同一个数（D-5）。

## 八、可程序化守卫

全部落在`tools/tier_coverage_check.py`（扩到ctest与参考表两个宇宙）、新脚本`tools/gate_time_check.py`与`tools/gate_tier_test.py`的腿命令串桩断言，语料与既有条目同形、注册进ctest：

1. **参考完备性**：三树`ctest --show-only=json-v1`的每个条目、两份清单的每条条目，在所用构型下必须有参考（`default`行或例外行）；缺即红。「所用构型」不是声明，从消费腿集合派生：ctest条目按消费它的腿的构型各登记一套行（三棵判定树对应`ctest-Debug`、`ctest-IDE`、`ctest-ASan`三套；`T2-perf`对应发布扫荡树的`ctest-Release`构型，它除该腿`-R`结果（perf名集合）外还有第二个消费者——开跑前的标量校准（D-4的哨兵集合），故按两个集合的并集登记行，D-3）；清单行按真正消费它的e2e腿的构型登记——`examples_manifest.txt`的行只在`e2e-Release`登记（唯一消费腿是`T2-release-e2e`，D-7载体段），其余清单行在`e2e-Debug`、`e2e-ASan`、`e2e-Release`都登记。构型键一律带宇宙前缀（D-3），两侧的行不会因条目与清单行将来撞名而互当多余或缺失；与该派生集合不符的多余行同样判红。派生集合里的「D-4的哨兵集合」以参考表`哨兵`列的标记为输入，每个参与标量校准的构型必须有5–8条标记行（D-4的选型规模），缺即红——否则清空`哨兵`列就让并集收缩成perf名集合、差集依旧为空，本守卫会真空放过「该构型根本没有哨兵行」的退化态，把校准腿的缺输入留到运行期才暴露。
2. **孤儿行**：参考表里不得有清单/树里已不存在的条目名（改名即失效可见，与`tier_coverage_check`的dead selector同型）；perf条目的存在性按`NLANG_PERF_TESTS=ON`形态的枚举核对（守卫八差分的ON侧），不得按三棵判定树的枚举判孤儿——那三套清单里本就没有它们。
3. **棘轮**：本轮实测超预算而未登记例外行的条目红；低于半预算报advisory（不红）。
4. **标量带门**：校准结果出带即该腿红，文案给出应重录参考的构型与本轮实测候选行。
5. **工作量一致性**：参考行必须带参考工作量与测量形态；本轮系数≠1时，帽必须由同一个函数计算（D-5）；系数<1判红（D-8）；每条目的自报实际工作量必须等于`参考工作量 × 系数`，不符即红（D-8的自报口径，同时拦「系数或构型轮数没被被测物读」）；并断言该树中属于该构型派生集合（守卫一口径）的每个条目的`TIMEOUT`等于它的**看门狗帽**，即`max(参考秒数 × 本轮工作量比 × WATCHDOG_MULTIPLIER, MIN_WATCHDOG_S)`——D-1那条含地板的公式，不是少了`max`的裸积：被地板顶住的条目会在裸积等式下误判红（D-2）；系数抬了却没重configure同样在这条等式下现形，处置见D-2。探针：构造一条耗时线性于轮数的桩条目，其参考秒数必须大于`MIN_WATCHDOG_S ÷ WATCHDOG_MULTIPLIER`＝12秒，否则看门狗帽恒被120秒地板顶住、翻倍探针看不见帽的变化；在`NLANG_TEST_WORK_FACTOR=2`下重新configure桩树，断言其自报轮数、预算**与看门狗帽**同步翻倍而不是判红（ctest形态没有运行期旋钮，系数只从配置进来，F-4）——这一条专门拦Bazel #12411型错误与D-1的漏项。
6. **慢集回补与口径**：`类别`列≠常规 的条目必须有甲路径的族归属（该族src覆盖它所测源码、`unit`或`e2e`片段命中该条目名）**或**乙路径的`理由`认领，两者都没有即红；回补还须实测：守卫把腿将要用的那对`-R`/`-E`原样交给`ctest --show-only`（实测它按真实筛选语义出清单且不跑任何测试），断言该慢条目在输出里——「实际会跑＝`-R`命中－`-E`命中」这条等价式因此是ctest自己算的，守卫不复制筛选次序，F-12的`-R`/`-E`相消正好在这里被拦；e2e宇宙按D-7末段的集合式复算派生清单，同样不模拟跑器内部；参考秒数>`SLOW_MIN_REF_S`而仍标`常规`的行，`理由`列为空即红；`--record`后`类别`、`参考工作量`、`哨兵`与`理由`四列不得丢失（守卫比对重录前后的人工标注列）。
7. **倍率自洽**：断言`WATCHDOG_MULTIPLIER > SAFETY_MULTIPLIER × SCALE_BAND_MAX`（预算先于看门狗触发）、`MIN_WATCHDOG_S = 2 × MIN_CAP_S`、对参考表每行断言看门狗帽>预算（clamp不得下界大于上界）、以及`MIN_CAP_S > 哨兵条目最长实测`（否则哨兵自己被自己的帽杀）。
8. **类别守卫**：性能类成员以**配置期差分**为准——独立scratch目录在`NLANG_PERF_TESTS=ON`与`OFF`下各configure一次（只配置不构建；不得借发布扫荡树做差分，那棵的缓存已被`T2-perf`置ON，差分在它里头配OFF会与腿互相干扰，反之亦然，D-6树复用段），两次`ctest --show-only=json-v1`的条目名差集必须等于参考表中`类别=性能`的行集合——那些行登记在D-3新增的发布扫荡树`ctest-Release`构型下，`T2-perf`腿的预算输入正是它们；这个差集同时就是各ctest腿`-E`里perf名集合的唯一来源（scratch目录算出、与参考表无关：perf行缺参考也不会漏进别的腿）。再断言这些条目不出现在T0/T1任何腿的实际条目集合里（按守卫六那条`--show-only`等价式算；`-E`恒带名集合后这条结构上成立，它实际拦的是`-E`漏带该集合）。grep毫秒字面量只做advisory不判红——谓词不可判定的理由见D-6末段。
9. **族选择器非空**：`tools/test_families.txt`每个族的src选择器必须至少命中仓库里一个现存文件（幻影glob当场判红，D-7的tensor glob教训）。
10. **计时口径一致**：判定所用的实测口径（并行度、`--repeat`）必须与参考行的`测量形态`一致，不一致判红并提示重录。
11. **载体闭合**：参考表里`类别`≠`常规`的每一行必须落在至少一条T2腿实际消费的条目集合里，并按`(构型, 条目)`配对：ctest腿的构型取它跑在哪棵构建树连同`-C`（F-1：三棵树的判定腿都跑`-C Debug`，单看`-C`分辨不出树），e2e腿的构型取命令行显式携带的`--config`参数（D-3），两侧都换算成参考表的带宇宙前缀构型键（前缀由腿的类型给出，`--config`的参数值本身不动）；仅按条目名集合对上不算，构型没配对的同名条目不构成闭合。`--config`的值取判定构型三值之一，与`e2e_leg`今天拼工具路径用的构型参数是两回事：ASan腿的二进制仍取自`/Debug/`（D-3已证两条路径同形），照抄路径形态会把ASan行配成Debug行计价，正是F-2的4.83×。条目集合的计算：ctest腿按守卫六的`--show-only`等价式（含该腿的`-R`/`-E`与树/`-C`——T2复用形态下四条ctest腿不带类别`-E`、只带perf名集合的`-E`，见D-6与D-7），e2e腿按D-7末段的清单集合（`T1-debug-e2e`在T2里消费的就是整份`manifest.txt`，示例趟只随`T2-release-e2e`进来）。桩烟测另钉三件事：`T2-perf`的命令串含`-DNLANG_PERF_TESTS=ON`与`-C Release`；四条ctest腿都带perf名集合的`-E`（ON缓存树下`-C Debug`的清单靠它滤净，D-6树复用段）；每条e2e腿都带显式`--config`（缺它本守卫的构型配对没有输入，从二进制路径猜构型只是把F-10的「旗标改判决」搬进「路径改判决」）。缺载体即红：`类别`列登记的只是排期意图，不保证真有人跑它（D-6通则，性能类今天的处境就是反例）。

## 九、实施顺序

前提与依赖按下列顺序，标「前提」的步骤不做完后面的步骤没有数据源：

0. **前提：e2e跑器记录逐条目耗时**（F-5）。跑器为每条目输出耗时并支持`--record`产出参考行；没有这一步，参考表的e2e构型无从生成，预算判定也无输入。
1. 参考表与`--record`：三树＋perf构型＋三e2e构型各录一轮实测（perf构型是在装有Release二进制的构建树上以`NLANG_PERF_TESTS=ON`跑那两条perf条目加按D-4选型标准挑出的5–8条哨兵（哨兵在`-C Release`形态与perf同趟顺带跑，给`T2-perf`腿的标量校准以参考来源，D-4）——登记-only零重编译，D-6；参考表入仓、一次录制全员共享，无Release二进制的机器不必补录。各轮须在门禁锁内、按当时代码的默认并行形态录，并把该形态写进`测量形态`列；并行形态定了以后重录一次），人工定各构型的`default`、例外行与`类别`列，并按D-3的两种必填情形填`理由`列，哨兵条目按D-4的选型标准挑5–8条并登记。**跨机实测也在此步**：至少两台机器各录一轮同构型，比较逐条目倍率分布（D-4的假设检验）。
2. 标量校准与带门：按**每条腿**将要用的并行形态现采哨兵（D-4，本版不做跨腿复用）、发布`NLANG_GATE_MACHINE_SCALE`、出带判红并给候选行。
3. 消费点接线：`tests/CMakeLists.txt`按参考表派生`TIMEOUT`（删除`nlang_add_qtest`处手抄的2.7x-8.7x注释，`:1634`）；`tools/gate_tier.sh`的ctest腿改为跑完按junit逐条目耗时判预算；`tests/e2e/run_e2e_tests.py`与`tools/qtest_progress.py`改内联判预算（跑器的`TIMEOUT_SEC`常量与`/Debug/`乘3分支被公式取代，F-10的「旗标改判决」现象随之消失。这句只对门禁腿成立：腿显式传构型（D-3）、给标量（D-4），判决与帽读同一个数。裸调用的构型与标量都按D-2的缺位回落走：构型按二进制路径猜并在文案里写明猜测，标量取`SCALE_BAND_MAX`。因此裸形态的预算并非一律比今天的定值90秒宽松：带宽倍率4×2＝8之下，参考秒数低于11.25秒的条目预算落在90秒以下（低于7.5秒的还被`MIN_CAP_S=60`的地板钳到60秒），反而比90秒更早失败。这不是回归而是口径从「拍」换成「派生」的必然结果，失败文案必须注明「未做本机校准」来交代这一口径）；ctest命令的`--timeout`退为兜底默认，只在参考表尚未补齐的过渡期起作用——守卫一补齐后就不该再有**被消费**条目靠它兜底（被消费口径就是守卫一的派生集合；扫荡树里按并集口径不设行的条目不被该腿消费，本就没有行可缺，D-3）。
4. 工作量与排期归位：`nd_resolve_stress_tests`的例行轮数改由登记处按构型给（`NLANG_TEST_ROUNDS`，D-8）并由被测物自报；慢集成员由参考表`类别`列表达（不进`gate_tiers.txt`，理由见D-7），Qt界面族的ASan排除在该列登记（D-7末段：该排除截至本文撰写尚未进码，提速批的选择器形态若先落地则从它迁入该列并撤下选择器，否则由本步直接登记）；`tools/test_families.txt`补tensor族（src与`unit`片段按D-7甲路径）；性能系数环境变量贯通（测试侧读系数并自报工作量，被测物内部时限只读标量），且系数同时在配置期被`tests/CMakeLists.txt`读进`TIMEOUT`（`$ENV{NLANG_TEST_WORK_FACTOR}`，D-2）；e2e侧按D-7末段改清单子集化——`T1-debug-e2e`改设`NLANG_E2E_MANIFEST`为整份`manifest.txt`（示例趟随之退出每轮；`类别`过滤只作用于T0派生子集），T2腿的载体按守卫十一核对；收口批新增`T2-perf`腿（D-6）。
5. 前置根治（D-12五件）与资源互斥（D-11）。
6. 去锁（D-10）与文档同步（第十节），最后一步删锁——前面任何一步没落地就删锁，等于把冲突变成偶发红灯。

**守卫落点**：守卫不单独排队，随它保护的那次改动同批落地，否则出现「守卫先红、改动未到」的窗口，而那种窗口最容易以临时豁免收场（豁免名单忘了关就是永久的）。对应关系：守卫一（参考完备性）与第1步同批——第1步的验收标准本就是「四个ctest构型与三种e2e清单形态的每个被消费条目都有参考行」（perf构型的被消费集合是perf名集合与哨兵名集合的并集，D-3），两者同时成立，不存在谁先红；守卫二（孤儿行）与守卫七（常量自洽）也在第1步（前者只需参考表存在，后者只读D-1常量，可先于其他步骤）；守卫四（标量带门）随第2步；守卫三（棘轮）与守卫十（计时口径一致）随第3步（预算判定与`测量形态`比对都在消费点，接线之前无从判定）；守卫五（工作量一致性）、守卫六（慢集回补与口径）、守卫八（类别守卫）、守卫九（族选择器非空）与守卫十一（载体闭合）随第4步。第3步接线期间若某条目仍缺参考行，由ctest的`--timeout`兜底帽放行（第3步已写明），但缺行条目必须出现在该构型`ctest --show-only`枚举与参考表的差集报表里，差集按各构型的派生集合计算（守卫一口径；扫荡树按并集口径不设行的条目不计入差集，D-3）；第4步结束时该差集必须为空，此后不再有豁免名单。

顺序上的一个硬约束：第6步必须与第5步同批或在其之后提交，中间任何提交点都不得处于「已去锁、未去真实互斥」的状态。第5步与第6步谁先谁后属实施计划的调度细节，本文只约束「不得反向」。

## 十一、风险与已知限制

| 风险 | 缓解 |
|---|---|
| ctest腿的预算判定在跑完之后，超预算条目已把整条时间付掉 | 看门狗帽封顶最坏等待；e2e与自研包装器内联判定，只有ctest腿是后判（F-4所限，ctest无旋钮） |
| 看门狗帽从今天的紧经验值抬到`max(参考×10, 120)`，挂死的红灯趟要等更久才出结论 | 只有真挂死才付这笔（今日帽相对实测普遍留百倍级空档，F-3：ASan树91条可测的有帽条目中位占用率约1%，逼近帽的只有个位数条目）；e2e与包装器内联判定不受影响；挂死条目下一轮进`--repeat after-timeout`例外取证流程 |

| 争用是逐条目不均的：有的条目受并行影响1.1倍，有的3倍，中位标量对后者偏乐观 | 个别条目出预算时按D-15处置（人判：真实慢化改参考，争用敏感写例外行），不用「把整表乘大」逃避；守卫十钉住口径一致 |
| 参考表需随改动维护，可能漂移 | `--record`重录＋只降不升棘轮（D-15）＋孤儿行守卫＋`类别`列不被重录冲掉（守卫六） |
| 机型差异超出标量带，且跨机倍率分布尚未实测 | 带门判红并要求按机型重录（或本机覆盖文件），不外推（D-4）；实施第1步强制第二台机器实测后再定参考表是否分机型 |
| junit的逐条目耗时口径与参考录制口径不一致（串行录、并行判） | 参考行带`测量形态`列，守卫十比对口径并拒绝混用（D-2末段） |

| 去锁后两会话并发，真实互斥面可能没勘察全 | 前置根治（D-12五件）先做；资源claim在腿组装层显式声明并全部落`LOCK`行，冲突可归因，不用白名单排除逃避 |
| 去锁后陈旧工具守卫与并发的时序窗（守卫读工具mtime，重建与守卫交错会误判） | 守卫在其所属腿的资源claim内执行，重建腿与测试腿之间靠`build-dir:<指纹>`串行 |
| 工作量自报是新契约：字段名各写各的、或干脆没报，判定侧就会拿缺进去的工作量当真 | 自报字段按条目自身单位命名（`rounds=`、`cases=`一类，与参考行`参考工作量`列同单位），**没报即红**而不是按缺省1通过；守卫五实测整条链路（D-8） |
| ASan构型30轮可能撞不上那个被弃`ConcreteParamList`的所有权错误 | 该错误在ASan下当场即报，撞不上时抬系数即回100轮口径，成本可控；实施期若实测表明需要更多轮，按实测上调该构型行的`参考工作量`，而不是把条目搬回排期轴（D-9规则2） |
| 收口批多一条`T2-perf`腿，性能类条目按系数长跑会把收口批墙钟拉长一个量级 | 该腿只在打tag前跑（release级门禁同点），例行腿一条不含（守卫八）；跑多久由人按环境给`NLANG_TEST_WORK_FACTOR`（缺省1），守卫十一只核「有没有载体」不核跑多久——长跑成本归强度轴而不是排期轴（D-8） |
| 示例面退出每轮（`T1-debug-e2e`改设清单后不再附示例趟），44条示例的验收晚到收口 | 载体是`T2-release-e2e`（实测今天该腿与`T1-debug-e2e`都附这一趟，退出只发生在T1），守卫十一钉住该载体不缺；示例是验收程序而非单元覆盖，其回归通常先在语言面/标准库面条目现形，与mnist那行同型、代价已计入 |
| 去锁后两会话并发，`threads_tests`的错峰顺序断言在争用下可能翻转判红 | 该条目的激励窗口与放弃阈值读同一个`NLANG_GATE_MACHINE_SCALE`（D-12第4条第3类），失败文案直说时序敏感并指向例外行；D-14不给重试，处置是人判（改激励形态或按例外行在性能环境跑），不用白名单排除逃避 |
| Qt界面族在ASan构型退出每轮，那四条的内存缺陷发现从T1推迟到T2 | 功能面由IDE构型的Debug腿每轮照常覆盖（该族在Debug与IDE构型仍标常规）；内存面由T2的ASan全量形态承接（四条ctest腿在T2不带类别`-E`，守卫十一按`(ASan构型, 条目)`配对钉载体不缺）；`tools/test_families.txt`没有Qt/nide族，故这四条走乙路径，由`理由`列写明这两个载体（守卫六）——不得写成甲路径，那会把「少跑」误记成「有族回补」 |

- lit的耗时档案只用于排序：`By default, lit will run failing tests first, then run tests in descending execution time order to optimize concurrency… The timing data is stored in the test_exec_root in a file named .lit_test_times.txt.`（同上URL）；源码里历史耗时只被读成`previous_elapsed = abs(time)`与`previous_failure = time < 0`并用于`main.py::determine_order`排序，没有任何超时判定读它（<https://github.com/llvm/llvm-project/blob/main/llvm/utils/lit/lit/Test.py>、<https://github.com/llvm/llvm-project/blob/main/llvm/utils/lit/lit/main.py>）。
- lit把失败与超时的耗时记成负数：`Mark the elapsed time for failed tests as negative so LIT can distingiush failed from successful test runs just based on the time value.`（原文含拼写错误，`time = min(-t.result.elapsed, -1.0e-6) if t.isFailure() else t.result.elapsed`，<https://github.com/llvm/llvm-project/blob/main/llvm/utils/lit/lit/TestTimes.py>）；`ResultCode("TIMEOUT", "Timed Out", True)`的末位字段即isFailure，故超时同样记负（D-14引用此点）。
- lit没有按历史耗时推预算的旋钮：`maxTimeBudget`/`maxTimeAverage`/`maxTimeMultiplier`在CLI定义、`TestingConfig.py`与命令指南中均0命中，相近者只有全局`--max-time`。
- Bazel每类别秒数：`timeout / Time Limit (sec.): short 60, moderate 300, long 900, eternal 3600`，且`Tests which do not explicitly specify a timeout have one implied based on the test's size`（<https://bazel.build/reference/test-encyclopedia>）。
- Bazel告警旗标不改帽、建议双向：手册条目无任何百分比——`Using this option does not affect a test's timeout value, merely warns if Bazel thinks the timeout could be restricted further.`（<https://bazel.build/docs/user-manual#test-verbose-timeout-warnings>）；阈值只在源码里：`Only suggest timeouts that are less than 75% of the actual timeout (unless there are no higher timeouts).`、`Set fuzzy minimum timeout to half the previous timeout…`、`Set fuzzy maximum timeout to 90% of the timeout. A test this close to the limit can easily become timeout flaky.`（<https://github.com/bazelbuild/bazel/blob/master/src/main/java/com/google/devtools/build/lib/packages/TestTimeout.java>）——75%是「建议值」的上限而非触发点，达到90%时建议的是更长类别，故建议是双向的（D-15据此说明本仓「只降不升」是有意收紧而非沿用）。
- Bazel #12411仍未解决：`Bazel warnings related to test timeouts still use defaults instead of the specified override`（<https://github.com/bazelbuild/bazel/issues/12411>）；源码`shouldEmitTestSizeWarningInSummary`读的是声明的timeout属性，从不读`--test_timeout`覆盖表（<https://github.com/bazelbuild/bazel/blob/master/src/main/java/com/google/devtools/build/lib/runtime/TestResultAggregator.java>）。
- CTest的`--timeout`只给无帽条目设默认：`This option effectively sets a timeout on all tests that do not already have a timeout set on them via the TIMEOUT property.`（<https://cmake.org/cmake/help/latest/manual/ctest.1.html>）；`TIMEOUT`属性页：`This setting takes precedence over CTEST_TEST_TIMEOUT.`（<https://cmake.org/cmake/help/latest/prop_test/TIMEOUT.html>）。「该属性在配置期固定」是对文档的准确转述而非原文，本文按转述使用。
- CTest文档面没有任何按机器缩放的超时旋钮：文档列出的入口为`--timeout`、`CTEST_TEST_TIMEOUT`、`--stop-time`、`--test-timeout`、`TIMEOUT_AFTER_MATCH`、`TIMEOUT_SIGNAL_NAME`，均为定值或全局截止（同上URL）。
- CTest的超时重试用途语：`after-timeout — Allow each test to run up to <n> times in order to pass. Repeats tests only if they timeout. This is useful in tolerating sporadic timeouts in test cases on busy machines.`（同上URL，D-14引用）。
- CTest的`TIMEOUT_AFTER_MATCH`官方用途与D-2的分离同型：`Because the test's start time is reset, its execution time will not include any time that was spent waiting for the matching output.`、`Set TIMEOUT to a longer duration that accounts for resource acquisition and use TIMEOUT_AFTER_MATCH to control how long the actual test is allowed to run.`（<https://cmake.org/cmake/help/latest/prop_test/TIMEOUT_AFTER_MATCH.html>）
- CTest调度面手段原文：`If multiple tests specify the same resource lock, they are guaranteed not to run concurrently.`（<https://cmake.org/cmake/help/latest/prop_test/RESOURCE_LOCK.html>，该句无范围限定词，跨进程范围靠F-11实测）、`Do not run this test in parallel with any other test.`（`RUN_SERIAL`）、`Set to specify how many process slots this test requires. If not set, the default is 1 processor.`（`PROCESSORS`）、`While running tests in parallel (e.g. with -j), try not to start tests when they may cause the CPU load to pass above a given threshold.`（`--test-load`，均在ctest(1)同页）。

**从本文撤出的四条**：①lit的参数名曾写成`test_timeout`，实为`maxIndividualTestTime`；②曾称Bazel的告警是「只在实测低于帽75%时建议下调、只降不升的棘轮」，实为双向建议且75%是建议值上限、百分比不在用户文档里；③曾把「`RESOURCE_LOCK`只在单个ctest进程内」当作文档立场，实为文档未言及、由F-11实测确定的实现事实；④旧台账曾引「lldb套件把消毒器构建的等待上限从120秒抬到600秒」佐证按构型调帽，与PR llvm/llvm-project#197953的实际改动不符——非消毒器路径的120秒未变，ASan路径是从最坏1200秒的轮询改为600秒以对齐`lit_config.maxIndividualTestTime = 600`（<https://github.com/llvm/llvm-project/pull/197953>），该说法不再作为本文论据。
